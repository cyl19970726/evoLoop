# evoLoop project guidance

evoLoop studies and builds a project system that learns from real work: sessions contribute evidence and knowledge, a dedicated cognition session reconciles it and drives the next step, and responsibilities evolve when outcomes justify change. Start with [CONTRIBUTING.md](CONTRIBUTING.md); use [product definition](docs/product/definition.md), [architecture](docs/architecture/overview.md), and [development standards](docs/development/standards.md) for the current published contract. [Research](docs/research/README.md) contains publishable investigations, experiment protocols, results, and proposals; it is evidence, not current authority. The former validation reports have moved there. Earlier `docs/design/` remains local historical evidence.

- Complete work in the responsible domain, including fixes and verification. A product or architecture session need not hand every implementation task to one central developer. New persistent roles require evidence, a trial, and a review condition; a new chat window alone is not a new role.
- Feishu Bitable is the intended task authority. An external knowledge system or vault owns the living Wiki, including its text and revisions; it may use Markdown but must stay outside this development repository. This repository owns formal product, architecture, development, and configuration documents. Do not copy task status or Wiki bodies here as a second editable authority.
- Preserve provenance, the observed revision, conflicting interpretations, and superseded decisions when changing knowledge. A successful notification is not evidence that the receiving session used it. Report implementation checks and user-facing validation separately.
- Use the [package architecture](docs/architecture/packages.md) and [Codex integration](docs/architecture/codex-integration.md) as proposed implementation boundaries. Dogfood findings and feature proposals enter the same task authority; schedules create traceable work under the same acceptance rules. App Server threads and existing desktop chats are separate integration surfaces until interoperability is verified.
- Respect the current stage: `docs/` and isolated Wiki experiments exist; the harness, production Feishu adapter, and production Wiki are not deployed. PostgreSQL is selected for runtime persistence; the rest of the application technology stack remains proposed. Describe a proposed interface or check as planned until it has run.
- Before production implementation, review the [technology selection proposal](docs/architecture/technology-selection.md) and package boundaries. The recommended TypeScript/Node stack and OpenViking foundation remain proposals until adopted; PostgreSQL holds runtime records, not a second task or Wiki authority. Fixed-version research results do not transfer automatically to a newer release or another client language.
- Keep raw sessions, archives, external Wiki contents, secrets, local run outputs, and private source material out of public GitHub. Review public document links and assets before publishing. Preserve unrelated work in this shared workspace.
- Keep future publishable exploration in `docs/research/`, with the question, scope/version, method, observations, limitations, and decision impact. Add pages to the research index and site manifest. Preserve original experiment evidence outside the public repository; research reports do not become a second living Wiki or task authority.
- Project skills belong at `.agents/skills/<name>/SKILL.md`. Do not install or register a global skill without the user's specific global-scope authorization.
- For documentation changes, follow [documentation maintenance](docs/development/documentation.md). The local documentation toolchain provides `npm ci`, `npm test`, `npm run docs:check`, and `npm run docs:build`; also run `git diff --check` in a Git checkout. A GitHub Actions workflow is present, but report remote CI only from the run for the relevant commit. No branch protection or public site deployment is implied.
