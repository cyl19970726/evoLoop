# evoLoop project guidance

Start with [CONTRIBUTING.md](CONTRIBUTING.md): select the task's reading path, make the change, and verify it. Read only the relevant product, architecture, or development sections; use [docs/README.md](docs/README.md) to find more. Current decisions live in [docs/decisions.md](docs/decisions.md); research is evidence and proposals, not adoption.

- Complete authorized work in the responsible domain, including fixes and verification. A product or architecture session may implement its own fixes. New persistent responsibilities require evidence, a trial, and a review condition; a new chat alone is not a new role.
- Frontend design and implementation start at [the frontend documents](docs/frontend/README.md), then the affected page and shared interaction rules. Product goals and cross-system contracts retain their existing authoritative locations.
- The workbench primarily helps humans observe progress, evidence, changes and results. Most routine changes follow a human conversation with an Agent, which uses the project-local `evoloop-workflow` business skill in `.agents/skills/` and the [CLI](docs/development/agent-cli.md), then reads back the shared service state. Both interfaces use the same authorization, fixed revisions and operation recovery; frontend development skills are not product business skills.
- Respect the stage: use [the roadmap](docs/roadmap.md) for current capabilities and acceptance scope, [local operation](docs/development/local-run.md) for runtime and migration requirements, and the lockfile for selected versions. Bounded local or Agent use does not establish human experience, external-service guarantees or production readiness. PostgreSQL owns core project data and runtime persistence; OpenViking is the first replaceable knowledge backend (DEC-027), with Wiki bodies outside this repository. Follow the [implementation entry](docs/development/standards.md#开始业务实现时) when extending business implementation.
- Keep each source authoritative: evoLoop owns Task/Schedule and process Document revisions in PostgreSQL; Feishu is a connector. Repository product, architecture, development and configuration documents stay in each repo's `docs/`, outside Document Table. Living Wiki text and revisions remain outside this development repository. Details and revision flow belong to [documentation maintenance](docs/development/documentation.md#每类事实的权威位置) and [project data](docs/architecture/project-data.md).
- Preserve provenance, observed revisions and superseded decisions. Separate design, source inference, actual execution and user use; a notification does not prove consumption. Follow [evidence and delivery rules](docs/development/standards.md#证据与交付).
- Preserve others' work in this shared checkout. Agree file ownership and hand off evidence using [session coordination](docs/development/standards.md#多-session-协作); do not switch the shared branch or include unrelated changes in a commit.
- Keep raw sessions, external Wiki bodies, secrets and private run material out of public Git. Use the [documentation workflow](docs/development/documentation.md) for publication and checks. Project skills belong at `.agents/skills/<name>/SKILL.md`; global installation or registration requires the user's specific global-scope authorization.

- The project-local `development-workflow` skill at `.agents/skills/development-workflow/SKILL.md` supports building, reviewing and evolving engineering norms and their evaluation. It is distinct from the `evoloop-workflow` product business skill. Version project skills through focused PRs so new worktrees receive the same guidance; do not require every skill for every task.
