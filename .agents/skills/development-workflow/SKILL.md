# 开发规范与流程

把项目的目标和约束，变成开发者能使用、能验证、能修订的工作方式。
你负责贯通规范、工具配置和实际执行：AGENTS.md 提供入口，Git 支持协作，CI 提供检查，CD 完成运行交付；这些组成由项目的真实需要决定。

**工作单位是一项开发决定。** 例如“这次改动该检查什么”“这个 PR 现在能否合并”“部署结果不明时下一步做什么”。从决定出发，才能判断该写规则、修工具，还是维持现状。

沿着这条线工作：**选一项真实工作 → 找到决定失准的原因 → 改进对应机制 → 实际使用 → 据结果修订。**
新项目从即将发生的工作开始；已有项目从实际任务与历史开始。普通功能开发照现行流程完成，遇到相关缺口再修复。

## 在 evoLoop 中承接这项工作

从 `AGENTS.md` → `CONTRIBUTING.md` 选择本次入口。通过 evoLoop 分派的 Task，同时用 `../evoloop-workflow/SKILL.md` 核身份、固定 context 和交付路径；写任务或交接说明时读其 `references/writing.md`。本 skill 负责如何改进工程方法，业务 skill 负责如何读取和记录工作，两者不互相排除。

Lead 负责目标、范围、责任选择和交付回收；规范负责人修项目 skill、入口与检查/交接方法；功能开发负责人修具体业务能力；产品文档负责人维护产品模型。按真实 Role 与授权承接，不用职责名称推定已有常驻 Session。必要跨域修改先约定文件所有权，普通功能修复无需经过规范负责人审批。具体分派、返工和同 Session 再承接见[CLI 交接路径](../../../docs/development/agent-cli.md#lead-分派返工与再次承接)。

截至 2026-10-28，本项目的产品与架构职责没有专属 skill：先从各自 Role 职责、`docs/product/` 或 `docs/architecture/` 的权威正文和本次固定 Task 工作。它们可以把个案的来源、判断和反例留在适当 Document/Wiki；只有后续任务反复需要同一种判断方法，才提出项目内 skill 的具体增量。不能以新建空文件代替方法，也不能因换聊天复制 skill 或新增全局安装。

## 1. 选一项工作，讲清要改善的决定

先读正常项目入口和本次相关现场，确认目标、当前阶段、有效授权与已采纳约束。提案、旧记录和现行合同分开看；影响本次工作的冲突要保留来源并解决。

以一项任务为锚点，回答：开发者需要决定什么？当时能获得哪些信息？怎样的动作与结果算合理？
从零建立流程时，也可以用下一次普通改动作锚点，无须等待事故。需要覆盖多个领域时，选择能体现其不同决定的代表工作，不要求遍历全仓库。

例如，目标是“最新提交检查通过后才合并”。现场却只有旧提交的绿色结果。此时需要改善的是**合并依据与待合并版本的对应关系**。“加强质量意识”无法告诉执行者下一步该做什么。

## 2. 判断原因，选择改动位置

沿“可获得的信息 → 决定 → 动作 → 产物与后续结果”检查断点。Agent 的完成叙述是线索，要与调用结果、文件和版本核对。

| 观察到的问题 | 优先考虑的改法 |
| --- | --- |
| 规则合理，但入口找不到或多处互相矛盾 | 修入口、合并权威正文，保留必要引用 |
| 规则要求的动作没有工具支持，或承诺超出实际覆盖 | 补能力，或准确缩小保证并安排适当人工核验 |
| 当前方法造成反复返工、等待或无效检查 | 调整方法、检查范围或协作方式，比较成本 |
| 信息和能力齐备，执行却跳过了适用要求 | 定位跳过原因，修执行路径或反馈；单纯加重措辞通常无效 |
| 实际行为合理，只是偏离作者预想步骤 | 接受合理替代做法，修正评价标准或含混规则 |

继续上例：如果 CI 根本不在 PR 上运行，应修配置；如果有结果却取错提交，应修结果核对；如果当前提交已失败，应先处理失败。三者不应统一变成“再加一次 review”。

选择能解决原因的最小改动，包含保留、删除和合并。用户授权边界与有效合同持续约束工作；可试行和退出的是工作方法，实验结论不能自行取消授权。

## 3. 做成下一位开发者能直接使用的结果

在授权范围内修改相关正文、脚本或配置，并完成项目要求的验证。把规则放回现有权威位置，其他入口用链接接入。

本次若是实际仓库工程任务，沿[贡献流程](../../../CONTRIBUTING.md#提出与完成变更)从现场与方案走到隔离 worktree、必要回归、集成差异自审、聚焦 PR、当前 head 检查与独立审阅、正常合并。通过 evoLoop 承接时，再按[业务 CLI 工程交接](../../../docs/development/agent-cli.md#仓库工程任务与动作交接)核身份和回执；方法说明不授予受限目录、Git 或 PR 权限。失败保留在原 Task，真实使用与代码合并分别验。

| 承载位置 | 应帮助开发者完成什么 |
| --- | --- |
| AGENTS.md 与贡献入口 | 找到适用规则，理解稳定约束，进入本次所需步骤 |
| Git 协作约定 | 保护已有改动，隔离并行工作，形成聚焦差异，审查、合并和恢复 |
| 验证说明、脚本与 CI | 选对检查，理解覆盖范围，把结果对应到实际版本 |
| 发布约定与 CD | 确认授权、版本和环境，核验交付结果，处理未知与回退 |

涉及哪一部分，再查 [工程控制](references/engineering-controls.md) 的对应章节。尚无部署目标的项目可以没有 CD；技术栈、分支策略和文件布局沿用项目选择。

一条可用规则应让执行者看出**何时适用、怎么决定、什么算证据、缺证据怎么办**。例如在确有此合并合同的项目中，可以写：

> 合并前核对当前 PR head 与必要检查的提交标识。待合并版本的检查未成功时继续处理或等待。核对后 head 发生变化，重新核对。交付记录写明实际依据的版本和结果。

这只是表达示例。具体哪些检查必要、谁能合并，由目标项目的合同与真实配置决定，不照搬成通用政策。

## 4. 让实际使用检验规则和 skill

先固定任务、候选版本、预期行为和失败信号，再执行；预期依据用户目标与项目合同制定。按 [评价方法](references/evaluation.md) 组织两种观察：

**向前看：下一位 Agent 能用吗？** 给无本轮会话历史的 Agent 正常项目入口、真实任务和必要材料，让它实际修改、运行和交付。评价标准另存，预期答案、旧结论和修复提示不交给执行者；权限与工作边界仍须说清。

**向后看：真实开发中发生了什么？** 用任务当时的规则和授权核对历史，恢复关键决定、动作、产物和后续结果，分别判为符合、偏离、不适用或证据不足。缺日志保留为未知，后来的要求不能追溯成先前违规。

上例可以用“旧 head 成功、当前 head 等待中”的情境检验合并判断。检查实际动作和产物，不能只看它是否复述“应核对最新 CI”。

评价本 skill 时，新 Agent 必须实际使用候选 skill 完成流程工作。还要观察它能否找到当前入口、分清必做与按需、选出下一步；功能完成并不自动说明表达清楚。记录理解阻塞发生在哪里，避免只给“完整、清晰”之类总评。

若任务专门检验任务表达，选择功能修复、文档审核、探索调查等会导向不同动作的真实样本。保留来源 Task 的固定历史，另做候选；让新读者用候选 skill 产生实际交接稿、审阅差异或调查产物，观察能否选对责任、第一步和检查，而非只让它复述模板。执行输入与评价判据分开；作者已读过答案的自测不能冒充独立使用。独立读者由 Lead 组织时，交付固定候选和输入，标为待验，不自行增开 Run。

选取与变更风险相称的任务，不为每次小修重跑完整实验。无历史继承仍可能共享系统指令与模型先验，需披露；结构检查只证明格式。任务成功支持已测范围，若声称提效或因果收益，还需要可比的旧流程或简化路径及成本证据。

## 5. 按结果采纳、修订或退出

角色方法的改进也走这一步：记录真实摩擦与当时可用版本，判断是任务输入、Role 职责、CLI 能力还是 skill 方法的问题。只把有适用条件和可观察检查的复用方法改到现有项目 skill；留来源、修订和下次真实任务的复看条件。若新方法增加无效读取、误导决策或返工，按原修订回看并简化或撤回。修改 Role 责任范围与公共派单规则时由相应负责人协调，不靠一次局部失败扩大所有职责。

交付可审查的改动与实际验证：改变了哪个决定、产物在哪里、观察到什么、还有什么未验证。规范采纳、代码合并、构建成功、部署完成和用户目标达成分别报告。

按项目既有审查方式采纳，保留来源、版本和必要的替代关系。原始私密会话与内部材料留在受控位置，公开只保留必要去敏结论。
目标、阶段、工具能力或协作方式改变，出现反例或明显负担时复查；有效的保留，失效的修复、简化或删除。架构角色可负责这项工作，无须另建永久审批角色；周期监控需用户另行授权。
