# 评价开发规范、流程与本 skill

## 先固定问题与预期

明确是在验证“能找到并遵守规则”“规则与工具事实一致”，还是“规则改善了工作结果”。三者需要不同证据。
预期来自用户目标、有效授权、已采纳合同及真实能力；不能只用候选规范给自身打分。
在执行前记录候选版本、任务与环境、适用规则、触发条件、可接受替代做法、预期行为和产物、失败信号及限制。
记录可以放在既有任务或评价笔记里，不要求每次修改新增模板或数据库。

评价 Task/Role skill 的接手链时，固定公开 Task 的完整验收与所有必要权限；把额外评分判据、预期答案和旧审计结论留给评价者。候选、实际 Run 输入和已发布服务/工作区 skill 的版本分别记录，避免用更新后的文件解释旧执行。

规则有效的最低链条是：适用情境 → 规则可获得且可理解 → 决策与动作合理 → 产物和下游结果满足目标，成本可接受。
规范写得完整、Agent 复述准确、测试数量多，都不能单独证明这条链成立。

## 前向：无会话历史的实际使用

### 准备

- 固定候选 skill/规范和项目快照；记录实际使用版本。评价 skill 时，任务应要求 Agent 用它完成具体流程工作，而非只评审 skill 文字。
- 使用真实且有代表性的任务；合成夹具适合可控反例，但标明合成，不把植入故障说成历史真实事故。
- 让新 Agent 从正常项目入口工作，提供业务原始材料和必要环境。不要把预期答案、怀疑的问题、历史结论或修复提示混入任务。
- 把评价标准与执行者输入分开保存。权限、隔离目录、允许的副作用、完成边界仍须明确，不能为“盲”而隐藏安全或任务条件。
- 使用支持无历史继承的运行模式，例如 fresh session / `fork_turns=none`；记录实际设置。它仍可能共享系统指令、模型先验、工具与全局规则，报告这一限制。
- 选择隔离工作区，保护真实仓库与外部系统。不能模拟的能力标为未验证；不为了评价未经授权部署、发信或改远端规则。

### 执行与检查

让 Agent 实际读取、决定、编辑、运行检查并交付。保存足以回查的输入、工具动作/结果、diff、版本和产物；有条件时保留完整运行记录。
按目标选择有区分力的正常情境、反例和边界；不必每次覆盖所有工程控制。

可选情境包括：

| 要验证的决定 | 有区分力的任务 |
| --- | --- |
| 验证与风险匹配 | 普通文档修改；行为修复需要有效回归测试 |
| 工具保证准确 | 文档宣称全面扫描，工具实际只扫描特定输入与模式 |
| 协作边界 | 工作区有他人未提交改动，仍需形成聚焦产物 |
| 合并依据 | 旧提交 CI 成功，当前 head 待运行或失败 |
| 交付依据 | 构建成功但未部署；写入返回不明但远端已完成 |
| 跨项目复用 | 不同技术栈或无 PR 平台的项目，仍能合理设计流程 |

评价者依据预先固定的标准核查实际产物和执行，而非执行者自评。声称测试通过要有对应输出，声称合并/部署要有固定版本的远端或运行证据。
接手评价逐段记录：固定目标与验收是否读全，Role/skill 如何取得，必要原件哪些页或图片实际可见，哪里重复或截断，提问是否到达并被回答，哪些部分由人补齐，成果的消费者是否真的据此行动。已验证过的资料读取或同 Session 续作可以引用其固定证据；只补缺少的跨模块观察，不机械重复整套测试。
记录符合、偏离、不适用和证据不足；对意外但合理的替代做法按目标判断，不因不符合作者预想步骤就判失败。
作者可以修复发现的问题。复跑相同题目要说明 Agent 是否已知道答案；已知上下文的定向复测不能充当新的盲测。
结构校验只证明 skill 格式等机械约束；实际使用成功也只支持已测任务范围。

## 后向：核对真实开发历史

先选样本，再读结论。包含成功、失败与普通任务，说明选择范围；投诉案例可定位问题，但不能代表总体发生率。
按任务发生时的规范版本、用户要求、授权与环境评价，不把后来新增的要求追溯成之前的违规。

恢复每个关键决定：任务与触发事实 → 当时可用规则/信息 → 理解与决定 → 工具动作 → 结果与产物 → 后续使用和成本。
对照原始调用与结果、Git 对象和配置、CI/部署回执；把 Agent 叙述与实际物证分开。
有 `session-forensics` 类能力时可用其恢复历史；没有时仍按上述链条检查可获得的原始记录。不要用记忆摘要替代决定性原始证据，也不要求安装全局 skill。
未见读取调用不等于没读过；未见结果证据也不等于动作完成。截断、加密、缺日志、版本缺失等必须保留为证据限制。

逐项给出：

- **符合**：适用要求与行为有对应证据。
- **偏离**：适用要求和实际行为明确不一致，说明造成的影响。
- **不适用**：触发条件、阶段或权限范围不成立。
- **证据不足**：无法可靠重建要求、动作或结果；说明缺什么。

再判断成因：规则错误/遗漏/含混或难发现，工具能力缺口，输入/授权不足，执行者跳过，合理例外，或评价设计不当。
不要自动归责执行者或追加条款。私密原始记录留在受控位置，公开只保留必要去敏结论与可公开来源。

## 从符合性走到有效性

同时观察任务质量、用户目标达成、返工、人工纠偏与介入，以及阅读、等待、测试、维护成本。
若声称比原流程更好或改善由规范造成，需要可比的旧规则/简化路径、相近任务难度与环境，并说明模型、全局指令和工具等混杂因素。
没有对照时，报告具体案例和范围，不编造增益百分比，不把“Agent 成功”归因于 skill。
一轮成功不证明跨项目长期有效；一次失败也不证明所有规则无效。优先做能区分竞争解释的下一次验证。

把结论分成：观察到的行为与证据、对偏差原因的判断、最小改进、已实际完成的复测、未覆盖范围。
结果应驱动保留、修复、简化或退出，而不是不断增加门槛。
