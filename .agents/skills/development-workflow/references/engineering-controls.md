# 工程控制：规则必须对应实际能力

按本次涉及的范围读取和核对。以下是决策提示，不是所有项目必须新增的文件、检查或关卡。

## 入口、权威与 AGENTS.md

- 找到当前工作目录真正适用的指导及其作用域。区分用户授权、项目合同、局部覆盖、待采纳提案和旧记录；不要仅按文件名或更新时间猜权威。
- AGENTS.md 放稳定的项目约束、入口和决策边界。详细步骤归属现有贡献指南、开发文档、工具或专项 skill；避免一条要求在多处完整复制。
- 入口要足以让新 Agent 找到相关规则，同时避免为了一个小改动强制读取所有文档。检查链接和规则是否真能被当前客户端发现。
- 对模型、权限、目录、命令、平台能力的说明必须核对实际环境。项目 skill 默认留在项目内；跨项目安装和发现遵循用户的明确授权，不能由 skill 自行扩大。
- 规范可以规定结果和边界，保留执行者对可逆实现细节的判断。每个强制动作都应能说明它防止的错误或满足的合同。

## Git 与多人协作

- 先确认负责的仓库、分支、工作区和已有改动，避免覆盖或提交他人的工作。并行编辑需要明确所有权；是否使用 worktree 由共享风险与项目惯例决定。
- 采用项目已有的分支、提交、PR 和 review 方式；流程不必一律等同 GitHub PR。提交包含可解释的相关改动和验证，避免顺带整理整个仓库。
- 合并条件要对应将要合并的版本。核对目标分支、当前 head、必要检查和审查；旧 head 成功不证明最新提交成功。检查后 head 变化时重新核对，支持时使用预期 head 限制合并。
- 核对实际审批身份：多个 Agent 共用一个 GitHub 身份不等于多位可批准者。本机独立审阅与平台 approving review 分别留证；平台门槛须能由当前身份或可信检查真正履行，不能通过伪造批准或常规绕过满足形式。
- 文档中的“必须通过”与平台真正强制的保护规则是不同事实。平台不可读时记录未知，不能因为 workflow 文件存在就声称保护已开启。
- 推送、合并或其他写入返回不明时，先回读远端状态与对象标识，再决定是否重试；不能凭超时判断失败，也不能凭本地提交判断远端成功。
- 恢复方式应与影响匹配：保留现场，理解已共享的提交和依赖后选择修复或回退。不要擅自丢弃改动或改写共享历史。

## 本地验证与 CI

- 从实际脚本、实现和工作流确认命令、依赖、运行条件与覆盖范围。区分静态检查、单元测试、集成测试、构建与真实场景验证，描述它们各自能证明什么。
- 改持久模型或状态时，除迁移非空旧数据外，还核旧对象继续读取、写入、固定依据与恢复的相关组合。保留旧修订和失败，不以换对象掩盖接续缺口；工具升级不证明所有已有实例已升级。
- 检查应跟随变更风险。行为修复优先能复现问题的回归测试；文档或轻微外观修改使用适合的检查。完成项目必需检查后，只有新改动、失败或未解决风险才需要重复或扩大。
- 自动检查保证应写到可观察的精度。例如只扫描发布 Markdown 的几种路径前缀，不能描述为“阻止所有文件中的本机路径泄露”；可选择缩小声明或扩展工具，取决于实际目标。
- 核对 CI 触发条件、路径过滤、运行版本、权限与本地命令是否匹配。避免必须检查被过滤而永远等待；涉及不可信输入、凭据或写权限时检查其边界。
- CI 结果需带提交标识、相关任务和状态。pending、跳过、取消、缺失和成功不可互换；需要哪些任务以当前合同和实际配置为准。
- 不通过停用检查、绕过钩子或放宽断言制造成功。失败要定位是实现、环境还是规则问题，并报告未验证的部分。

## CD 与运行交付

- 先确定是否已有交付目标、环境、发布权限和实际机制。只有 CI 时如实写明无自动部署，不把构建产物当运行交付，也不为了流程完整擅建 CD。
- 需要部署时，明确要发布的固定版本、目标环境、配置与凭据来源、成功信号和恢复路径。数据库或不可逆数据变更需要项目适用的备份、兼容与迁移判断。
- 发布回执、健康检查和实际使用分别提供不同证据。核对运行版本和目标环境，避免“服务可访问”掩盖旧版本仍在运行。
- 写入结果未知时先核对已部署版本与状态，使用现有幂等机制或标识避免重复动作；不要无依据地重发、重跑迁移或反向回退。
- 用户授权和既有审批边界持续有效。提前准备可审查产物、验证和恢复说明；确有缺少的授权时再请求，不能自行新增无来源的审批仪式。

## 把控制与成本一起维护

规则的责任要对应有人或工具真正能够完成的动作。没有能力时，应补能力、缩小保证或明确人工核验，不能只增加“必须”。
观察阅读、等待、测试、维护和人工介入成本。重复失效的规则应定位原因；试用有明确范围和复查信号，不自动永久化。
采用项目已有记录保存决定和验证证据，不另建竞争性的任务权威或强制台账。
