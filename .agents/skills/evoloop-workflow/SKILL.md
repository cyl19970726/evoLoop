# evoLoop business work

The usual handoff is: a person sees progress and evidence in the workbench, discusses the goal or decision in an existing Agent session, you act through the project CLI, then the person sees the result in the same project's read views. The workbench is mainly for human observation, reading, traceability, and feedback; do not require a person to click through routine work. Act only within the authority actually given in that conversation and by the project service. This skill cannot grant additional rights or turn a discussion into automatic acceptance.

Use the project-local CLI against the authorized coordinator. Start with `npm run --silent cli -- help` and `npm run --silent cli -- session`; use [`agent-cli.md`](../../../docs/development/agent-cli.md) for setup, command forms, and recovery. The CLI and core API share the workbench's business boundary. If a named command or request is absent from `help`, `command types`, or `request types`, do not invent it.

For an assigned Task, read its current state and `context` before acting. A Task already `ready` or `active` needs no repeated judgment or acceptance; `task.judge` addresses a proposal, and delivery follows a started execution. Do not run every Task through a fixed sequence regardless of state. Keep the TaskRevision, sealed Document revisions, source hashes, and any partial or unavailable reads visible in your result. If the 16 MiB context budget marks a fixed source `partial`, read that revision separately with `original`. For a Document or knowledge assignment, read the fixed revision and its provenance; a current title or search result alone is not the fixed basis. Ordinary authorized fixes can proceed directly. When evidence is insufficient, record a bounded investigation or a judgment with a relook condition rather than silently accepting new work or creating a permanent Role.

Use `command schema TYPE` for common commands and `request schema NAME` for named endpoints, including nested required fields and enums. Prepare the JSON file from that schema, submit through `command run` or `request NAME`, then read back the result and affected object. Keep `projectId`, `operationId`, and observed `expectedVersion`; never substitute a new operation ID after a timeout or unknown result. Consult `receipts` and the appropriate core operation or named external reconciliation. A 404 lookup does not prove a write failed. Stop on conflict, denied scope, incomplete fixed input, or unknown external outcome until the original intent is reconciled.

Keep evidence categories separate: native Run completion, technical validation, immutable delivery, the declared observer's actual use, Task closure, Stage review, and later adoption are different observations. Record the artifact revision and checks; report failed or unobserved consumer use honestly. Close only when the explicit acceptance and use conditions are met, and choose the next task, research, pause, or stop with a reason. Leave fixed results and links for the person to inspect in the workbench. An artificial test or Agent observation does not establish human use.

Keep tokens, raw sessions, external Wiki bodies, private originals, and local receipt files in a private local directory outside the repository or explicitly ignored by Git; never publish them. An `original --out` target must be a new directory under an existing parent. Use fixed links and permitted summaries when reporting what was read. Manual discussion handoff records are declarations, not proof that an existing Desktop chat received or adopted them.
