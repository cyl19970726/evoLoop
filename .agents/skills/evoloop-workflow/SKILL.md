# evoLoop business work

The usual handoff is: a person sees progress and evidence in the workbench, discusses the goal or decision in an existing Agent session, you act through the project CLI, then the person sees the result in the same project's read views. The workbench is mainly for human observation, reading, traceability, and feedback; do not require a person to click through routine work. Act only within the authority actually given in that conversation and by the project service. This skill cannot grant additional rights or turn a discussion into automatic acceptance.

Use the project-local CLI against the authorized coordinator. Start with `npm run --silent cli -- help` and `npm run --silent cli -- session`; use [`agent-cli.md`](../../../docs/development/agent-cli.md) for setup, command forms, and recovery. The CLI and core API share the workbench's business boundary. If a named command or request is absent from `help`, `command types`, or `request types`, do not invent it.

If the native input identifies a managed Loop/Dispatch/Run and supplies a private CLI wrapper, read [the managed worker guide](references/managed-workers.md). Use that wrapper instead of looking for a human's token. The controller already starts and fixes this Task; write a signed submission or bounded decision before the Turn ends. Ordinary `delivery.record` cannot run while this Run is in flight.

When writing or changing work, read [the writing guide](references/writing.md): make the content understandable without earlier chat, include necessary context and fixed links, use a diagram only where it clarifies the work, and keep acceptance observable. Task content has one authority in its primary Document; use Task commands to maintain it, not an independent edit to the same Document.

For an assigned Task, read its current state and `context` before acting. The four states are `todo`, `in_progress`, `done`, and `cancelled`. Create a bounded Task with `task.create` using clear content and independent acceptance; the service creates its primary Document atomically.

Before setting `consumer`, inspect the actual principal in `session` and establish who will personally use the current Delivery and sign the observation. For an Agent consumer, set the exact `principal.actorId` that will sign it, not a `roleId`, display name, or explanatory phrase; put explanation in `evidence` or `reason`. External human consumers remain supported by the existing reviewer-attestation contract. When actual use is part of acceptance, declare its `consumer` and set `useRequired: true` together. Then `task.close` requires the latest observation by the declared consumer for the current Delivery to have `result=used`; worker completion, a Delivery alone, or another actor's use cannot substitute.

Start it with `task.start` to publish/pin the primary. Omitting `basis` inherits and validates existing fixed sources; explicit `basis: []` deliberately removes other sources. To change a superseded source, record an applicable retain decision or explicitly select the intended fixed revisions; never silently read the latest version. No standalone spec or issue must be created first. Do not invent the old proposal/judgment/acceptance state sequence. A recorded todo does not expand actual authority. To change the body or acceptance of ongoing work, reconcile any in-flight Run, reopen, update, and start again; keep older results and fixed input history. Waiting or verification remains in progress with a clear reason and next action. Close only after the agreed evidence passes; consumer or human use is required only when the task explicitly requires it. Do not create a separate verification Task by default.

Keep the TaskRevision, primary Document revision, sealed source revisions, hashes, and any partial or unavailable reads visible. If the 16 MiB context budget marks a fixed source partial, read that revision separately with `original`. For other Document or knowledge assignments, read the fixed revision and provenance; a current title or search result alone is not a fixed basis. Ordinary authorized fixes can proceed directly; missing evidence calls for a bounded investigation, not an automatic permanent Role.

When the background Loop runner is already operating and the first cognition Task must inherit trace material, enroll the Loop with optional `initialState: "paused"`, declare and read back the bounded study material at the observed Loop version, then use `loop.state active`. Do not race an immediately active enrollment to attach evidence before its first poll. Omitting the field preserves the ordinary immediately active Loop.

For a managed trace study that should reach future cognition Tasks automatically, a project reviewer with read and write authority declares one bounded source Task revision and at most ten current formal Run decision IDs through `loop.studyMaterial.declare`; use `command schema` and then `read study DECLARATION_ID` to inspect the server-derived Run IDs, fixed Task revisions and input hashes. A configured controller inherits exactly those references into each newly software-created cognition Task before dispatch. Do not put Run IDs in Task prose, attach to a guessed future Task, or use a worker grant as a substitute for the declaration. `loop.studyMaterial.revoke` stops new inherited trace reads without erasing history. Source and business Tasks may be done; a replaced source slot, closed Session, revoked source grant, removed declaring reviewer credential, or incomplete copy blocks new access. An undeclared cognition Task continues normal work without automatic trace access.

For a trace-based division investigation, a reviewer may explicitly adopt a known terminal, owned Run as a Task external reference with `request schema reference.task-decide`: set `kind: "run"`, `referenceId` to that Run ID, `revision` to its fixed TaskRevision ID, and `contentHash` to its `inputHash`. This hash identifies the Run input, **not** its transcript. Read back the new Task revision and fixed reference before dispatch. The managed worker receives only this source metadata; use `read run RUN_ID --trace` to inspect the permitted native work trace when useful. Respect partial pages, unsupported item counts, revoked grants, closed sessions and unavailable native history; never infer complete evidence from a saved summary. A source Task moving later does not add access, and a role alone grants no trace access. Adoption is a reviewed evidence choice, not a new Role or proof that division improved outcomes.

Use `command schema TYPE` for common commands and `request schema NAME` for named endpoints, including nested required fields and enums. Prepare the JSON file from that schema, submit through `command run` or `request NAME`, then read back the result and affected object. Keep `projectId`, `operationId`, and observed `expectedVersion`; never substitute a new operation ID after a timeout or unknown result. Consult `receipts` and the appropriate core operation or named external reconciliation. A 404 lookup does not prove a write failed. For a saved transactional `/api/commands` intent, `receipts retry RECEIPT_UUID` first reconciles and can explicitly replay the exact same ID, actor, project, payload and version through core idempotency. It requires the recorded original actor to match the currently verified actor; older receipts without an actor can only reconcile. It cannot alter the intent or retry external uploads/publishing; never delete a pending receipt to bypass recovery. Stop the affected operation on conflict, denied scope, incomplete required fixed input, or unknown external outcome. Reconcile unknown writes under the original intent and never bypass a denied read. For planning from another Task's limited read scope, follow the managed worker guide rather than assuming all business sources must be readable by the planner.

If `task.start` explicitly rejects an inactive stage, read the Task and stage before deciding the new scope. `task.update` can preserve the same Task with an explicit `stageId`: omission inherits, `null` detaches, an ID selects an active stage in the same project. Explicit stage assignment requires write and review permissions; an actual change requires todo and no inflight or unknown Run. Non-null assignment also needs consumer, evidence and stopCondition. Keep the complete content, acceptance, current expectedVersion and a clear reason; never reopen the old stage or create a duplicate Task just to bypass the rejection. Read back the new revision and its proposal before starting. A confirmed rejection stays rejected; a reviewed, changed scope is a new intent with a new operation ID, unlike recovery of an unknown result.

If a linked Document was republished while a Task was still todo, there may be no Impact to review. Read both fixed versions and decide the actual scope. To retain the old source, use `task.start.retentions` with its `documentId`, selected `revisionId`, the current `observedAdoptedRevisionId`, and a clear per-source `reason`; require review authority. The server seals the reviewer and time with the basis. This is valid only against that observed adopted revision; a later publication requires another review. Explicit `basis` selection requires explicit retentions for older sources. A generic update reason does not authorize retention, and no impact means neither automatic acceptance nor permission to fabricate one. A confirmed rejected start remains rejected; submit the reviewed new intent with a new operation ID and read back the sealed retention before dispatch.

Keep evidence categories separate: native Run completion, technical validation, immutable delivery, the declared observer's actual use, Task closure, Stage review, and later adoption are different observations. Record the artifact revision and checks; report failed or unobserved consumer use honestly. Close only when the explicit acceptance and use conditions are met, and choose the next task, research, pause, or stop with a reason. Leave fixed results and links for the person to inspect in the workbench. An artificial test or Agent observation does not establish human use.

An owner with review permission can explicitly close a managed cognition Task with `task.close.decisionId` instead of `deliveryId` when the signed preterminal `worker.decision` has a matching known-terminal Run and settled `worker.outcome` for the current fixed Task revision. Read the decision, Run, original source Inbox, and outcome before recording acceptance evidence. This closes only that bounded judgement, never the source business Task. A `waiting` decision additionally needs exactly one concrete handoff: `waitingInboxId` for the same source's formally disposed `next_action` Inbox plus a still discoverable source business Task, or `handoffDispatchId` for an earlier signed child business dispatch from this cognition worker, parent dispatch, loop, and source. The latter permits bootstrap sources and seals the exact child Task separately from the original source Task; the child remains unfinished. Bootstrap waiting without a formal child, or a source that is itself another cognition Task without its own child, cannot use the source-Task closure route. Tasks requiring consumer use still need the usual Delivery and use evidence. Do not infer a decision from a native final answer or create a Delivery for a no-action decision.

When a managed worker records an issue or report with `document.create`, supply `origin: { taskId: <this Task>, runId: <this Run> }`. The service derives the fixed Task revision and signs the writer; never guess or provide a revision ID. An issue is a problem report, not proof of consumer use or repair. Cognition reads an issue only through its exact source revision and verified original; choosing to publish that revision as a Task input is a separate signed review decision, not automatic acceptance of the issue or completion of a fix. Ordinary unscoped Documents and reports do not themselves wake cognition.

For a real direct-material/Wiki comparison, read [the evaluation guide](references/evaluation.md) before freezing inputs or reserving Runs. Freeze the definition first, keep every actual attempt and unknown cost, then record signed assessments and a limited next-step decision; do not reconstruct the experiment from a report afterward.

For an owner discussion, read [the discussion guide](references/discussions.md). Record decisions through `discussion.decision.record`, which appends the owned Document and discussion event together. If a separate Document edit has advanced its head, read both fixed originals before explicitly requesting controlled recovery; never silently move the discussion pointer or replay an already rejected decision as an unknown result.

For a bounded responsibility adjustment, first inspect the real source, current Role and Task, and the fixed diagnosis Document. During the accepted cognition parent's active Run, before its final worker Decision, `division.decide` records one durable method choice or a delegation-template-bound capacity/specialist/new-Role choice. For binding choices, read the current Loop's `orchestration/loops/LOOP_ID/delegation-choices` through your scoped CLI, then inspect the exact template, accepted existing Role and fixed diagnosis before submitting. The diagnosis original must already be readable in your existing cognition scope; a new binding cannot grant access to evidence that justified itself. Binding choices require an explicit template grant to the current Loop cognition Role for a worker, or the controller actor ID listed in the template. Neither a static Role grant nor Role text permits delegation. An already accepted trial Role can consume one new-Role allocation. New proposal and acceptance in the same decision additionally require `newRoleAllocation.creation.allowProposeAndAcceptTrial: true` and `maxTrialDays` (1–90), a complete `proposedRole` and `expectedFirstTaskOwner`. The first Task must still be todo at the observed version, Goal and Stage, with no unsettled Run or Dispatch. The proposal review must be future, within the trial bound and before template expiry. The researcher signs the choice; the configured controller accepts the trial under the template. Both Role operations, binding, policy and division event commit together or roll back. For a binding choice, cognition `waiting` must cite the prior `divisionDecisionId`; `no_action`, `stop` and `failed` leave the intent unused. A `method` choice records an approach without binding, policy revision, new Role, or authority. Update content and consumer before fixing its first Task version. A suitable existing todo Task may be requested once under its original Role through the ordinary same-source child path before the final decision; then sign `waiting` with `divisionDecisionId: null`. A method on the current in-progress cognition Task may instead yield a real report through `worker.submit`. Method alone does not justify `waiting` and its decision ID must never be cited as a binding. Read back the operation and, for a binding choice on your own parent, the binding and fixed Document original. `division.revoke` removes current new-start permission while the old policy and dispatch remain evidence.

After a completed parent Run and its final cited waiting Decision, the controller may consume the single intent within the original Loop budget. Consumption records a pending child before any Task owner transfer. The normal Task update must bridge the binding's observed version, and the child cannot claim or start until `division.confirmTransfer` verifies that journalled update. An `in_progress` first Task stops with `TASK_HANDOFF_REQUIRES_REOPEN`; do not silently reopen it or create a replacement. The receiving worker reads its own binding and fixed diagnosis original, verifies its hash, then signs `division.ackHandoff` with its exact Run and Task revision before `worker.submit` or `worker.decision`. Only that brokered worker may acknowledge or report the dynamic child; a controller cannot sign for it. The receipt is the worker's declaration of reading, while actual work, Delivery, independent use, and trial benefit require their own evidence. Expiry or revocation denies new Session/Run starts; exact prior owned work can still be reconciled and closed. Isolated fixture tests cover this path; they do not establish a live native trial or actual sustained Role need.

Keep tokens, raw sessions, external Wiki bodies, private originals, and local receipt files in a private local directory outside the repository or explicitly ignored by Git; never publish them. An `original --out` target must be a new directory under an existing parent. Use fixed links and permitted summaries when reporting what was read. Manual discussion handoff records are declarations, not proof that an existing Desktop chat received or adopted them.
