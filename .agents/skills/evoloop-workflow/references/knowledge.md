# Knowledge ingestion, query, and lint

Use `request schema knowledge.ingest` before submitting a fixed, adopted process Document revision. The body is exactly `{ "operationId": UUID, "documentId": UUID, "revisionId": UUID }`; the route project and authenticated actor supply the remaining scope. Native ingestion is material parsing and indexing. A `submitted` or `completed` reply records processing status only; `indexStatus: "unverified"` does not establish retrieval quality. A `failed` reply is a known processing failure. If the reply is lost or reports `unknown`, keep the saved receipt and original operation ID. Use `knowledge-ingestion OPERATION_UUID --project UUID` to inspect status, or `receipts reconcile RECEIPT_UUID` to match the original actor, document and revision. Never retry this external mutation through `receipts retry` or issue a new ID to escape an unknown result.

Use `knowledge-query QUESTION --project UUID --scope published|sources --limit 1..20` for bounded discovery. Hits carry the fixed ID, revision and content hash; the index remains unverified and can omit relevant material. Read the full fixed Wiki revision or Document original before making claims. Query output is not a newly adopted basis. Where a Task needs a new external reference, use `reference.task-decide` against its current Task revision and then read its sealed basis; do not silently replace a fixed source with the latest search hit.

For synthesis, compare the fixed original material with relevant existing published knowledge and its provenance. An Agent authors a source-backed candidate through `knowledge.propose`, reads it back, runs `candidate-lint CANDIDATE_UUID --project UUID`, and performs a separate semantic review of claims, contradictions, definitions, missing concepts and source support. Structural findings are prompts to inspect and repair; `semantic: "not_run"` means the service has not made that judgment. Then use the existing `knowledge.review` and `knowledge.publish` flow with the actual reviewer and permission. For an already published fixed revision, `knowledge-lint KNOWLEDGE_UUID --project UUID --revision UUID` checks structure; investigate findings and propose a reviewed revision where warranted. A query answer or lint finding alone does not publish a correction. The native OpenViking integration has no semantic-lint endpoint in its current selected version, so do not describe this Agent review as a native service result.

Do not create a second Bot compiler or writer for Wiki pages. Preserve one reviewed publication path, fixed source revisions and hashes, superseded decisions, and the distinction between processing, retrieval, candidate synthesis, review, publication, and actual consumer use.
