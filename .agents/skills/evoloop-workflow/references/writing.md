# 写清楚任务正文与验收

任务的完整正文统一由主 Document 保存；Task 保留独立验收标准。一次创建或修改保持两者一致，不能维护两份可冲突的正文。

## 写给下一位接手者

任务说明应让一位没参加前面讨论的人或 Agent，读完即可知道要做什么、从哪里开始、怎样交付。开头直说要改变什么以及原因，再按必要程度补背景、范围、约束、输入和输出。用常用词和具体例子；第一次出现的项目缩写要解释。未知写成待核实的问题，不把猜测当事实。

保留会改变执行或验收的信息；小任务可以只写几段，不强制填满大型模板，不用层层抽象名词代替具体对象和动作。

## 链接要带阅读理由

长规格、issue、讨论和报告可以链接引用。链接说明文档名称、要读的章节和与本任务的关系；任务说明仍保留必要摘要。执行依据引用固定修订，背景阅读与实际采用分清，不因正文里出现链接就自动采纳所有内容。使用服务实际返回的受控链接和固定标识，不编造链接语法。当前工作台使用 hash 深链：Task 为 `#/p/PROJECT_UUID/tasks/TASK_UUID`，固定过程文档为 `#/p/PROJECT_UUID/documents/DOCUMENT_UUID?revision=REVISION_UUID`；填写真实 UUID。报告在外部阅读时在 `#` 前加本次已知的工作台 origin（不要带令牌）。不要猜 `/app/p/...` 等路径；无法确认时保留明确 ID/修订与可执行的 CLI 读取命令。

## 图只用在需要它的地方

对象关系、流程分支或状态变化确实难以用短文说明时，直接附一张精简图，标清节点、方向和含义。选用当前读者能打开的格式并核呈现；Mermaid 要保留图源，图片要随修订保存必要资源。图可配一句解释，不代替正文中的关键限制和验收。简单任务无需配图。

## 验收写到可以判定

验收标准单独填写，采用“检查什么 + 用什么输入和操作 + 预期结果/证据”。避免“功能正常”“符合预期”“质量良好”等无法直接判定的句子。技术检查、目标消费者使用和长期效果分别写，只要求任务实际约定的验证；有失败条件时写出应出现的行为。

验收标准与实际结果要分开记录：标准描述怎样算完成，结果描述实际做过什么以及证据。默认在原任务内完成验证，不为每次验收创建新任务；只有明确的独立验证工作才另建 Task。不得以写出 acceptance 或执行者声称完成代替约定检查，真人使用仅在任务要求时等待。

## 写完后自读

不看历史聊天，下一位执行者能说出工作范围、必要依据、交付物和完成标准吗？重要来源能打开吗？图能看懂吗？有没有同一验收在多处写成不同版本？只修实际缺口，不为了自检增加没有用途的章节。

## 示例

标题：修复 CSV 导出的日报日期。

正文：运营在台湾时区的凌晨导出日报时，日期会变成前一天，导致汇总错位。修正导出层的日期计算；数据库仍保存 UTC，其他报表不在本轮范围。参考服务返回的《日期字段约定》固定修订及其“日报日期”一节，其中规定按 Asia/Taipei 计算业务日期。若现有约定与此不同，先报告矛盾并明确本轮采用的基线。

验收：用业务时间 2026-10-21 00:30（Asia/Taipei）的记录导出，日期应为 2026-10-21；分别检查跨月、跨年和空值。附样本与检查结果，说明未覆盖的情况。
