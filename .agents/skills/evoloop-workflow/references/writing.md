# 写任务：让下一位知道要解决什么

本页供需求 Session 或 Leader 写 Task、主 Document 和验收；从业务目标划本轮范围时先读[需求方法](../../evoloop-requirements/SKILL.md)。执行者接手读[普通接手](ordinary-handoff.md)，形成成果读[成果写作](results.md)。Task 的完整正文由主 Document 保存，Task 操作同时维护它；验收字段单独可判定。不要再写一份独立、可能冲突的任务规格。

## 从用户要作的决定写起

开头用几句话说明受影响的人与问题、本轮要改变的结果、当前 Task owner、交付给谁、第一步从哪里开始。随后只补会改变执行或验收的范围、约束和未知。责任以实际 Task owner 为准；Role 名称、候选 Session 或 ready 状态不能代替已接手的事实。尚待分派就写明等待谁安排。

给执行者一个能行动的目标和固定依据，让它选择调查或实现方法。若有必须回答的子问题，写出与结果的关系；探索线索标为按证据下钻，避免把历史审计的每个问题变成每项 Task 的清单。小任务几段足够，不要求统一大模板。第一次出现的项目缩写要解释，推测要标待核。

可用短骨架，不必逐项设标题：

> 因为【谁遇到什么问题】，本轮要让【可观察结果】成立。由【当前责任者】在【范围】内交【产物】给【验收者】。先读【必要输入】；用【真实样本】从【普通入口】做【操作】，应得到【结果】，留下【证据】。通过后由【下一责任者】做【下一步】；当前等待【谁】做【什么】。

## 来源和验收

先从原问题和假通过反例设计验收，再固定实现范围。**完成条件**说清用户可观察的结果和边界；**验收方案**写谁在什么候选或正式环境、用哪个真实样本和普通入口、做什么、预期及反例；**证据约定**写哪份固定图、操作记录或原始回执能证明哪项条件，以及怎样从 Task 打开。环境尚不存在时指定准备者与交验前须回填的实际 URL/CLI、版本、权限取得方式、样本准备与清理；不编造地址，也不把环境阻塞写成产品通过或失败。所有条件通过仍可能留下原问题时，补能区分的状态或操作；高成本但无区分力的重复检查可复用已有合格证据。

每个关联资料说明**用途、固定修订/hash、阅读程度**：执行依据须读，背景或反例按需读，未采纳提案不能写成决定。正文保留行动所需摘要，长原件用固定链接与目录承载；关联或下载成功不等于执行者已读懂。变更在途 Task 先核原 Run，再按重开、修订和开始的业务规则处理，不覆盖旧固定输入。

验收把样本、入口、操作、预期结果、指定的独立验收者、证据和通过后的下一责任连成一条可执行路径；已有旅程就引用并补本次差异，不再复制大模板。样本应能重现原问题，只有合成数据时说明覆盖限制。把执行者自检、当前候选的独立使用、按需发布后的正式入口复测及长期效果分开，实际结果留到交付时记录。研究验能否支持下一决定，文档验读者能否行动，工程验目标行为和约定的发布/复测；按[接力判断](coordination.md)给相称完成点。工程接力遵循[共享主分支与审阅](../../../../docs/development/standards.md#共享主分支与审阅)；失败默认回原 Task，只有确属独立工作才另建 Task。人工使用仅在任务约定时要求；代码、Run 终态或报告存在都不代替验收。

新 Task 的 `consumer` 与 `acceptanceMode` 仍决定真实签署身份。验收者按 DEC-042 与 DEC-046 选：验收交 Leader 指派的独立验收 Session（`acceptanceTarget: business_session`），`consumer` 写受管验收身份；难验收的——要对照使用者目标作产品判断、要跨系统追因、要跨发布走完整用户路径，或要先设计样本与反例才能验——写承担难验收的那个验收身份，并把样本、反例和判据在正文里设计好，不留给验收者临场猜。写这类 Task 时，`consumer` 写那个验收身份，并写 `acceptanceTarget: named_agent`（由声明的业务身份直接验收，不经验收接力）；`acceptanceMode` 可以省略（省略就是 `independent_agent`，直接验收要求的正是这个值），写别的方式（如 `human_required`）会以 `ACCEPTANCE_POLICY` 拒绝；这个值下 `acceptance.assign` 会被明确拒绝，Leader 不安排接力，`work acceptance` 显示“等待某身份验收”。已有的 target 可用 `task.update` 改成这个值，或写 `null` 清空（需 review 权限、Task 在 todo）。需求 Session 不做验收者（DEC-046）：它只照验收结论合并与发布，并事后抽查。使用者要亲用时写人（`human`）。`leader` 只在使用者为该 Task 明确要求 Leader 验收时使用，Leader 不是常规验收选项。`business_session` 仍要在候选和正式环境中排除作者 Session 与安排者 Leader。未声明时保留历史合同，由 Leader 在具体安排中选定可核的接收者，不从共享 actor 名称猜 Session。验收安排、候选使用和正式复验是不同阶段，不能只写“交 QA”。

写 Task 时连同验收者写明四项验收约定：**工作类型**（`kind`：`implementation` 实施、`research` 调研、`validation` 验证、`defect` 缺陷、`documentation` 文档、`operation` 运维与配置）、**验收前置**（无、刷新、发布、迁移、改配置并重启）、**阶段**（候选、正式或两者）和**样本**（谁准备、谁清理）。执行者的自检、CI 和 Run 终态写进交付证据，不代替验收；作者与安排者都不验自己的交付。其中**工作类型**选 `kind`：`defect` 缺陷（短写：复现步骤、期望与实际、出现的版本、严重度、回归测试、验收者要能复现原问题）、`documentation` 文档、`operation` 运维与配置（发布、迁移、改配置并重启），其余按原义用 `implementation`、`research`、`validation`；不再用标题前缀“缺陷：”代替类型，旧 Task 的类型不变，已有的缺陷类 Task 在没有在途 Run 或交付时用 `task.update` 改类。**验收前置**写在 `acceptancePrecondition`（`none`、`refresh`、`release`、`migration`、`config_restart`），`task.create` / `task.update` 都可写，修改规则与验收者相同（review 权限、Task 在 todo）；阶段与样本仍写在正文的验收方案里。验收方案还写明：验收者自己做至少一个反例，不只跑作者的测试；改页面的，写“从普通入口打开页面并读回”；功能带开关的，正式阶段写“开关已在正式环境打开并看到效果”，开关由谁打开也写上。前置不是 `none` 时，交付到了也要等有人用 `task.acceptancePrecondition.mark`（review 权限，写明证据，如“已发布到包含该提交的部署版本”）标记该交付的前置已满足：标记前投影显示“等待发布／迁移／重启”，不显示可验收；这时 Task 只是待验，不算失败，安排者也不催验收者，前置满足后再安排或通知验收。每个交付只标记一次，新交付要重新标记。`work task`、`work acceptance` 和 Task 详情会读回标记人、依据和时间（`acceptance.preconditionMark`），验收者据此核对前置是凭什么被认定满足的。

设计会影响验收时，在当前正文给一段可读对照：**现状（版本/状态）→ 选定目标（固定图或行为）→ 必须改变/允许不同 → 本轮覆盖与剩余责任**。把关键状态纳入同一组条件，例如空闲、忙碌、拒绝和结果未知；不把设计示意图的文字与像素尺寸误当必须相同的产品内容。每个条件约定能从 Task 打开的证据及其版本；条件已写清时沿原件引用，不为补格式打断在途 Run 或改写旧固定输入。

前端任务引用[当前工作旅程](../../../../docs/frontend/journeys/current-work.md)，以用户正常窗口截图确定主要阅读条件，记录内容视口的 CSS 宽高、浏览器缩放和截图像素宽高；无法核实的值标未知，再量测实际正常窗口。不要沿用默认 1280×720 代替用户窗口，短窗只作额外边界测试。截图的留存、更新和公开范围按[文档维护](../../../../docs/development/documentation.md)处理。

| 工作 | 本次问题 | 有区分力的成果与检查 |
| --- | --- | --- |
| 功能修复 | 谁在什么操作下遇到错误 | 补丁、原失败复现与相邻拒绝边界；仓库变更核 diff、PR、当前 head 检查，部署后原路径另验 |
| 文档审核 | 哪位读者无法理解或据此行动 | 权威正文差异或有据保留；新读者能用它完成解释或交接 |
| 探索调查 | 哪项未知妨碍哪项决定 | 支持或反对某选择的原件、反例、未验边界与最小下一步；允许结论为维持现状 |

## 链接和例子

使用服务返回的固定标识与已知工作台 origin，打开后核可见 ID、修订和 hash。当前工作台深链：Task `#/p/PROJECT_UUID/tasks/TASK_UUID`；过程 Document `#/p/PROJECT_UUID/documents/DOCUMENT_UUID?revision=REVISION_UUID`；知识页 `#/p/PROJECT_UUID/knowledge?knowledgeId=KNOWLEDGE_UUID&knowledgeRevision=REVISION_UUID`。外部阅读时在 `#` 前加本次已知 origin，不带令牌。无法核链接时给明确 ID、修订和可执行 CLI 读取命令，不猜路径。

例如，HTML 报告完整阅读的 Task 可直接写成：

> 读者从任务成果入口打开固定 HTML 报告时，主阅读区域过窄，难以连续读完。本轮由功能开发负责人修复报告阅读路径，交候选 PR 和逐步使用报告给任务指定的独立验收者。先读原失败报告的固定修订、[当前工作旅程](../../../../docs/frontend/journeys/current-work.md)及正常窗口截图；以原来读不完整的报告为样本，从任务成果入口打开，在与用户正常窗口可比较的条件下，从首段连续读到末段，核正文、图、末尾内容可达，再返回原任务。记录每步预期、实际结果、截图与视口条件。指定验收者在当前候选上亲用；失败回本 Task 修复并复测。候选通过且审阅、当前 CI 合格后，由有权发布者合并、发布，再交指定验收者从正式入口复测；全部约定条件满足后由有权者关闭。尚未发生的环节记为待验。

这个例子描述任务与判据，不宣称修复已经通过；对应的[使用报告例子](results.md#逐步使用报告示例)保留实际失败。

再如“Session 即时输入”任务的短正文可写：

> 正式页面当前只有“保存待处理”；选定目标图展示连续阅读、紧凑状态与底部多行输入。目标图是设计基准，示例文字和工具数量可变；回复、历史和输入在正常窗口及异常状态仍须可读、可操作。本轮从 Sessions 普通入口处理同一原 Thread 的空闲与忙碌输入：空闲只启动一次，忙时两条授权补充关联原 Turn；拒绝或结果未知时保留原意图并按原 ID 核对。验收者先用固定图和同条件截图核布局，再用输入 ID、接收及 Turn/Item 回执核实际处理；unknown 卡出现的窄屏原反例要复测。逐条件记录通过、失败或未测及证据版本。候选通过、必要审阅和发布后从正式入口复测；仍未覆盖的产品旅程留给原计划的下一责任。

这段是**任务写法示例**，不宣称即时输入已经发布或验收；实际任务需替换为当前固定基准、目标图、消费者和条件。[配对报告写法](results.md#逐项覆盖与关闭)说明如何交证据。

对这个例子，交验前由作者提供候选 head、实际可进入的地址/CLI、授权样本 Session、视口及原生能力清单；有权发布者另给正式部署版本，指定验收者分别核候选和正式入口。正常窗口、390px unknown 卡、忙时两次补充、空闲一次启动、重复/断连/撤权及长历史分别对应原 Task 的条件；图证明阅读和操作空间，inputId、操作回执及 Turn/Item 证明发送与关联。已知阻断阅读的候选先返工；缺原生能力时注明本阶段未就绪和准备责任。候选通过、独立使用、合并发布、正式同路径复测逐段留证，失败回原 Task。

非前端的调度任务也可如此写：指定验收者在作者隔离候选核忙碌、重复、unknown、身份拒绝等确定性合同；有权发布者准备正式服务及原 Leader 可用的 Role/Skill，验收者再观察原 Leader 面对真实开发、两项自然就绪的独立验收、待发布与返工时是否自主安排并正确回程。Root 代派或两个 `running` 标签不能证明自主调度或真实重叠；证据须关联触发、原 Thread/Turn、读取的 Skill 版本、安排、不同 Session 的实际执行与结果。候选环境实际 URL、CLI、schema、账号授权、样本和清理命令由作者交验前固定；正式环境由发布者给版本，网关未恢复时记阻塞。具体操作与证据沿该任务的固定验收方案执行，不把方案当已执行结果。

图只在关系、分支或状态难以用短文说明时使用；图源与资源随修订保存并核呈现。写完自读：新接手者能说出问题、责任、必要依据、交付、完成判据和第一步吗？只修发现的缺口。
