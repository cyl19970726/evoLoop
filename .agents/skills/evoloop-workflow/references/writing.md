# 写清楚任务正文与验收

任务的完整正文统一由主 Document 保存；Task 保留独立验收标准。一次创建或修改保持两者一致，不能维护两份可冲突的正文。

## 写给下一位接手者

任务说明应让一位没参加前面讨论的人或 Agent，读完即可知道要做什么、从哪里开始、怎样交付。开头直说要改变什么以及原因，再按必要程度补背景、范围、约束、输入和输出。用常用词和具体例子；第一次出现的项目缩写要解释。未知写成待核实的问题，不把猜测当事实。

保留会改变执行或验收的信息；小任务可以只写几段，不强制填满大型模板，不用层层抽象名词代替具体对象和动作。

## 让读者知道责任与下一步

开头几段应能回答五个问题：**什么问题、谁当前负责、要交付什么、怎样算完成、现在谁做哪一步**。责任用读者认识的职责名表达，并以实际 Task owner 为准；Role、承载 Session 和运行状态另用可追溯记录核对。尚待 Lead 分派就直说，不把候选责任人写成已接手，不把 ready 写成正在运行。

可按需要用这个短骨架，不要求逐项设标题：

> 因为【具体受影响的人和问题】，本轮要让【可观察的结果】成立。
> 当前由【责任者】处理【范围】，交付【产物】给【实际验收者】。
> 从【必要输入与第一步】开始；做到【判据】后交付。当前等待【人/条件】做【下一动作】。

范围、权限和会影响决定的限制放在动作附近。固定来源用“依据与回执”集中列名称、阅读理由、修订/hash 和链接；运行账目、失败原回执、完整日志留附件或过程报告。不删除约束以换取短文，也不把同一串 ID 在每段重复。执行者仍须实际读取本 Run 的封存输入。

进展记录用“已经做成什么；还缺什么；由谁做下一步”，与初始验收分开。修改正在执行的任务须先处理在途/未知 Run，再按重开、修订、开始的规则进行；写法实验另存候选，不覆盖旧 Task 或历史固定正文。

## 按工作类型选择交付和验证

| 工作 | 正文先说什么 | 有区分力的交付与验收 |
| --- | --- | --- |
| 功能修复 | 谁在什么操作下遇到什么错误，修复后应有什么行为 | 实际补丁、原失败复现及相邻拒绝边界；需要仓库变更时核集成 diff、PR、当前 head 检查与合并，部署后原路径复测另记 |
| 文档审核 | 哪位读者不能理解或据此行动，哪些权威正文需要改善 | 实际正文差异或有据保留；新读者用文档完成解释、设计或交接任务，记录误解与帮助 |
| 探索调查 | 当前哪项未知阻碍哪个决定，允许用什么办法核查 | 带依据的结论、支持/实测/未验边界和最小下一步；发现不支持也可完成调查，不以新实现或新增 Run 充数 |

## 链接要带阅读理由

长规格、issue、讨论和报告可以链接引用。链接说明文档名称、要读的章节和与本任务的关系；任务说明仍保留必要摘要。执行依据引用固定修订，背景阅读与实际采用分清，不因正文里出现链接就自动采纳所有内容。使用服务实际返回的受控链接和固定标识，不编造链接语法。当前工作台使用 hash 深链：Task 为 `#/p/PROJECT_UUID/tasks/TASK_UUID`，固定过程文档为 `#/p/PROJECT_UUID/documents/DOCUMENT_UUID?revision=REVISION_UUID`，固定知识页为 `#/p/PROJECT_UUID/knowledge?knowledgeId=KNOWLEDGE_UUID&knowledgeRevision=REVISION_UUID`；填写真实 UUID。知识页不能写成 `/knowledge/KNOWLEDGE_UUID?revision=...`。报告在外部阅读时在 `#` 前加本次已知的工作台 origin（不要带令牌）。打开后核对可见的知识或文档 ID、固定修订与哈希；旧正文仍可见不代表请求的固定版已读到。不要猜 `/app/p/...` 等路径；无法确认时保留明确 ID/修订与可执行的 CLI 读取命令。

## 图只用在需要它的地方

对象关系、流程分支或状态变化确实难以用短文说明时，直接附一张精简图，标清节点、方向和含义。选用当前读者能打开的格式并核呈现；Mermaid 要保留图源，图片要随修订保存必要资源。图可配一句解释，不代替正文中的关键限制和验收。简单任务无需配图。

## 验收写到可以判定

验收标准单独填写，采用“检查什么 + 用什么输入和操作 + 预期结果/证据”。避免“功能正常”“符合预期”“质量良好”等无法直接判定的句子。技术检查、目标消费者使用和长期效果分别写，只要求任务实际约定的验证；有失败条件时写出应出现的行为。

验收标准与实际结果要分开记录：标准描述怎样算完成，结果描述实际做过什么以及证据。默认在原任务内完成验证，不为每次验收创建新任务；只有明确的独立验证工作才另建 Task。不得以写出 acceptance 或执行者声称完成代替约定检查，真人使用仅在任务要求时等待。

工程回执先写实际改变及未满足的判据，再集中给 Task/Run/Session 与固定输入版本、commit/PR/merge commit、检查与失败、固定产物和真实执行者；部署状态、消费者使用入口及下一责任另写清楚。未发生的步骤标待办或未验，不能用占位符写成通过。原 Task 的失败观察和旧交付保留，修复后由实际消费者按约定复测当前 Delivery；单独发现的新问题才考虑另建有来源任务。完整动作与身份边界见[CLI 工程交接](../../../../docs/development/agent-cli.md#仓库工程任务与动作交接)。

## 写完后自读

不看历史聊天，下一位执行者能说出问题、当前责任、工作范围、必要依据、交付物、完成标准和下一步吗？重要来源能打开吗？图能看懂吗？有没有同一验收在多处写成不同版本？只修实际缺口，不为了自检增加没有用途的章节。

## 示例

标题：修复 CSV 导出的日报日期。

正文：运营在台湾时区的凌晨导出日报时，日期会变成前一天，导致汇总错位。修正导出层的日期计算；数据库仍保存 UTC，其他报表不在本轮范围。参考服务返回的《日期字段约定》固定修订及其“日报日期”一节，其中规定按 Asia/Taipei 计算业务日期。若现有约定与此不同，先报告矛盾并明确本轮采用的基线。

验收：用业务时间 2026-10-21 00:30（Asia/Taipei）的记录导出，日期应为 2026-10-21；分别检查跨月、跨年和空值。附样本与检查结果，说明未覆盖的情况。
