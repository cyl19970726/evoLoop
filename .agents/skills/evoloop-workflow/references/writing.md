# 写任务：让下一位知道要解决什么

本页供 Lead 写 Task、主 Document 和验收。执行者接手读[普通接手](ordinary-handoff.md)，形成成果读[成果写作](results.md)。Task 的完整正文由主 Document 保存，Task 操作同时维护它；验收字段单独可判定。不要再写一份独立、可能冲突的任务规格。

## 从用户要作的决定写起

开头用几句话说明受影响的人与问题、本轮要改变的结果、当前 Task owner、交付给谁、第一步从哪里开始。随后只补会改变执行或验收的范围、约束和未知。责任以实际 Task owner 为准；Role 名称、候选 Session 或 ready 状态不能代替已接手的事实。尚待分派就写明等待谁安排。

给执行者一个能行动的目标和固定依据，让它选择调查或实现方法。若有必须回答的子问题，写出与结果的关系；探索线索标为按证据下钻，避免把历史审计的每个问题变成每项 Task 的清单。小任务几段足够，不要求统一大模板。第一次出现的项目缩写要解释，推测要标待核。

可用短骨架，不必逐项设标题：

> 因为【谁遇到什么问题】，本轮要让【可观察结果】成立。由【当前责任者】在【范围】内交【产物】给【验收者】。先读【必要输入及第一步】；达到【判据】后交付。当前等待【谁】做【什么】。

## 来源和验收

每个关联资料说明**用途、固定修订/hash、阅读程度**：执行依据须读，背景或反例按需读，未采纳提案不能写成决定。正文保留行动所需摘要，长原件用固定链接与目录承载；关联或下载成功不等于执行者已读懂。变更在途 Task 先核原 Run，再按重开、修订和开始的业务规则处理，不覆盖旧固定输入。

验收写“用什么输入或操作检查什么、预期出现什么、由谁使用”，把技术检查、消费者使用和长期效果分开。实际结果留到交付时记录。默认在原 Task 验证，只有确属独立工作才另建 Task。人工使用仅在任务约定时要求；Run 终态、报告存在和验收各有自己的证据。

| 工作 | 本次问题 | 有区分力的成果与检查 |
| --- | --- | --- |
| 功能修复 | 谁在什么操作下遇到错误 | 补丁、原失败复现与相邻拒绝边界；仓库变更核 diff、PR、当前 head 检查，部署后原路径另验 |
| 文档审核 | 哪位读者无法理解或据此行动 | 权威正文差异或有据保留；新读者能用它完成解释或交接 |
| 探索调查 | 哪项未知妨碍哪项决定 | 支持或反对某选择的原件、反例、未验边界与最小下一步；允许结论为维持现状 |

## 链接和例子

使用服务返回的固定标识与已知工作台 origin，打开后核可见 ID、修订和 hash。当前工作台深链：Task `#/p/PROJECT_UUID/tasks/TASK_UUID`；过程 Document `#/p/PROJECT_UUID/documents/DOCUMENT_UUID?revision=REVISION_UUID`；知识页 `#/p/PROJECT_UUID/knowledge?knowledgeId=KNOWLEDGE_UUID&knowledgeRevision=REVISION_UUID`。外部阅读时在 `#` 前加本次已知 origin，不带令牌。无法核链接时给明确 ID、修订和可执行 CLI 读取命令，不猜路径。

一项实际研究任务要判断 Task 派发、普通消息与 Session 唤醒是否需要新机制。原 Task 已说清主题，却把六组子问题和大量操作说明混排。可改写为：请说明现有机制已做什么、缺什么、是否需要新增，并用空闲接任务、忙时收消息、进程退出三个场景检验结论。这个写法只示范如何突出决定；不能替换原 Task 的完整授权、验收和固定来源。

另一项实际文档工作曾用设计 HTML 与图片写使用说明。可这样交接：产品文档负责人为第一次打开工作台的人解释三个页面区域、真实状态和任务往返；先核材料目录中的固定原件，遇图与实际能力冲突时标为未验。交可打开的固定 Document 给 Lead；验收看 Lead 能否据它解释使用路径，并追到关键原件与限制。实际读取和 Lead 使用发生过，但该例不证明新写法提升了效率；原任务验收仍以其固定版为准。

图只在关系、分支或状态难以用短文说明时使用；图源与资源随修订保存并核呈现。写完自读：新接手者能说出问题、责任、必要依据、交付、完成判据和第一步吗？只修发现的缺口。
