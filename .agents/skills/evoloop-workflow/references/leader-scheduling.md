# Leader: stage and acceptance scheduling

Use the current project's CLI identity and fixed Task revisions. Read `work acceptance --project PROJECT` for the paged Task stage projection and persisted Session obligations; follow its work cursor until the page is complete. `persistedWorkIdle` means only that the listed database obligations are clear. `missingCapabilities` names the concrete execution, CLI, identity or message-grant gap; `readyForAcceptance` requires both an idle Session and no gap. Check native control, Role binding, material CLI identity, message grant, conflicting files and the actual recipient before assigning work. A missing grant is a configuration decision for the responsible reviewer, not something a model can self-grant.

## Dispatch before doing

The Leader's Turn is for reading, judging and arranging, not for producing the business artifact. Treat an execution request from the user or a demand Session as work to shape and assign, not as permission to perform that work in the current Turn. First create or select a bounded Task with its goal, scope, acceptance and consumer; then assign a suitable business Session and start its authorized Run or queue. Report the Task, responsible Session, whether execution actually started, and the next check. Do not write code, revise documents, perform bulk data operations or write investigation reports in the Leader's Turn. If no suitable receiver exists, state the capacity or Role gap and propose another same-Role instance or a new Role; do not fill the gap by doing the work yourself.

Only a new Role, private configuration, merge, release or budget overrun needs the user's confirmation before action. Other dispatch, ordering and acceptance arrangements remain the Leader's decisions. Confirmation is an authorization step, not an instruction for the Leader to execute the work.

- **Archive request.** The user asks the Leader to archive three named Documents. The Leader creates a bounded Task for the document and architecture Role, assigns it to that Role's Session, and replies with the Task ID, responsible Session and whether the Run started. The Leader does not call `document.archive` in its own Turn.
- **Investigation request.** A demand Session asks for a small report on backlog causes. The Leader turns the question into a Task with a fixed scope and acceptance, assigns it to the appropriate business Role, and reports the arrangement. Producing the report in the Leader's reply is not a substitute for the assigned delivery.
- **Counterexample.** The user asks the Leader to archive three Documents, and the Leader replies "Done" after calling `document.archive` in its own Turn. This is wrong even when the writes succeed: the work has no bounded Task, assigned responsibility or independent acceptance, and it hides the execution behind an arrangement Turn. The correct response is to create and assign the Task before any business write.

For each ready Task, state one action, prerequisite, responsible person or Session, and whether a Run or message has actually started. Use `work.plan.set`, `work.dependencies.set` and `work.review.set` for priorities, dependencies and decisions. Save a Task assignment and start its authorized Run through the existing queue or reserve path. Continue other independent work while a release or an occupied Session waits.

For current Delivery acceptance, inspect `work task TASK`, the fixed Delivery and Task policy. The Task must declare its consumer and mode. You are not a routine acceptor (DEC-042): an explicit Leader target is required for Leader acceptance, and a Task carries one only when the user asked for it. Routine acceptance goes to an independent business Session you assign. When a Task's consumer is the requirements Session's business identity, that Session accepts directly from the normal entrypoint: do not arrange a relay for it, reassign its consumer or accept it yourself; it is not woken automatically, so list such Tasks with a ready Delivery in your report to the user. When the Task's acceptance precondition (release, migration, configuration restart) is not met yet, record the Task as waiting for that precondition instead of arranging acceptance, and arrange the formal re-check after the release is announced. The executor's self-check, CI and Run terminal state are evidence, not acceptance. Historical unspecified agent targets need a concrete business Session choice. Use `request acceptance.assign --project PROJECT --id TASK --file PRIVATE_JSON` with one immutable operation ID, fixed Delivery, scope and actual recipient. The declared `senderActorId` must be the arranging reviewer's current actor. Then read `work acceptance TASK`. Agent arrangements use the existing Session message queue and retain their original message and operation IDs on unknown outcomes. The recipient records `session.message.receipt` after reading, then its own observation; confirm processing, native Turn, read receipt and observation separately.

Put anything the recipient should know beyond the template — what to try, what to skip, where the fixed entrypoint is — into `scopeDescription` (and `entrypoint`), which the relay's own message carries. Do not post a separate message with the `messageId` or `messageOperationId` the arrangement reserved: those IDs belong to the relay. If you did (for example a longer handoff), the relay accepts the message you saved as long as its sender is the declared sender, it goes to the arranged Session and its context is the arranged Task revision; it is checked as written and never rewritten, so include the arrangement ID in your text. A message that differs in sender, Session or Task revision still blocks the arrangement as `MESSAGE_BINDING_CHANGED`. After a service build with this rule is running, the relay tick re-reads arrangements blocked only as `MESSAGE_BINDING_CHANGED` and links the ones whose saved message now qualifies; the recipient then links the observation already recorded with `work acceptance observe`, and the Task closes without repeating the acceptance. Never rewrite an existing observation or sign `used` for someone else to get there.

Human arrangements appear in `work acceptance mine`; only the named human credential can record the read. Use `work acceptance read RELAY --project PROJECT --task TASK --file PRIVATE_JSON` and then link the person's existing observation with `work acceptance observe RELAY --project PROJECT --task TASK --file PRIVATE_JSON`. Agent credentials cannot sign either action. A blocked arrangement emits one durable Leader notice; a later result still arrives through the existing observation notice. A linked observation still needs the Task's other closure conditions.

For a second QA instance, prepare or reuse one authorized same Role Session. Verify its Thread, current execution profile, business CLI actor and exact message grant before assigning it. A Role name or an idle badge does not supply these. If preparation is incomplete, record the missing capability and its owner, and keep other independent work moving.

Retire only a temporary instance whose business responsibility is completed or explicitly handed off. Read `work retirement SESSION`; verify no active or unknown Run, message, claim, assignment or unobserved acceptance remains and that `nextAction` is the close step. Record the exact decision and close operation with `request session.retirement.approve --project PROJECT --id SESSION --file PRIVATE_JSON`; then submit `runtime.session.close` using the same close operation ID. Read the original operation, `closed`, `closeVerifiedAt` and `nativeArchiveVerified`. A `closing` state or an unverified archive remains pending reconciliation. Preserve the Role, Task, Delivery, observations and dependent resources.

When QA reports failure, keep the old Delivery and observation, update the original Task through its normal rework contract, and arrange acceptance of the new Delivery separately. Report the exact handoff and next owner to the user; candidate code, CI, merge, formal release, independent use and Task closure remain separate facts.

A Task whose `acceptanceTarget` is `named_agent` is accepted directly by its declared consumer identity: do not arrange a relay (`acceptance.assign` is refused with `ACCEPTANCE_NAMED_AGENT`); `work task` and `work acceptance` show it as waiting for that identity. When the Task declares an `acceptancePrecondition` other than `none`, the delivery is not ready to accept until a reviewer marks it with `task.acceptancePrecondition.mark`; the projection shows `acceptanceConvention.readiness` as `waiting_precondition` and the next action as waiting for the release, migration or restart. A declared consumer that is an Agent finds its own pending deliveries with `work acceptance mine` (`direct` list, by the same rule and index as the workbench's 等我使用的交付: the current delivery passed its technical check, the identity has not recorded `used` or `failed`, plus whether its precondition is met).
