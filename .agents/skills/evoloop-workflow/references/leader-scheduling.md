# Leader: stage and acceptance scheduling

Use the current project's CLI identity and fixed Task revisions. Read `work acceptance --project PROJECT` for the paged Task stage projection and persisted Session obligations; follow its work cursor until the page is complete. `persistedWorkIdle` means only that the listed database obligations are clear. Check native control, Role binding, material CLI identity, message grant, conflicting files and the actual recipient before assigning work.

For each ready Task, state one action, prerequisite, responsible person or Session, and whether a Run or message has actually started. Use `work.plan.set`, `work.dependencies.set` and `work.review.set` for priorities, dependencies and decisions. Save a Task assignment and start its authorized Run through the existing queue or reserve path. Continue other independent work while a release or an occupied Session waits.

For current Delivery acceptance, inspect `work task TASK`, the fixed Delivery and Task policy. The Task must declare its consumer and mode. An explicit Leader target is required for Leader acceptance; historical unspecified agent targets need a concrete business Session choice. Use `request acceptance.assign --project PROJECT --id TASK --file PRIVATE_JSON` with one immutable operation ID, fixed Delivery, scope and actual recipient. Then read `work acceptance TASK`. Agent arrangements use the existing Session message queue and retain their original message and operation IDs on unknown outcomes. Confirm processing, native Turn, recipient read receipt and the recipient's own observation separately. Human arrangements appear in `work acceptance mine`; only the named human credential can record the read and use. A linked observation still needs the Task's other closure conditions.

For a second QA instance, prepare or reuse one authorized same Role Session. Verify its Thread, current execution profile, business CLI actor and exact message grant before assigning it. A Role name or an idle badge does not supply these. If preparation is incomplete, record the missing capability and its owner, and keep other independent work moving.

Retire only a temporary instance whose business responsibility is completed or explicitly handed off. Read `work retirement SESSION`; verify no active or unknown Run, message, claim, assignment or unobserved acceptance remains. Record the exact decision and close operation with `request session.retirement.approve --project PROJECT --id SESSION --file PRIVATE_JSON`; then submit `runtime.session.close` using the same close operation ID. Read the original operation, `closed`, `closeVerifiedAt` and native archive result. A `closing` state or an unknown archive result remains pending reconciliation. Preserve the Role, Task, Delivery, observations and dependent resources.

When QA reports failure, keep the old Delivery and observation, update the original Task through its normal rework contract, and arrange acceptance of the new Delivery separately. Report the exact handoff and next owner to the user; candidate code, CI, merge, formal release, independent use and Task closure remain separate facts.
