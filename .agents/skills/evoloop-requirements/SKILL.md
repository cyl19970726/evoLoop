# 从需求到可接手的工作

从用户要完成的事出发。先读当前对话、相关 Task 的固定正文与结果，再按问题选择[产品定义](../../../docs/product/definition.md)和[功能场景](../../../docs/product/functional-scenarios.md)中的必要部分。用户原话、已采纳决定、执行观察和自己的推断要分开；已有 Task 可承接时沿原 Task 修订，不另造同题工作。

## 定义本轮

用几句话连起五件事：**业务目标 → 整体关系 → 本轮范围 → 依据与未知 → 完成后谁接什么**。整体关系复杂或跨多个 Task 时，给一张能看出用户、对象、步骤和本轮切片的总图；小任务用短文即可。总图是共享理解，不代替每项 Task 的固定正文。

判断问题、关键做法和验收办法各自是否足够清楚。问题或评价办法未明，先取得真实场景与判据；做法未明，交调查、比较或有界试做；三者足够时再交实施。研究的成果可以是有据维持现状或停止；方案已写出却无法判断是否解决用户问题时，先补样本和使用办法。不要仅凭 Task `kind` 套同一完成流程。

**创建 Task 前先设计怎样验收。** 从用户目标、当前差距和风险推导可观察的完成条件，再选能区分真解决与假通过的环境、样本、入口、操作、预期和反例；最后确定每项需交什么可打开的固定证据，以及谁准备环境、谁自检、谁独立验收。条件是结果，方案是实际验证步骤，证据是步骤发生且结果匹配的记录。若 Root 代派也会让“并行 running”成立，就不能用这项指标验 Leader 自主调度；若截图不能证明消息进了原 Turn，就要补输入与原生回执。关键环境或判据未知时，写清决定者与补齐条件，先做有界调查，不留给 QA 临时猜测。

验收者按 DEC-042 与 DEC-046 选：常规的交 Leader 指派的受管验收 Session；难验收的——要对照使用者目标作产品判断、跨系统追因、跨发布走完整用户路径，或要先设计样本与反例——写承担难验收的那个验收身份（`acceptanceTarget: named_agent`），样本、反例和判据在正文里先设计好；Leader 只在使用者明确要求时验收。本 Session 不做验收者（DEC-046）：只照验收结论签字、合并与发布，并事后抽查验收质量。同时写明工作类型（`kind`，缺陷写 `defect`）、验收前置（`acceptancePrecondition`）、阶段与样本（见[任务写法](../evoloop-workflow/references/writing.md)）。本 Session 自己做的发布、配置或文档修改不自签，交独立验收 Session 或第一位实际使用者。本 Session 不会被自动唤醒：DEC-046 之前以本身份为消费者、一时改不了的在途 Task，由 Leader 另建“合并前验收”或“正式验证”Task 交验收 Session，本 Session 主动查这些报告并照结论签字。

例如“业务报告入库后工作停住”，先画出业务 Session、任务记录与 Leader 的回程，标明本轮只补结果通知；通知接口未定是实施者需核的未知。工程 Task 验通知和接续，另用真实任务验整条协作；一份历史任务写法研究只需证明建议能支持下一决定，不因为同在计划中就要求它部署服务。

按[任务写法](../evoloop-workflow/references/writing.md)写清受影响者与问题、预期改变、本轮边界、必要固定材料、可自主选择的行动空间、产物、真实样本与普通入口、验收者及下一责任。关键未知若会改变方向，指出谁决定、需要什么证据；不影响当下工作的疑问留作待核。用反向检查：即使所列条件都通过，原问题是否仍可能存在？

涉及用户可见结果时，先固定**当前基准、选定目标和本轮必须改变的部分**；指出哪些外观或实现差异允许、哪些状态和操作不能漏。已有设计图就给可打开的修订与用途；视觉效果会影响成败却没有目标图时，先安排有界设计。逐条件对照完整用户路径：每项写明样本与状态、动作、预期、验收者和适合的固定证据，标出本 Task 只解决哪段、剩余问题及下一责任。截图能证明呈现，发送、接收或原生 Turn 关联还须相应回执。研究、运维和后端工作按其决定与行为选证据，不统一要求截图或部署。

## 登记并交接

项目 Task 的主 Document 是本轮正文的权威位置，附加资料用固定修订/hash 标明用途。先核本人 CLI 身份、当前 `help` 与命令 schema；在已有授权内用 Task 命令创建或维护 Task，并回读正文、验收、owner 和版本。要求实际使用时，消费者须是将亲自签结果的真实 actor；身份或分派未定时交 Leader 明确，不把 Role 名称、候选 Session 或通知计划写成实际接手。具体字段、在途改版与未知操作恢复沿[业务 CLI 指南](../../../docs/development/agent-cli.md)和[协作 Skill](../evoloop-workflow/SKILL.md)，此处不复制协议。

给 Leader 可读的任务组合、建议顺序与依赖、每项交付目的、独立验收责任和未决决定。Leader 决定责任、资源冲突与排序；业务 Session 在正式派单内自主执行。创建成功、Leader 已收到、受管 Session 已接手是不同证据。先从现有工作变化入口对账；业务结果主动通知 Leader 的新接口只有在实际部署并回读后才写成可用。

本期引擎只编排 Leader 与业务 Session。需求与 Evo 系统 Session 独立通过项目 CLI 工作，不因此获得自动唤醒或排程；插件和 Stop Hook 不是交付前提。目标改变时指出受影响的原 Task、Run、交付与下一决定，按现有修订和返工规则处理，不覆盖旧依据。方法本身反复失效时，将真实案例交 Evo 评估最小改法及后续使用效果。
