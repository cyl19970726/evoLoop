# 提交可处理的 evoLoop issue

目标仓库默认是 `cyl19970726/evoLoop`。这里只处理 evoLoop 本身的问题；私有项目自己的问题留在该项目。发现 evoLoop 问题时，先判断能否在不泄露私有数据的前提下公开描述；不能时交该项目负责人决定私下联系方式。

公开 issue 是给维护者复现和分诊的工作单，不是聊天记录。只写处理所需的最少事实。

## 硬边界

- 不使用使用者本人的账号代替智能体。智能体以自己的身份运行 `gh`，并保留实际提交者身份。
- 不把令牌、Cookie、私有路径、主机名、内部 URL、原始会话记录、未公开材料或别人的数据写进正文、标题、截图或命令输出。
- 不把安全漏洞、可利用细节或仍含敏感数据的复现公开提交。改用 GitHub 私密安全公告：`https://github.com/cyl19970726/evoLoop/security/advisories/new`。
- 本技能不授权代班检查新 issue、以使用者账号公开回复或承诺修复时间。提交后在任务允许时读回 URL 与字段；其他动作另取授权。
- 只有本次任务明确要求提交 issue 时才执行创建命令。自测、验收和普通排查只生成正文与命令，不真的创建 issue。

## 1. 选择类型

| 类型 | 用在什么时候 | 标题前缀 |
| --- | --- | --- |
| 缺陷 | 已有能力的结果错误、失败、回退或与已说明的行为不符 | `[缺陷]` |
| 改进 | 当前能力可用，但使用方式、可理解性或工作成本仍可改善 | `[改进]` |
| 使用咨询 | 文档或行为不清楚，需要维护者解释怎样使用；不是要求新增能力或报告错误 | `[咨询]` |

类型不确定时按读者下一步判断：要维护者修错误选缺陷，要改变能力选改进，只需澄清现有用法选咨询。不要混在一个 issue 里。不同问题分开提交。

## 2. 八项必填内容

每个 issue 都按同一顺序写齐下列八项。Issue Forms 会提供同样字段；用 CLI 时照下面的骨架写。

### 1. 类型

只写 `缺陷`、`改进` 或 `使用咨询` 之一，并让它与标题前缀一致。

### 2. 一句话

写“谁在做什么时遇到了什么结果”，只写现象，不写猜测的原因，也不要写成修复方案。

### 3. 环境

至少写全：

- evoLoop 版本：`/api/version` 返回的 commit；不能读取时写“未知”并说明原因。
- 实例：共享正式实例，或自建实例的名称/用途；不要在公开 issue 写私有域名、主机名或绝对路径。
- 入口：页面、具体 CLI 命令或 API 路径；命令中的令牌、私有 ID 与路径要删掉。
- 运行时与模型：如 Codex 或 Claude，以及实际使用的模型。
- 提交者：真人，或哪个智能体身份。
- 来源项目：发现问题时所在的项目名称；不放私有项目 URL。

### 4. 复现步骤、预期与实际

按从普通入口开始的顺序写最短复现步骤。分别写“预期”和“实际”，不要只贴一段日志。改进建议写当前做法与希望改善的结果；咨询写已经读过什么、仍在哪一步不清楚。

### 5. 证据

写错误码与报错原文（已去敏）、操作 ID、截图或可公开的链接。Task 或 Session ID 只有确有必要时保留，并注明来自哪个实例；删掉正文、参与者与他人数据。

### 6. 影响

写是否挡住工作、有无绕开办法、每次还是偶发。缺陷再写影响范围或严重度；改进写重复发生的工作成本；咨询写不澄清会妨碍哪个决定。

### 7. 已排查

写搜过哪些重复关键词及相关 issue、在哪个最新版本上试过、能否复现，以及做过的相邻检查。没有搜到的也写清，不伪造结论。

### 8. 隐私自检

逐项确认并保留在正文：

- 已删除令牌、Cookie 和密钥。
- 已删除私有路径、主机名、内部 URL。
- 已删除原始会话记录、完整日志和附件中的他人数据。
- 截图和报错已裁掉或打码敏感内容。
- 内容可以出现在公开仓库。

## 3. 先搜重复

用标题和正文中的稳定名词、错误码、页面或命令搜索开放和已关闭的 issue：

```sh
REPO="${EVOLOOP_ISSUE_REPO:-cyl19970726/evoLoop}"
QUERY="<错误码或稳定关键词>"
gh issue list --repo "$REPO" --state all --search "$QUERY in:title,body" --limit 30
```

找到同一问题时，在当前允许的渠道补充新的版本、复现和影响，不重复开单。相近但可独立处理的问题可以分开，并在“已排查”写相关编号。

## 4. 用 CLI 提交

智能体提交的 issue 固定带两个标签：

- `由智能体提交`
- `来源项目`

上游维护者一次性建立标签：

```sh
gh label create "由智能体提交" --repo "$REPO" --color "5319E7" \
  --description "由智能体身份提交的 issue"
gh label create "来源项目" --repo "$REPO" --color "0E8A16" \
  --description "来源项目名称写在 issue 的环境字段"
```

提交前确认标签存在。缺标签时停下并告诉维护者，不省略标签后继续：

```sh
for label in "由智能体提交" "来源项目"; do
  gh label list --repo "$REPO" --limit 100 --json name \
    --jq '.[].name' | grep -Fxq "$label" ||
    { echo "缺少标签：$label" >&2; exit 2; }
done
```

把第八项自检后的正文写到临时文件，再生成并检查命令：

```sh
BODY="${TMPDIR:-/tmp}/evoloop-issue.md"
TYPE="缺陷"
SUMMARY="登录后打开版本页时页面持续显示加载中"

sed -n '1,240p' "$BODY"
printf 'gh issue create --repo %q --title %q --body-file %q --label %q --label %q\n' \
  "$REPO" "[$TYPE] $SUMMARY" "$BODY" "由智能体提交" "来源项目"
```

只有本次任务明确允许公开提交时，才执行等价命令：

```sh
gh issue create \
  --repo "$REPO" \
  --title "[$TYPE] $SUMMARY" \
  --body-file "$BODY" \
  --label "由智能体提交" \
  --label "来源项目"
```

命令成功后在当前任务或交付记录保留 issue URL；需要确认内容时用 `gh issue view <URL> --json title,body,labels,url` 读回。命令失败时保留原错误与 body 文件，不删证据，也不在未核对是否已创建前换标题重试。确认完成或错误已转成去敏证据后，按任务的数据保留规则删除临时 body 文件；不要提交到仓库。

## 完成检查

- 标题只有一个问题，类型前缀与第一项一致。
- 八项均有内容；不适用时写明为什么不适用，不只留空。
- 复现能从普通入口执行，预期与实际分开。
- 重复搜索已在第七项留下关键词和结果。
- 智能体提交同时带“由智能体提交”和“来源项目”。
- 隐私五项全部核过，公开内容不含私有材料。
- 自测只到正文、命令或表单预览；没有在未获提交授权时创建 issue。
