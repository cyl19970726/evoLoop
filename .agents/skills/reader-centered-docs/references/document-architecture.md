# 从解释关系推导内容架构

## 先问每篇帮读者理解什么

文档集合可以沿读者的任务分工，不需要和代码包一一对应。不同解释视角可以共享模型和例子，但应有各自完整的主线。

| 解释视角 | 读者进入时的问题 | 应形成的理解 | 通常需要的内容 |
| --- | --- | --- | --- |
| 产品 | 为什么需要它，能帮我做什么 | 价值、能力、使用方式、限制 | 熟悉困难、目标、完整场景、能力与体验、价值判断 |
| 架构 | 为什么这样组织，机制如何成立 | 内容与责任如何协作、变化怎样受控 | 内容模型、操作、责任边界、调用或数据路径、关键取舍 |
| 核心模型 | 两篇里的术语究竟指什么 | 能区分核心对象、关系、状态与规则 | 定义、相近概念对照、准确例子、生命周期与约束 |
| 接入 | 我需要提供什么，能得到什么 | 准备、合同、责任和端到端验证 | 最小接入、完整示例、错误与恢复、能力范围 |
| 运行 | 怎么启动、修改、验证和排错 | 可以完成任务并解释结果 | 前提、步骤、预期结果、限制、恢复 |
| 状态 | 现在能依靠什么 | 分清目标、实现、部署、实际验证 | 有版本的事实、证据范围、已知限制与下一步 |

这些是内容职责，不是一套必须生成的文件。短文可以在一页中承担多个职责。只有在独立阅读、更新频率或内容规模需要时才拆篇。

## 产品篇内部如何展开

以“读者理解逐步发生了什么”检查章序，允许依据已有熟悉度调整：

1. **从已有困难建立目标。** 描述具体情形和损失，解释希望产生的变化，让读者知道为什么需要继续读。
2. **建立核心对象和概念。** 给可以指认的例子，以及容易混淆的概念之间的差异。解释到理解主场景所需程度，更多细节再进入模型篇。
3. **说明能力和变化机制。** 解释入口、动作、状态变化、结束条件与理由。使用目标明确的图；若产品没有成长机制，不强加“学习闭环”。
4. **走完一个连续场景。** 跟踪具体输入、条件、取舍和结果；必要时展开第二轮及反例。区分教学假设与真实案例。
5. **从场景推导实际使用。** 将产品体验、人工参与和 Agent／系统职责放回任务。只写已确认操作；设计体验标明其状态。
6. **解释怎样判断价值。** 说明成功、失败、待观察与无法判断各意味着什么，以及如何查当前能力。

可以先给极短例子建立概念，再在机制之后完整回看。允许这种有认知目的的回访，避免每章重讲总目标。按章节列出“读前→读后→最有效的解释/例子→下一问”即可，不必造新数据库。

## 架构篇如何承接产品篇

沿用主场景中的对象，逐步揭示承担职责的结构：

- **内容与状态：** 长期保存什么，哪些是原件、解释、投影或临时结果；谁能改变它们。
- **行为：** 什么触发动作，读取哪些输入，怎样改变状态，何时结束，失败怎样恢复。
- **责任与连接：** 谁发起、谁执行、谁判断、谁保存；接口、信任与持久边界分别在哪。
- **外部接入：** 接入者继续拥有什么，核心提供什么；怎样在另一业务证明合同成立。
- **设计与实现距离：** 按准确版本说明哪些已实现，哪些仍是目标、局部实现或待验收。

内容模型图、职责图与时序图回答不同问题，按读者问题决定是否都需要。图中出现 API、Worker、队列或数据库时，说明其真实作用及与业务对象的区别；不要让运行设施看起来像认识必须晋级的层级。

## 当产品从业务中独立

沿同一个场景核对：哪些概念跨业务成立，哪些是业务的标签、事实和流程；原件和凭据由谁持有；谁执行采集、分析或行动；核心能力怎样读取与返回；设计通用性、参考适配和真实业务验收分别有什么证据。

核心文档可以包含业务案例，案例存在不等于业务拥有核心规则。业务指南可摘要核心能力并引用权威正文，不应维护第二份会独立变化的接口定义。

## 迁移时保护的是完整理解

旧稿的价值可能在论证过程、细节、条件、反例、图，或章节之间的递进。逐字保留所有文字并不自动保留这种价值，全部重写也可能损失它。

先抽取实质内容，再按最新定位和实现核对。将仍有效部分写回主线，必要时改术语、换案例或分离历史状态；保留原始版本便于追查。目录、别名和旧链接服务于这个过程，不应取代主要交付。
