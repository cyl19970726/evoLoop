# 独立认知 Wiki 后端选型（2026-10-19）

> **历史研究记录。** 本文保留 2026-10-19 的只读选型判断；于 2026-10-19 整理为公开阅读版，未重新运行候选或复核上游最新版本。文中的 `main` 链接和 GitHub star 数只代表当日访问与快照，不代表当前源码或规模。后续固定版本实测与当前判断见[首轮验证摘要](../references/validation-summary.md)及[Wiki 功能与流程比较](../references/wiki-feature-comparison.md)：OpenViking 已做受限样本验证，可继续串行试点，但还不是正式选型；检索、记忆或编译入口本身不能证明持续的 Wiki 修订可靠。

## 判断与边界

**在本文三个图/检索基础组件中**，Graphiti + FalkorDB 最适合先验证证据来源与时间失效；这不是完整独立 Wiki 系统的总体定案。补查的 OpenViking 已内置资源、会话、记忆和 `ov compile` 编译入口，且有官方 LLM Wiki Skill 示例，因此比这三个基础组件更接近用户目标，值得优先试验。此为当时的研究排序；后续实测与现阶段判断见公开的[首轮验证摘要](../references/validation-summary.md)和[功能与流程比较](../references/wiki-feature-comparison.md)。Graphiti 是 Apache-2.0 的开源框架；**Zep 是另一个托管产品**，不能把 Zep 的用户、线程、治理、托管性能和控制台能力算作 Graphiti 自带。[Graphiti 项目说明](https://github.com/getzep/graphiti/blob/main/README.md#zep-vs-graphiti)、[许可证声明](https://github.com/getzep/graphiti/blob/main/pyproject.toml)、[OpenViking 官方说明](https://github.com/volcengine/OpenViking/blob/main/README.md)

原对照的三个项目都**不是完整的 LLM Wiki 编译与维护系统**。它们处理摄入、索引、图或检索；没有核到能原生承担“按主题持续修订的权威综合页 + 假设/决定状态 + 人类审阅 + 引用校验 + 影响传播”的完整工作流。Graphiti 的 community/saga summary 和 Cognee 的 improvement 是辅助生成物，不能直接当权威 Wiki 正文。OpenViking 的官方 Skill 实际提供 Wiki 编译流程，但审阅、并发修订和确定性的来源撤回仍需验证。认知正文应在独立知识空间；Markdown 格式可以使用，只是不把开发仓库 Markdown 当权威存储。此处对前三者“不具备完整工作流”是依据已核的产品 API/文档所作的**能力边界推断**，不是对所有扩展生态的穷举证明。

本轮只读核对 Context7、各项目官方 GitHub 文档及部分源码；**未安装、运行或连接任何候选，未用真实历史测试正确性、并发、性能与恢复**。当时未公开的早期设计稿曾建议把仓库 Wiki 作为权威；本选型已按用户此后的要求，将权威认知正文放在独立知识空间。当前公开边界见[架构总览](../architecture/overview.md)；这不等于本文已实测候选。

## 需求拆分

一条 session 产出先作为**不可变材料/证据**登记（稳定 ID、来源 URI、片段定位、采集与事件时间、可见范围）；抽取的实体/事实保留对应证据。另一层是可读的**主题综合页**，由维护 session 按证据形成、修订、标记争议/失效，并把变更指向受影响的任务或决定。检索命中、图边、自动摘要均不能自动成为当前结论。跨 session 提交宜是候选变更；维护者处理冲突；后续 session 读取指定主题的当前修订并能下钻依据。这个分层也避免把向量库当成唯一事实源。

## 补查：OpenViking 更接近独立知识系统

OpenViking 主仓库采用 **AGPL-3.0**，官方称完整开源、无激活门槛；`viking://` 是虚拟 URI，**不是开发仓库里的文件路径**。实际内容在 AGFS/RAGFS（本地文件系统或 S3 等后端），向量索引独立存 URIs、摘要和嵌入；本地试验可用本地内容与向量后端，线上部署要配置鉴权和备份。[README](https://github.com/volcengine/OpenViking/blob/main/README.md)、[许可证](https://github.com/volcengine/OpenViking/blob/main/LICENSE)、[存储架构](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/05-storage.md)、[配置](https://github.com/volcengine/OpenViking/blob/main/docs/en/guides/01-configuration.md)

它把导入文档/网页/仓库的 **resources**、`session.commit` 后异步提取的 **memories**、**skills** 放在同一空间；REST、SDK、CLI 和 MCP 提供 `add_resource`、`read`、`find/search`、`write/edit` 等接口，session API 归档消息并生成记忆。新内容需等待后台解析和索引完成后才可被语义检索。共享资源有账号内 ACL，用户私有资源隔离；这些权限需按部署配置验证。[CLI 操作面](https://github.com/volcengine/OpenViking/blob/main/docs/en/getting-started/05-cli-setup.md)、[MCP](https://github.com/volcengine/OpenViking/blob/main/docs/en/guides/06-mcp-integration.md)、[Sessions](https://github.com/volcengine/OpenViking/blob/main/docs/en/api/05-sessions.md)、[ACL](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/15-acl.md)

关键新增能力是 **`ov compile` 真正运行一个 agent 任务来生成或增量更新目标 Wiki**：需启用 Compile Runtime（本地可安装 `openviking[bot]` 并启用 VikingBot），安装仓库附带的 `llm-wiki` **示例 Skill**，传入来源与目标 `viking://` 目录。该 Skill 指示读现有 Wiki、合并主题页、保留矛盾与版本差异、在主张旁引用源 URI，并维护 `index.md`；输出页面是 OpenViking 知识空间内可由 API/MCP 读取的 Markdown，不是仓库正文。这个流程比 Graphiti/Cognee/LightRAG 更直接吻合“材料→跨来源综合页→后续 session 读取”。但规则主要由 Skill/agent 执行，**不等于数据库强制的逐主张来源完整性、自动因源删除而失效或人工批准门槛**；需以案例验收。[Compile 总览](https://github.com/volcengine/OpenViking/blob/main/docs/en/context-compilation/01-overview.md)、[LLM Wiki 示例](https://github.com/volcengine/OpenViking/blob/main/docs/en/context-compilation/02-llm-wiki.md)、[Skill 规则](https://github.com/volcengine/OpenViking/blob/main/examples/compile/ov-compile-skills/llm-wiki/SKILL.md)

并发边界：底层 path lock 保护 `rm/mv/add_resource/session.commit` 等操作、任务队列恢复后台处理，但官方明确**不提供跨内容/索引/队列的原子事务**。MCP `write` 默认 `replace` 覆盖，`edit` 是精确字符串替换；未核到发布 Wiki 页时的 `expectedRevision` 条件写。Compile 请求有短期有效的 `Idempotency-Key` 防重复提交，却不保证两个不同编译任务不会互相覆盖同一页。最小试验应一个项目 Wiki 仅允许维护 session 串行发布；其他 session 提交材料或候选变更，发布前读现有页、留快照，并对冲突人工复核。[并发与恢复](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/09-transaction.md)、[MCP 写入语义](https://github.com/volcengine/OpenViking/blob/main/docs/en/guides/06-mcp-integration.md)、[Compile 提交恢复](https://github.com/volcengine/OpenViking/blob/main/docs/en/context-compilation/01-overview.md)

备份方面，`ov export/import` 迁移单个资源或用户树，`ov backup/restore` 的 OVPack 覆盖账号内公开 scope 内容，能带语义 sidecar 与可选稠密向量；**不带用户账号/API keys**。官方提示 backup 非原子时间点快照，严格一致性须暂停写入。`ov snapshot` 能保存/回滚工作空间版本，但不能替代“每条 Wiki 主张对应哪份原始证据、来源撤回后该结论是否仍有效”的应用层核查。[OVPack](https://github.com/volcengine/OpenViking/blob/main/docs/en/guides/09-ovpack.md)、[CLI snapshots](https://github.com/volcengine/OpenViking/blob/main/crates/ov_cli/README.md)

**判断：支持 OpenViking 作为比本文三项更优先的总体试验候选，但仍未选定。** 它用同一个开源服务覆盖材料、会话、记忆、Wiki 编译与读取，且已有较大的社区；Graphiti 胜在显式 episode→事实来源及双时间失效，OpenViking 的 Wiki 来源关系主要由页面链接和 Skill 维护。真正影响选择的门槛是：两个 session 竞争同页、旧来源删除或更正、人工修订在再次 compile 后保留、OVPack 恢复后链接有效。四项均未经实测，不能用 star 数或示例 Skill 的文字承诺代替验收。

2026-10-19 查询 GitHub API 时的 star 数：OpenViking **40,242**、LightRAG **40,200**、Cognee **32,478**、Graphiti **31,970**；OpenViking 已达到用户希望优先考察的社区量级。star 是筛选成熟度的弱信号，实际维护与可靠性仍看上述试验。[OpenViking API](https://api.github.com/repos/volcengine/OpenViking)、[LightRAG API](https://api.github.com/repos/HKUDS/LightRAG)、[Cognee API](https://api.github.com/repos/topoteretes/cognee)、[Graphiti API](https://api.github.com/repos/getzep/graphiti)

## Graphiti 最小试验与仍需自建的薄层

**仅当选择图/检索基础组件路线时**，Graphiti 的优势是把“哪条证据生成哪条事实、事实何时有效/失效”放在底座中，且有官方 MCP 可供不同 session 读取。试验只取一个项目、少量去标识化材料，不把已有真实历史送往外部；服务本机运行，先确认模型提供者与数据去向，再投入受许可的材料。若最先需要的是大量异构文件入库、引用片段和数据集 ACL，Cognee 更适合作为替代试验；但须核对其特定后端的隔离/来源能力和 OSS/授权边界。LightRAG 适合作检索对照，不应优先担任权威认知底座。

薄层建议仅有四件事：① 独立的原材料登记与对象存储（稳定 source/fragment ID、校验和、URI、时间、访问范围；Graphiti episode 记这些 ID，原文件不依赖图数据库单独保存）；② 独立的综合页存储（例如一张 SQLite/Postgres 版本表或现成可 API 编辑的 Wiki，页有稳定 ID、修订、状态、来源引用、假设/决定/争议字段；正文可用 Markdown，权威副本不在开发仓库）；③ 一条维护流程，session 提交候选变更，维护 session 核证据、合并/保留冲突、发布当前修订并产生受影响任务 ID；④ 统一读取接口，按项目和主题返回“当前页 + 修订 + 依据”，并可追到原片段；对所有写入做版本条件校验/单写入串行，不能假设 Graphiti `group_id` 或 MCP 自动解决并发编辑。任务表继续是行动权威，Wiki 只保存认知及任务引用。

试验验收应做三条贯穿案例：旧结论被新证据推翻后旧事实如何失效、页面如何修订；两 session 给出相反解释时能否保留双方来源并阻止静默覆盖；删除或撤回一份来源后能否找出依赖它的事实/页面，且备份恢复后 ID 与引用仍可用。记录调用次数、处理延迟、人工整理成本、下轮 session 是否正确使用修订。未经这些实测，不承诺自动准确判矛盾、自动完成综合页维护，也不承诺生产级隔离或恢复。
