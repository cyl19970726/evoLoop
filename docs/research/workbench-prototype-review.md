## 检查与后续工作

原型仅在本页模拟导航、筛选、状态变化和按钮反馈；刷新会重置。已检查内联 JavaScript 语法及十个视图的合成状态路径；另在真实浏览器操作了提议与补证、需求版本比较和 r2 采用后保留 r1、分工替代选择与撤回、日程暂停、运行未知/同步冲突、逐 case 评价及 Wiki 搜索空态。

Wiki 浏览器路径检查了历史 v2 候选不可直接发布、来源不可核对时停住、恢复来源后的独立发布、未知结果先核对、返回 v4 后模拟已读但采用仍待验。集成检查据此补上候选基线绑定、来源/基线发布阻止，以及列表、详情和异常页的状态一致性。桌面阅读/Review/评价及 390px 手机知识/评价页完成目视检查；手机菜单可切换，十个视图无整页横向溢出。原型目前仅演示一个临时候选，未实现完整候选历史、全部历史修订回读或权限变更场景。

后续文档分类澄清检查了整理面板的审阅、合并、构建三个独立阶段，以及原有 r2 采用后仍保留 r1 的路径；桌面与 390px 手机整理面板完成目视检查，手机无整页横向溢出。[项目数据](../architecture/project-data.md#6-工作文档怎样沉淀为仓库正式文档)的新流程图在浏览器渲染成功。同步补充产品定义、文档维护、领域合同、存储、前端、包架构和知识流；自动化整理仍是待实现设计。

用户随后指出，上述版本虽区分了文档用途，却仍把 repo 文档纳入了 Document Table，设计并不符合其范围要求。DEC-023 因此收窄文档表和目录；前述界面检查仅证明当时模拟可运行，不证明用户认可该分类。当前目录以过程文档及 Task 直接关联为准，仓库 `docs/` 独立维护。

本次纠正后的浏览器检查确认：目录只列 DOC-021、DOC-018 两份过程文档；两者均能与关联 Task 往返跳转；侧栏仓库入口实际打开独立产品报告。工作台、存储、知识流和项目数据图均可渲染；390px 过程文档页无整页横向溢出。真实 link 保存、仓库来源解析与数据库约束仍未实现。

后续表格/全文调整的浏览器检查确认：键盘打开 Markdown、r1/r2 切换、完整七节正文和表格、原文显示、Task 链接独立跳转及 Task 返回全文均可操作；HTML 在空 sandbox 的 srcdoc 中显示独立样式，滚动可见报告末尾，原文以文本显示。390px 列表和两种阅读页没有整页横向溢出；表格自身允许横向滚动，返回列表恢复所记录的滚动位置与行焦点。此次 HTML 是内嵌的自包含合成报告，未验证上传资源包、外链依赖或脚本执行，也不是面向任意不可信文件的安全验收。

这些是界面和模拟路径证据，不是用户亲用或服务验证。尚未实现后端、权限、持久化、真实 Wiki/飞书/Codex API，也未覆盖每条产品路径的完整异常分支。将来做真实产品时，要用固定修订、授权、幂等请求和可回读结果替换页面内状态，并以独立消费与实际用户效果检验价值。


## 转入真实前端首片方案（2026-10-20）

### 范围与结论

用户最初要求按合并后的产品文档检查并完善原型；随后明确指出左侧目录过多、不必把静态原型继续实现完整，选择“先收敛前端首片方案，暂不写前端代码”。据此停止原型扩展，保留问题和真实前端验收约束。**本轮交付只有文档方案；公开原型与前端代码均未修改。** 中途本地试改候选尚未完成最终验证，已撤出本轮差异，不作为已修复或产品可用的证据。

固定对照为 `main@d74d68a087b9ef45c2d3ff96381dd4cffc223bac`：按[完整旅程](../product/definition.md#从一个目标走到第一次有效交付)、[工作台](../product/workbench.md)与[日常工作](../product/daily-loop.md)审计源文件，实际打开原型首页、提议与手机布局。原有目录十项平铺，开场就是已有需求的复核；选择现有领域责任者后，提议仍只有送交判断或补证，不能演示接受。其余新路径缺口主要由源码对照发现，不能一概说都已在真实业务中复现。

### 目录怎样收拢

**模块、路由和产品对象不应逐项变成常驻菜单。** 首期建议左侧只有总览、工作、知识：待判断/任务/过程文档放工作区；关联在对象详情；分工、日程、评价从相应工作上下文进入；待处理/异常固定可达。知识仍可独立浏览，过程文档可先于任务存在，Git 正式文档仍是独立来源。这样减少一级入口而保留完整行为与稳定链接。

三项目前是设计建议，尚未用真实前端验证；不能宣称三项对所有项目最优。后续从普通入口观察首次查找、切换、回退和手机遗漏，再决定是否需要提升高频入口。导航唯一正文见[产品约定](../product/workbench.md#项目范围导航与事实状态)，不在本报告另维护一套菜单。
