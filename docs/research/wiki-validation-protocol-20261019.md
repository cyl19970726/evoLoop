# OpenViking 与 nashsu/llm_wiki：共同验证协议 v1

> 研究记录：冻结实验协议与执行范围，非正式选型。公开整理版 2026-10-19；原始运行证据外置、未发布，本次未重新运行实验。协议中的将来时保留当时计划语境；已完成的实际结果分别见 [OpenViking](openviking/results.md) 与 [nashsu](nashsu-llm-wiki/results.md)，并非所有计划项目均通过。

2026-10-19。用户已要求创建两个独立 session 验证候选。此文件是实验与验收方案，不是认知 Wiki 正文。两个候选都尚未获最终采用。

## 要回答的问题

它能否支持不同 session 从材料和实际工作中形成、修订和使用认识，帮助下一阶段做出更好的产品动作？同时比较人阅读、维护的体验，以及集成和持续运维代价。安装成功、页面数量、检索命中或 README 声明不能单独回答这个问题。

用户边界：认知正文在开发 repo 外，Markdown 可接受；任务权威仍是飞书；全员认知，专门 Wiki session 维护；角色按工作证据动态演进。不得为候选预设一定胜出。

## 共同输入与文件归属

- 固定材料包：外置实验空间中 2026-10-19 轮次的 `common/`。材料来自当前需求的中文重建样例，**不是原始会话逐字记录，也不是对旧会话的审计证据**。原件未随公开报告提供，以下文件名是保留证据的定位标识。
- 两边同读 `fixtures/events.jsonl`、`fixtures/consumer-tasks.json` 与 `manifest.json`，按批次输入；不能提前把未来纠正注入初始知识库。
- 评价规则在 `evaluator/rubric.md`，仅构建/验收者读取，不能摄入候选或传给 fresh consumer。
- OpenViking 独占外置实验分区 `openviking/`，文档现位于 `docs/research/openviking/`。
- nashsu 独占外置实验分区 `nashsu-llm-wiki/`，文档现位于 `docs/research/nashsu-llm-wiki/`。
- 源码 checkout、依赖、知识正文、索引、运行日志、截图、备份都在各自外置目录；正式方案、运行摘要、证据索引和集成建议写各自 docs 目录。
- 不能改共同包、另一候选目录、主设计文档或全局配置。发现共同案例有问题，记录具体问题及建议；主会话统一修订后两边再使用同版。

## 推进阶段

### 0. 固定实验与能力核实

读取现有设计及对应调研作为线索，再查当前官方源码/文档；固定一个实际 commit/release。写出最短运行路径、数据实际位置、可调用接口、模型/嵌入依赖、必要人工操作。模型凭据缺失时说明缺的是哪项，继续源码、接口与无模型检查，不把模拟响应计为模型通过。

两边尽量使用同一可用模型与相同输入。记录精确模型、配置、上下文限制、调用/延迟、依赖和计算环境；无法统一时明确哪些比较会受影响。不要为了统一强行破坏产品原生流程。开始就记录预计能原生覆盖、需适配、无法覆盖的案例。

### 1. 原生最小流程

在隔离目录启动最小实例，从少量来源进入持久 Wiki，再由接口和人工阅读入口访问。核实重启后的持久化。先使用产品原生方式与官方附带 Skill，记录必要设置，不先重写产品。

### 2. 共同案例

| ID | 实验 | 核心判据 |
| --- | --- | --- |
| V1 | 先摄入 batch 1 的旧建议，再加入 batch 2 的用户纠正 | 当前方案采用独立知识存储、Markdown 可用；旧建议可追溯，不能伪称一直如此 |
| V2 | 对同一交接失败摄入两个不同解释 | 保留两方依据与不确定性，不按后写入者定真；能提出能区分解释的下一步观察 |
| V3 | 已知同一页基线的两个写者分别更新；可用接口下模拟写入超时/重试 | 无静默丢更新；重复处理可辨识；若没有条件更新，明确缺口和串行维护的限制 |
| V4 | 撤回一份测试来源，并按产品语义重建/维护 | 能发现受影响的认识与引用；不能把删除来源简单解释为相反结论成立 |
| V5 | 全新上下文的 consumer 只通过正常知识入口完成具体阶段方案 | 交付可检查产物，遵循新约束、引用依据，包含实际使用检验及下一阶段判断；只回答问答不够 |
| V6 | 把容量不足和新职责证据分别交给 consumer | 不遇到积压就新增角色；对新维度给出职责边界、替代办法、试行与退出条件，或有证据地拒绝 |
| V7 | 导出/备份到新位置，恢复或重启后再读取并消费 | 正文、来源、关联与已有修订/争议状态可用；明确哪些数据未随导出保存 |
| V8 | 按人类的实际操作路径看一页认识、定位依据、判断过时、修改纠错 | 记录步骤、所需知识和人工主动用时；Agent UI 检查不能冒充用户已经满意 |

V3/V4/V7 在候选自己的测试副本操作。原生不支持某能力就记录缺口，不为了全绿而跳过或用人工填答案。需要 UI 时按现有浏览器/桌面技能操作。

### 3. 独立消费与对照

构建者可能看到评价规则，consumer 必须是无历史继承的新上下文，只拿任务与正常知识入口，不拿答案、构建对话、原始材料全集或修复记录。可用子 Agent 或产品中新对话完成；若只能在构建上下文回答，标注上下文污染，不能记为独立验证通过。

用同一消费任务做一次原始材料直接读取的对照，检验 Wiki 带来的信息获取与行动收益。对照者同样无构建历史，只得到原始材料和任务。比较输出中的约束遗漏、无依据判断、来源追溯、修订采用、检索/阅读开销与人工介入。模型和入口差异要单列，不把全部效果归功于 Wiki。

任务答案不要求措辞一致；评价必须检查产物和可回查依据。对于有多种合理解释的场景，评价其证据与可验证下一步，不要求猜中预设结论。发现偶然模型错误时可有限重跑定位原因，保留首次结果，不反复改提示词直到偶然成功。

### 4. 最小适配与接入结论

先冻结原生成绩，再对一个关键缺口做最小适配试验（有价值才做）。说明代码/提示词/人工工作量、维护责任、能保证什么和不能保证什么。不得把适配后的成绩回填为原生支持，也不做整套 harness 重建。

结论允许：可直接试点、需有限适配、仅适合作为阅读入口、当前不适合或证据不足。设计接入职责：业务 session 怎么贡献，Wiki 维护 session 怎么修订，其他 session 怎么读取，飞书与正式 docs 如何引用而不形成多个权威。

## 结果格式与证据要求

每个案例记录：固定版本与配置、输入批次/hash、操作与真实响应/截图路径、期望与实际、通过/失败/未提供/阻塞/未验证、失败原因、实现层、耗时与人工介入。

实现层必须区分：原生存储/API 机制、官方 Skill/提示词、我们新增的适配/提示词、人工操作。文档声称/源码推断/实际运行分别标注。核心约束失守不能被漂亮 UI 或总体加权分抵消。

每个 session 交付 `plan.md`、`results.md`、`integration.md`；允许合并短文但须清楚覆盖三者。进度与结果放自己的目录，主会话通过这些文件和会话状态读取，不依赖模型记得跨会话发消息。

## 执行范围

用户的验证请求授权可逆的本地隔离下载、依赖安装与最小运行。只使用测试包，不上传完整历史、不购买/部署公网服务、不修改现有业务环境。全局 Skill 安装仍须具体明确授权；所需 Skill 默认只在项目本地使用。已有模型配置可按现有工具安全使用，不输出密钥；若缺少所需凭据或涉及新的付费承诺，问具体缺项并继续独立工作。

本轮先建立共同协议、材料与两会话。实际结果由各会话执行后填入，不能把此方案当成已跑通。
