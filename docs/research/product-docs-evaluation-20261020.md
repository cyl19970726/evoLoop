# 产品文档评估：能理解产品，下一步工作仍需收敛

2026-10-20 · 独立文档消费评估与改进建议。**这是研究判断，尚未采纳为正式产品方案。**

## 结论与先做什么

**当前文档足以帮助新 Agent 理解产品目标、重要边界和纠正处理原则；它作为产品设计基线是可用的，作为“一次读懂、直接选出小任务”的工作入口仍有明显负担。** 三个独立上下文的文本消费案例均守住了主要边界，但不能据此认定真人容易阅读、产品闭环已经有效，或文档能稳定指导所有实现任务。

最值得先修的不是再增加一套文档，而是集中回答三个问题：

1. **现在这一轮做什么？** [阶段路线](../roadmap.md#眼前的关键工作)有四条候选工作线，M1 又包含主数据、工作台、飞书和运行时；缺少一个可照着选择的首片示例及“本片暂不接通什么”的说明。消费案例 B 能写出正确过程，但把复现、纠正影响、阶段取舍、产物修订和后续使用验证装在同一任务里。
2. **为眼前问题读哪几节？** [文档导航](../README.md#当前正式文档)把 21 项正式文档列在同一张表中；根入口没有直接列出工作台产品页。HTML 有全站目录，长页没有页内目录。三个消费者实际申报阅读 6、9、6 页，其中 C 在第 3 页已有首轮回答，其后补读细节。页数不能等同于成本，但说明答案往往靠跨页拼合。
3. **每个细节由哪里唯一维护？** 产品定义同时承载定位、12 个场景及长篇验收；过程文档归属和沉淀流程在产品定义、日常闭环、工作台及架构中反复展开。当前核对的核心边界一致，重复的主要风险是未来改版要反复同步，而非本轮发现了普遍矛盾。

建议先做三项小改：现有入口加按任务分流的短路径；在现有路线页加入一条有边界的下一步工作示例；压短 P11 等长场景并用稳定链接指向详细行为。页内目录可作为随后的小型阅读工具改进。保留两维度、四部分、领域自主修复和证据驱动分工的产品方向。

## 方法与可观察判据

先做全文结构与主张核对，再让三个全新上下文的只读子 Agent 从快照根 README 自选链接完成不同任务。测试提示给场景和输出要求，没有给用户确认的标准答案；评估者保留这些约束用于判读结果。随后实际打开生成 HTML，核对正文层级、导航和图。没有让消费者互读答案，也没有给评分反馈后重跑挑选更好的首轮输出。

使用四种定性档位，不计算综合分：**可用**＝本次有明确正文和消费证据支持；**有条件**＝能完成，但仍需明显跨页整合或额外限定；**缺口**＝本次所需信息缺失、冲突或无法定位；**未测**＝需要的真人、运行或长期证据没有采集。档位只适用于对应问题，不是全产品评级。

### 结构上的具体问题

**F1：缺少首个小切片的范围示范，优先级为高。** 定义的“第一期范围”、路线 M1 和工作台“首期可用工作台”各自在合理范围内谈不同完成单位：M1 单次交接、M1→M2 接通工作台、六条路径完整才算首期范围完成。它们并非直接冲突，但没有集中说明“单片完成、阶段完成、整套工作台完成”的包含关系。B 的首轮任务把多个结果串在一起，是一个真实的可用性线索；B 的提示本身也包含两件事，不能把全部扩张归因于文档。建议先在路线中示范一个只交付诊断/选择的小任务，并指向后续实现切片，之后再用同题新消费者验证。

**F2：索引偏资料分类，缺少按意图进入的短路径，优先级为高。** 文档导航确实说明了每页回答什么，不能称没有信息架构。但“我收到纠正”“阶段全绿但用户不会用”“是否增设审核职责”都需要读者自行从目录映射到多个页面。C 先读 daily，再读定义便能回答原则，却仍补三页才讲清版本与试行细节。建议保留全目录作为第二层，第一层只列少量常见任务与具体章节，不要求读全套。

**F3：颗粒度在同一页面、同级场景间不均，优先级为中。** P03 用一段场景和一段验收表达恢复结果；P11 在同一 H3 下还包含 Document Table 范围、Markdown/HTML 阅读、两个任务改版、飞书冲突、多来源沉淀与合入/构建状态。前者适合定位，后者像压缩了多个规格页。工作台的信息层级列出七类二级导航，页面表又有日程、评价；它们究竟是一级入口还是子入口未在此处映射。可以用页内小节与分类解决，不必立即多拆文件。

**F4：防错约束重复，用户动作被技术细节打断，优先级为中。** “过程文档不含 repo docs”和“任务/合入/构建分开”在定义、daily、workbench、项目数据、合同、维护规范中都展开。重复摘要有助保护关键边界，本轮消费者也记住了它们；问题是多处出现可独立演进的细节。Wiki 产品页又进入 hash、操作 ID、串行发布、同基线写与 unknown；这些确有失败依据，应在架构/规范保留，产品页主要保留用户看见的拒绝、冲突、来源失效和恢复结果，再链接详细合同。

**F5：HTML 能读，局部定位与大图总览欠佳，优先级为中。** 见下文实测。它影响长页的跳读，不证明正文内容无效。

**F6：研究入口有一个邻接状态容易误读，优先级为低。** [研究索引的运行时小节](README.md#运行时与协作接入)仍说真实任务与桌面互通等“均未验证”；[路线当前基线](../roadmap.md#当前基线)却已补充独立 PR #2 的隔离线程夹具与桌面宿主通知消费。二者可按“原调查范围”和“后续夹具范围”解释，但索引未在该句标清时间和范围。应在小型后续修订中加一个固定后续证据链接，而非扩张为运行时审计。本轮按文件所有权不改该无关段落。

### 产品主线是否形成闭环

在文本设计上已经形成：定义的动机是减少重复解释、交接遗漏和无效交付；路线每阶段同时有交付和学习问题；loop 要求真实使用反馈改变下一步；P07 还要求两次相连循环。四部分的分工也有因果关系：认知选择行动，动态分工调整承载，任务机制保持责任连续，Wiki/evaluator 检查认识能否跨阶段改变行动。没有证据支持把现有文档评价为“只有概念和状态”。

尚未闭合的是这条设计到实际收益的证据。文档已经要求可比工作基线，也允许直接材料比 Wiki 更好；但首个真实任务族、人工串接的比较路径、何种变化足以继续投入，尚未具体选定。因而动机已讲清，四部分各自要解决什么也清楚，**它们在首片应各做到多深、收益是否抵消连接成本仍是待学问题**。应由一个受限试点回答，不能用本轮文档消费正确替代。

正文并未要求常规工作逐项等待中心审批：daily 明确领域责任者可接受权限内修复，独立判断只针对争议、新方向和跨域事项，并有缺人补位。三个案例没有出现集中审批误读。风险更在于每件小事若都被实现为完整字段、跨系统链接和全链评价，会把合理原则变成负担；这是待实现时应防的风险，本轮没有运行证据证明已经发生。建议使用与影响相称的任务范围及证据，不再增加审核岗位。

## 一个具体改写示例：P11 的层次收敛

现状结构是：P11 同时写过程文档身份/多对多关联 → 格式与全文阅读 → 需求改版和飞书冲突验收 → 讨论沉淀 Git → 补充验收。读者为了找到“需求改版验收”，也要经过格式和发布细节。

建议保留 P11 锚点，把该节改为下面的产品层摘要（**示例，未修改正式正文**）：

> **场景：**需求或技术讨论形成可追溯的过程文档，任务采用明确修订。新需求被采纳后，责任者逐项判断关联任务是否需要换基线；原讨论、旧任务依据与未采纳意见可回查。长期成立的结论可经仓库审阅纳入正式文档。
>
> **用户应看到：**过程文档与任务直接关联；repo `docs/` 从独立入口读取；Wiki 保存有来源的认识。修订和整理不会把三者变成同一份正文。
>
> **验收：**用一次需求改版核对两个旧基线任务：一个调整验收，一个记录仍适用的理由；再让新消费者按选定基线完成工作。若结论纳入 Git，能从固定过程来源追到采纳范围及合入 commit；任务完成、合入、构建和使用效果各自可查。
>
> **详见：**版本与旧编辑冲突见现有项目数据/合同；表格及 Markdown/HTML 全文阅读见现有工作台；多来源到正式文档的整理见现有项目数据 §3a。上述业务路径尚未运行。

重构时应在所属页保留原来必要的飞书旧版本冲突、HTML 原件/资源和多来源整理验收，再用链接连接，不能为了短而删除要求。若审阅认为格式阅读应独立成为产品场景，可保留 P11 的子判据，当前不必另建一页或立即增 P13。

### 下一步小任务应该有多小

可在现有路线页给一个当前阶段示例，而非把案例 B 的整个循环一次提交：**在固定文档基线和一个负责人反馈下，只定位“找不到下一步”的一个具体阻塞，比较至多三个解释，提出一项最小修复及其验收；本任务不实施该修复。** 输入缺少点击路径或纠正原文时明确待取得；必要事实未齐全时只交付受限判断，不补造原因。独立消费者核对“证据是否支持这一选择、下一任务是否可开工”即可验收这一调查。后续修复另有具体产物和真实使用验收，阶段效果继续待验证。

收到明确、已授权的本领域纠正则可并行修复并验证，不须等上述调查或专门认知 session 批准；跨目标或存在争议的部分才路由取舍。这样把责任闭环和任务切片同时保住。
