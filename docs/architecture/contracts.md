# evoLoop 领域合同

> 状态：拟议最小语义合同，2026-10-20；接口尚未实现。已确定 PostgreSQL 保存 evoLoop 主数据，飞书作为 connector 和协作入口；具体结构、API 与同步行为仍待验证。整体位置见[架构总览](overview.md)，数据所有权见[项目数据架构](project-data.md)，面向用户的行为见[产品定义](../product/definition.md)，落地方式见[开发规范](../development/standards.md)。

## 1. 通用身份与结果

跨系统引用使用稳定的项目、任务、日程、文档、文档修订、关系、来源、知识、逻辑 Role、Session、操作和成果标识。飞书等外部平台 ID 保留在 `ExternalBinding`，不能把可变化的标题、Wiki 路径或会话窗口名当唯一身份。每条可追溯变更至少记录行为者/承载 session、发生时间、所读基线、写入意图、操作 ID 与结果依据；可见范围跟随来源权限，不因被摘要引用而自动公开。

结果统一区分：`applied`（已回读证实生效）、`rejected`（明确失败且无效果）、`pending`（已接收待异步完成）、`unknown`（超时/断连，是否生效未明）。`unknown` 是持久待对账状态，不能映射为失败后盲重试，也不能伪称成功。后端没有强制条件写能力时必须报告“不支持”，不能用“先读后写”冒充原子操作。

## 2. TaskStore：行动状态的唯一权威

`TaskStore` 的主数据在 PostgreSQL；飞书多维表格是可读写的协作投影和入口，不拥有任务本体。人可在飞书受支持字段编辑，入站变更须由 core 核对身份、权限、基线和状态转换后成为内部 command，不能直接覆盖主数据。每个受管项目维持独立任务命名空间，evoLoop 不接管业务项目的代码与 Git 正式文档。所有入口经同一合同，飞书同步滞后不使 PostgreSQL 的已提交任务失效。[数据权威](project-data.md)

| 能力 | 最小语义 |
| --- | --- |
| `get/list` | 读稳定任务 ID、项目、类型、目标/判据、依据、优先级、责任 Role、状态、交付与修订标记；列表支持有边界的分页和过滤。 |
| `create` | 用操作 ID 在 PostgreSQL 去重；写超时按操作 ID 回读本体和事务结果，未能证明时保持 `unknown`。同事务登记待投影 outbox。 |
| `patch` | 只改指定字段，声明读入版本；PostgreSQL 事务中执行条件更新和状态校验，旧基线拒绝并返回当前版本供重审。飞书入站也走这一条，不以远端最后写入时间判赢。 |
| `archive` | 结束/归档任务但保留追溯，不把删除当作默认完成。 |
| `changes/reconcile` | 主数据变更通过内部提交记录观察；外部 connector 事件只提示远端需回读，水位与周期对账补事件遗漏、乱序和分页期间变化。 |

任务类型可包含缺陷、需求、调查、文档、知识维护和职责调整；创建任务不代表接受实施。状态至少能区分待判断、可做、进行中、待验证、完成、阻塞/暂缓；最终字段与飞书投影列映射须在真实表上定。任务“实现完成”与“效果已验证”是不同结论。重复任务归并时保留原 ID 和关联证据，不丢请求者的独特验收条件。任务引用作为判据的原生文档修订、Git commit 或外置 Wiki 修订时，应固定版本；后续更新触发影响复核，不静默改写已接受任务的依据。

业务任务状态、运行操作结果、效果验证状态分别记录并关联。[产品状态图](../product/agent-loop.md)表达主要转换：任务自己的验收含实际使用时，不能缺少使用证据而关闭；纯实现子任务可先完成，关联阶段效果仍待验证。阻塞保留缺项与解阻责任，暂缓保留恢复条件，取消保留原因及已发生副作用；停止请求被接受不等于运行已停止，取消不能清除 `unknown` 对账义务。

### 提议、判断与验收责任

`TaskProposal` 区分来源（如 dogfood、用户要求、定时检查）、类型（缺陷、需求、调查等）和接受状态。最少保留受影响项目/系统、报告者、观察与来源、预期效果、复现条件或未知、判断责任者、消费者验收、所读任务/知识修订和关联提议。归并只合并相同目标，不覆盖新增证据或原请求者的判据。

`ReviewDecision` 关联提议和读入基线、判断者、接受/补证/暂缓/不接受、理由、替代方案及再看条件。权限与资源内的常规修复可由现有责任者接受；新方向、争议或跨域事项路由给适当的独立判断者，必要时由负责人作目标取舍。缺少判断者时保留指派责任，不静默进入执行或无限无人接手。接受决定若因用户纠正或版本变化失效，重新判断后再派发。

`Delivery` 关联任务、运行、成果修订、已做检查、未验证项和实际使用入口。提交者可同时附带新问题/需求与知识候选，但“写交付”不自动拥有最终验收权。核对和亲用由任务中约定的责任者承担，独立性依风险与判据决定，不要求所有完成项都由人类逐条确认。

首期仍用单活协调者串行派发，租约、并发条件和失去独占后的停写行为在 PostgreSQL 上验证；不再把飞书记录字段当独占锁。数据库条件更新能约束内部抢占，却不提供跨 Codex、飞书和 Wiki 的恰好一次副作用。

## 2a. DocumentStore 与 RelationStore

`DocumentStore` 登记项目原生文档与外部引用文档，二者的**正文所有权不可混同**。`native` 文档由 evoLoop 在 PostgreSQL 保存正文，`DocumentRevision` 不可变，含作者、创建时间、内容校验、格式、权限与所读基线；更新当前指针须在事务中按预期修订条件提交，旧基线冲突须显式返回。`reference` 文档只保存外部系统、稳定定位符、观察到的修订、权限与摘要或元数据，不把外部正文悄悄复制为本体。既有本仓库和受管项目的 Git 正式产品、架构、开发规范仍以各自 Git 正文及 commit 为权威；DocumentStore 只登记 `ref + commit`，发布 HTML 也是只读视图。原生 Document 是独立资产，不是 Task 的描述大字段；一个文档的接受或更新不自动接受全部关联任务。

`RelationStore` 保存有方向、有类型的跨对象关系，例如 `justified_by`、`specifies`、`implements`、`validates`、`contradicts`、`supersedes`。关系端点可为 Task、Schedule、原生／引用 Document 修订、KnowledgeRef、EvidenceRef、Delivery 或 Review；至少记录项目、端点固定修订、关系作者、依据来源、观察时间、状态、ACL 和撤回／取代链。关系只表达一项**有来源的主张**，标签本身不证明任务已实现、验收已通过、知识为真或权限可继承。创建、改向或撤回关系须校验两端身份与权限；来源撤回、文档改版和 Wiki 修订触发相关关系与任务的影响复核。PG 可为跨 Task／Doc／Wiki 导航保存 `KnowledgeRef`，但 Wiki 正文、来源与内部知识依赖仍由外置 `KnowledgeRepository` 持有。

### UnitOfWork：同库原子命令

`UnitOfWork.run` 是中立事务端口，由 PostgreSQL 适配器提供一组绑定同一连接的 Task/Document/Relation/Schedule Store、操作去重记录与 outbox 访问入口。core 在这个作用域内重验对象版本、当前权限和采纳状态，再一并提交相应对象、关系和待发意图；不暴露 SQL 或 `pg.Client` 给 core，也不允许各 Store 单独提交。事务内只处理本库状态，网络读写、模型调用和外部发布放在提交前准备或提交后执行。

操作 ID 与命令摘要一起去重，同一 ID 带不同命令必须拒绝；提交结果未知时按该 ID 查询同库事务结果。首片验证最后一步失败时全部回滚、提交成功但回包丢失后恢复不重复创建，以及旧基线更新被拒绝。该合同仍待实现，数据库选型本身不是测试通过证据。

## 3. EvidenceStore 与 KnowledgeRepository

`EvidenceStore` 登记和定位原始材料：`sourceId`、项目、原件位置、片段定位、内容校验、来源类型、观察时间/记录时间、可见范围和撤回状态。原件可以仍在原始归档或受控材料存储；正文页里的引文和搜索索引都不是原件。取不到原件时返回“依据不可访问/已撤回”，不能从旧摘要补造证据。

`KnowledgeRepository` 面向开发仓库外的 Wiki/知识空间，至少表达：提交材料或候选知识变更；按项目/主题查找；读取当前页及指定修订；标明主张是观察、推断、假设、已采纳决定、争议还是已失效；列出来源与被其支持的知识页／主张及内部依赖；提出修订与发布；导出固定修订的只读视图。跨 Wiki 与 Task／Document 的关系在 PostgreSQL `RelationStore`，不由 Wiki 维护第二份任务关系权威。每个受管项目有独立知识命名空间。底座若只能搜索并生成答案，应如实标记未支持这些维护语义。[方向出处](../references/lineage.md)

贡献与发布分开：业务 session 提交“旧判断、观察与片段、解释/反例、建议范围”，Wiki 维护者负责与现行页综合、保留相反解释、处理过时链接和影响任务。新来源时间更晚不自动成为更正确的结论。来源撤回触发依赖查找及复核；受影响页先标待审，不能仅删除源记录就假定综合正文同步正确。决定的权威来自人类或授权范围内的责任者，不来自模型语气。

专门认知 session 初期可同时承担 Wiki 综合维护；其项目判断和下一步选择通过任务与阶段约定落实，KnowledgeRepository 不因存储了一个建议而自动批准或执行该建议。Wiki evaluator 的产品验收范围见[建设与有效性评价](../product/wiki-evaluation.md)。

页发布须声明读入基线与操作 ID。当前选型未能承诺可靠的页级条件写；在受限试点中采用单维护者串行发布、发布前回读与快照，旁路写入视为必须对账的风险。只有固定版本证明服务器确实拒绝旧基线写入，才可宣称多维护者安全发布。两候选的已观察结果见[验证摘要](../references/validation-summary.md)；当前未选正式后端。

`BlobStore` 管理仓库外受控原件的准备、按 hash 核验、发布读取与撤回；PG 只登记 blob 引用。发布顺序和恢复边界见[存储设计](storage.md)，PG 事务不覆盖文件系统。知识查询还须提供带权限和固定 revision 的类型/专题分页、正文、来源、出链/反链和有界邻域，详见[Wiki 前端模型](wiki-workspace.md)；这些是适配器需支持或明确报告缺失的合同，不假定 OpenViking 已有对应实体/API。

发布批准绑定不可变候选修订/hash 与所读知识基线；outbox 实际执行或重新写入前再核批准、权限、来源有效性与独占资格。已发出但结果未知的操作先对账，批准后来撤销不代表先前写入未发生。审阅结案可以是拒绝、归并或无需修改；只有接受并确需改正文的项才要求另有发布回执，结案和发布保持分离。具体时序见[Wiki 集成](wiki-integration.md#6-命令发布和纠正)。

## 3a. DocumentSource、SourceBridge 与 ContextQuery

`DocumentSource` 是外部文档读取端口：按已登记仓库、白名单路径及固定 commit 读取原始字节，返回内容校验、权限/可达性与来源状态；观察指定分支变化只产生候选修订，不自动采纳。首个实现为 Git 文档适配器。仓库路径移动须显式维持 documentId 映射；无法确定身份则待复核。正式 HTML 视图不另作独立来源。Git 端口不代替原仓库的修改与审阅流程。

`SourceBridge` 用例组合 Task/Document 固定修订、DocumentSource 和 EvidenceStore 读取，将选定材料交给外置知识空间。最少关联项目、原对象/修订、片段、内容 hash、来源采纳/撤回状态、权限策略版本、转换器版本和目标空间；据此去重并保留外部 sourceRef/处理回执。权限检查覆盖原件、摘要与目标可见范围。PG 保存传递映射，Wiki 保存来源内容及内部依赖；资料已送达、索引可用、知识已维护分别观察。来源变化触发影响复核，不能因入库成功就改 Task 或需求的接受状态。

`ContextQuery` 为人或 session 装配有限上下文：Task 固定执行依据、需求修订、Git commit、Knowledge 修订、当前变化/反例、真实使用结果及缺项。返回每项权限、读取时间、修订与校验，区分当前对象导航和历史依据；不得补造无法读取的来源。跨系统没有共同快照事务，精确引用组合不等于全局同时一致。上下文送达只证明传递，使用/采用由后续产物证据判断。

Task 接受和 Run 派发固定到不可变 TaskRevision 及依据集合；更新当前任务不改旧 Run 的依据。派发前复核权限、业务接受状态和重要来源/知识有效性，已撤回或待复核依据不得因后台扫描尚未完成而继续无条件使用。无法核对外置修订时报告缺项；跨系统检查后仍可能变化，不能宣称跨系统线性一致。具体表与约束见[存储设计](storage.md)，传递、反向影响和例子见[知识关联](knowledge-flow.md)。

## 3b. 工作台 Query / Command 合同

工作台、CLI、Agent 工具和 connector 共用领域命令。QueryService 只装配已授权的对象和关系，返回固定修订、当前版本、分源状态与缺项，不把搜索摘要当权威正文。Command 包含 operationId、行为者、项目、预期版本和变更意图；权限、状态和基线由服务端 core 在提交时核验。同一 operationId 的命令摘要不一致则拒绝。

浏览器保存新草稿不自动采纳它；已采纳的版本指针由显式决定和条件更新改变。发生冲突保留输入并返回可复核的当前版本；结果未知按 operationId 查询，而不是换 ID 重发。UI 分别呈现业务、运行、同步、知识和效果状态。刷新提示只要求回读，不能直接推进状态。前端结构与范围见[前端架构](frontend.md)。

## 4. RoleRegistry 与 SessionRuntime

`RoleRegistry` 记录逻辑责任的稳定 ID、目标、范围、主要输入、可写资产、交付、触发条件、与其他 Role 的交接、试行状态和修订。Role 可处于候选、试行、活跃、调整中、撤回；这描述职责约定，不是 session 运行状态。一个 Role 可有先后多个 Session 或经批准的并行实例。会话换窗、上下文压缩、模型替换都不自动变成新 Role。

`SessionRuntime` 的能力按实际宿主逐项声明：创建/继续、查询状态、发送已授权任务、读取回复/产物、请求停止、恢复关联；某能力不存在就返回 unsupported。发送消息或唤醒并不等于接收、执行、完成。不能凭“创建请求已发出”就登记为已运行。运行时身份映射保留 `roleId ↔ sessionId ↔ taskId` 的时间范围和来源；同一任务因续做换 session 时保留交接链。

分工管理者能读取任务负荷、结果、使用反馈和 Wiki 缺口，提出替代动作：改方法/工具、同职责增实例、临时专项、新 Role、合并或撤回。提案进入 TaskStore，不在 RoleRegistry 中直接悄悄改正式约定；试行含目标、成本、效果观察和退出条件。所有 session 可提出，分工管理者不控制全部业务任务。[方向出处](../references/lineage.md)

每个新 Session 引用当前职责说明或临时任务约定，补充实例目标、输入修订、首项任务、操作范围和交接/退出条件。新 Role 另附缺口证据、替代办法、独立责任与工作流程、试行基线和回看条件；换窗口仅更新实例关联。撤回 Role 时交接未完任务与知识、停止相应触发并核对在途实例，不能仅更改登记状态。流程见[动态多 session](../product/agent-loop.md)。

## 5. Coordinator：派发、交接与恢复

协调者消费 PostgreSQL 中 TaskStore 当前状态和 RoleRegistry 约定，按已授权规则选责任者，再调用 SessionRuntime；它不作知识真值或产品价值的最终裁决。最小运行记录保留：任务/Role/Session、派发操作 ID、预期动作、请求时间、运行时回执、最近已知状态、检查水位与下一次核对时间。业务 Task、外部同步 Sync、运行 Run 和效果 Review 各有状态，不合并成一个“完成”；运行状态可为待派发、派发中、运行中、待交付核对、结果未知、需人处理，实际名称待实现。

一次派发超时的恢复顺序是：按操作 ID 回读 PostgreSQL 中的任务、Journal 与 outbox → 查运行时是否有对应 Session/动作 → 需要外部协作投影时另查 connector 绑定和同步结果 → 能证实已派发则继续跟踪，能证实未派发才重发，仍不明则保留 `unknown` 并暂停重复执行。飞书投影同步成功不是默认派发前置条件；只有任务目标明确要求远端可见或远端协作时才按判据等待。重复创建、通知和外部副作用各自需要可查询的去重依据；TaskStore 的幂等键不能替代运行时幂等。重启先对账未结束动作、未复核交付和未决外部同步，之后才派发新任务。

通知最少区分“已请求发送、平台已接受、接收者已读/可处理、处理完成”；运行时只提供到哪一层就记录哪一层。没有投递或消费回执时保持未知，不能把请求 200 解释为受托人已醒来。对方完成后，责任者核对成果修订、检查结果和是否满足验收，再更新任务。阶段亲用另行记录，不能被技术检查通过自动替代。

## 6. StageReview：从交付到下一阶段

每个阶段记录目标、交付判据、预期使用效果、必须弄清的未知、责任者和读入的知识/正式文档修订。阶段结束关联实际交付、真实使用过程、用户反馈、失败/反例、成本、改变或保留的认识、下一阶段任务与 Role 试行建议。若只有产物没有亲用或效果证据，结果是“交付已完成、效果未知”；不填零或成功。

下一阶段工作应能追到上一阶段的判断及其来源；相关知识修订若被推翻，未执行任务标待复核。读取端只取与当前任务相关的页和关键反例，再下钻原料，不把整套 Wiki 当作无条件提示词。是否改善要与直接读取原材料等可比基线对照，记录编译、维护、读取和纠错的总成本。

回看结果应形成继续、补证、修订、暂缓、结束或请求具体取舍的选择，关联目标、依据修订、预期观察、责任和资源范围。已授权且满足接受条件的行动进入 TaskStore；没有新证据或有价值动作时允许等待/结束。阶段回看可由交付、使用反馈、来源变化或约定周期触发，触发成功不等于认知已完成，任务提交也不等于已执行。

## 6a. EvaluationRecord：评价证据与条件

评价是有来源的工作记录，`core/evaluation` 使用现有 Task/Run/Delivery/Review 与证据引用组织它；不新增一个独立模型执行系统。`EvaluationRecord` 至少包含 evaluationId、项目、协议/评分规则固定引用、任务族、来源包与可见性边界、候选实现/知识修订、模型/工具/预算条件、条件差异和创建者。被比较的材料组与 Wiki 组保留各自条件，条件变化产生新修订而非覆盖旧成绩。

每个 `EvaluationCase` 关联固定 TaskRevision、实际 Run/消费 session、输入修订、首次产物及重试、追源/人工介入、确定性检查和独立评审。`ConsumerOutcome` 分开记录知识采用、交付合格、真人效果与成本；值可为已观察、未观察或待复核，缺失不折算为零或通过。消费者不能得到尚未开放的答案与评分反馈；权限检查覆盖产物和逐 case 详情。

PG 保存这些记录、决定和固定引用；大原件按 EvidenceStore/BlobStore 定位，活 Wiki 正文仍外置。页面返回逐 case 证据与局限，汇总须标分母、失败/重试、未知和条件差异。评价结果先形成 ReviewDecision 或维护/补证提议，经同一任务接受规则推进；不能因为自动评分较高就自动采纳知识或关闭阶段目标。评价设计见[产品评价约定](../product/wiki-evaluation.md)。

## 7. ScheduleStore 与触发实例

这是定时任务的拟议合同；不表示已创建任何真实定时器。`ScheduleStore` 的日程定义及触发实例以 PostgreSQL 为权威，飞书日程视图若提供则只是 connector 投影。日程定义回答“何时、为何检查或做事”，具体工作仍进入同一 TaskStore；实现前验证时间计算、权限和外部映射。

| 对象 | 身份与语义 |
| --- | --- |
| Schedule | 稳定 `scheduleId`、项目、责任 Role、目标/任务模板、一次性时点或重复规则、IANA 时区、有效期、启停状态、修订、授权/资源范围、错过策略、重叠策略与再看/结束条件。 |
| Occurrence | 一次计划时点的触发实例，关联 `scheduleId`、定义修订、计划 UTC 时点、实际观察时间及任务 ID。相同 `scheduleId + plannedAt` 对应同一稳定触发键，修订号作为被观察基线，避免仅改描述就重复执行相同时点。 |
| 运行记录 | 到期水位、创建任务意图及回执、是否跳过/汇总、关联 Run、unknown 与对账结果；保存在 PostgreSQL Journal，仅用于恢复，不替代 Task／Schedule 主数据。 |

触发流程为：读现行有效日程 → 按时区计算到期 → 核定义修订、授权、积压和在途实例 → 记录稳定触发意图 → 创建/关联独立任务 → 按同一接受和派发规则推进。已授权的重复常规工作可沿用模板判据；运行中发现的新功能需求仍走提议判断。周期完成不能反复覆盖同一任务行，历史每次产物/成本可查。定时器响起不会直接等价于 `SessionRuntime.run`。

错过规则明确选择跳过、只补最近一次、汇总或有上限地补跑；禁止停机很久后无限补发。重叠规则明确选择等待、合并或已验证可并行，默认同一逻辑任务串行。没有新事实时，轻量检查只记录检查水位和“无需动作”；真正派发了检查工作就保留相应任务与运行记录，不能删掉无发现或失败运行来美化成本。

日程变更先核对旧修订尚未派发的实例；暂停默认只禁止后续触发，已运行任务按各自合同处理。要停止在途工作需显式产生停止操作并核实际结果。恢复或改时间后重算下一时点；重复事件、时钟回拨和重启不得仅凭触发次数新建工作。创建任务结果未知时先按稳定操作键查 PostgreSQL 事务记录；外部投影不明时再查 connector 绑定并对账，无法排除已有外部副作用就保留 unknown；没有跨系统恰好一次保证。

计划触发和 Codex 桌面产品自动化分别有宿主。首期只有一个自动调度权威，不同时为同一日程注册两套定时器。[定时产品行为](../product/daily-loop.md) · [Codex 映射](codex-integration.md)

## 7a. Connector 与 ExternalBinding

`Connector` 把内部对象投影到外部协作系统，并把外部允许的编辑转为内部 command；它不改变本体的权威。`ExternalBinding` 至少保存内部对象 ID／修订、外部平台和远端 ID、字段与身份映射、同步方向、最近已确认的双方基线、操作 ID、同步状态、冲突与解除状态。一次外部删除、失联或重建不删除 PostgreSQL 本体；按配置修复投影、暂停或解除绑定，保留历史与人工可核依据。

飞书第一切片仅承诺 Bitable 的**任务投影**。出站：主数据变更与 outbox 意图可在同一 PostgreSQL 事务提交；worker 写远端后回读确认并推进同步状态。PG 提交不等于飞书已更新，外部请求超时仍可能已经生效，按绑定与操作证据对账，不能盲重试。入站：事件只作提示，回读真实远端记录，将受支持字段的变更连同外部身份、远端基线送入 core；core 校验权限、当前内部修订和合法状态转换，冲突保留待决，不使用“最近写入者赢”。来源标记、操作 ID 与双方基线用于防回环；分页、乱序和漏事件由水位与周期对账补齐。飞书 Docs 正文若要接入，是另一种文档 connector 和 API 验证，不可从 Bitable 任务投影推断已有正文双向同步。

`Sync` 状态与 Task、Run、Review 状态独立；投影失败不回滚已提交的任务本体，也不默认阻断已授权运行。外部协作本身属于验收判据时，任务需明确要求相应远端可见性与回读证据。同步冲突、解除绑定、远端撤回和权限变化都写 Journal 供对账；不得把飞书当第二个可直接修改的任务权威。

## 8. 合同验收与尚未承诺的保证

第一条端到端试点至少贯穿：来源入库 → 两个 session 的相反解释 → Wiki 维护修订 → PostgreSQL 任务引用固定修订并执行 → 飞书投影与入站协作对账 → 交付后的实际亲用 → 依据效果形成下一任务/职责试行。随后演练文档旧基线写、同基线 Wiki 写、任务出站成功但丢响应、飞书入站冲突与投影删除、来源撤回、协调者重启、知识恢复及新 session 独立消费。每项报告要分开记录“原生能力、官方 Skill/模型行为、项目适配、人工操作、尚未观察”。

当前没有证据可承诺飞书事件完整投递、跨平台恰好一次执行、外部投影立即一致、OpenViking 0.5.0 安全多写者发布、源撤回自动修正全部页、可靠通知送达或 Wiki 比直接材料更高效。PostgreSQL 内部事务与条件更新还没有实现验证；不能把拟议合同描述为已运行保证。任何实现只能在验证后的边界内向上暴露能力；升级后重新跑相应案例。更细的测试和代码约定见[开发规范](../development/standards.md)。
