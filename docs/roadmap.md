# 阶段路线与当前状态

2026-10-25。阶段划分是当前实施建议；进入下一阶段取决于验收证据，尚无承诺日期。已实现切片的任务状态由本机 evoLoop/PostgreSQL 管理；飞书协作入口仍待接入。本页汇总能力阶段、已验证范围和进入条件。

**先理解目标体验，再选择当下工作。** [产品旅程 J1—J6](product/definition.md#从一个目标走到第一次有效交付)描述未来使用者从目标到首次有效交付及下一步；本页 M0—M4 描述 evoLoop 自身的实施阶段，两者不是同一套编号。下面的文档调查示例可在当前仓库执行，但不代替目标产品的首次接入体验；它也不证明旅程已运行。

## 完整目标与证明顺序

**最终要改变的是项目推进方式：**负责人给出目标、约束与关键取舍后，现有责任 session 能依据真实材料提出有边界的下一步，任务在开始时固定实际采用的主正文、需求和认识，由有权者承接并交付；目标消费者实际使用成果，反馈和反例再修订判断、受影响任务与下一动作，必要时补证、转向或停止。项目在换 session、丢回执和需求变化后仍能接续，负责人不必反复粘贴背景、传话和催促。两次相连的“行动→亲用→认识变化→下一动作”及第二次对前次证据的实际采用，是检验持续接续的目标；任务数、自动运行时长和 Wiki 页数不是替代指标。完整行为见[产品定义 J1—J6](product/definition.md#从一个目标走到第一次有效交付)与[P07](product/definition.md#p07--认识能够自主接续下一步)。

价值按三层核对：**基础可信**是身份、固定版本、权限、事务和恢复使一次选择可追；**首次有效交付**是领域工作经技术检查并被目标消费者沿原路径使用，结果可回到判断；**持续收益**是后续 session 正确采用纠正、减少重复提醒或遗漏，职责按真实负担试行且能退出，外置 Wiki 在可比任务中比直接读材料更有用或更省总成本。后一层必须有独立使用观察，不能由前一层的工程检查推定。少量材料直接可读时，不强制先建 Wiki 或新 Role。

S1a 只证明第一层的一小段：已采纳需求改版能让两个尚未运行的任务保留旧依据并分别作新旧基线选择，失败后仍可查决定。它尚未证明任务真正执行、交付被亲用、认知改变下一步、Wiki 有效、动态分工有收益或项目可持续运行。每次扩片均应选择能连接上一层到下一层的真实使用场景，记录预期、观察和反证；未发生的效果保持未知。

### 2026-10-24 有界使用核对

修复闭环中，认知读取固定 issue 与事故报告后创建真实修复工作；业务 Agent 提交实际代码改动与固定报告，独立负责人代理沿原关闭入口复测，并将使用结果留在共同记录中。后续认知实际读取该反馈和原报告，关闭原 Task 并选择等待。owner 可以申请关闭自己有权审阅的业务 Session，原生归档仍使用原 Session 的执行身份，不能借关闭权限取得新运行权限；同一关闭操作的 HTTP 重放、无权限和旧版本拒绝分别核过。该闭环发生在恢复后的新有限预算中，不重建事故丢失的尾部操作，也不把旧中断试用改记为通过。

周期试用使用同一 Schedule 的有限窗口：第一期实际执行、报告被负责人代理使用，反馈认知关闭原任务；业务真实在途时另一个获准到期槽因 overlap 跳过，暂停日程后同一业务 Run 自然完成。暂停超过五分钟且原任务已使用、已关闭后，再恢复一个到期槽，第二期认知实际读取前期报告原文与使用反馈，再更新并派发该槽生成的原 todo。最终账为两项 created、一项 overlap skipped、零 queued；两期报告均被负责人代理实际使用，反馈已关闭两项原业务任务。9 个 Run 全部完成，各自 Session 均核实原生归档；本轮 10 项 Task 为 7 项 done、3 项 cancel，取消记录未冒充判断通过。负责人代理关闭验证任务、回看阶段并选择 stop，Schedule 与 Loop 均已停止，服务调度保持关闭。

收束中曾真实拒绝一项原认知任务关闭：PostgreSQL 关闭读取漏掉日程的可信来源。PR61 补齐原来源核验后，同一原任务通过正常命令关闭；旧拒绝保留，没有另造运行或修改数据库伪造成功。该修复维护窗口未迁移 schema，核过备份、既有业务表和身份；进程内通用错误提示重启后变空，单列为诊断变化，不据此宣称历史错误根因已解决。

读取证据也分层记录：完整响应下载且哈希一致、完整正文实际出现在模型工具结果中、消费者理解并采用内容，分别需要证据。第二期结果认知的一次原件响应被完整保存，但展示给模型的正文被截断，全文语义消费未证；后续反馈认知的工具结果包含完整正文，负责人代理自己的完整阅读与采用收口清单另有独立记录。这些有限证据不证明全天日程可靠性、Wiki 比较收益、真人体验或生产服务可用。

第二条组合旅程整体尚未通过。后续独立负责人代理已沿正常工作台路径读回修复任务、固定交付与使用记录，以及日程修订、发生记录和对应任务链；这些前端读回不增加一次业务使用。业务 Session 的浏览器接入仍未验，局部修复闭环和两期 Agent 使用不能替代整体验收。

## 当前阶段的一个小任务

**示例：定位一次“看完材料仍找不到下一步”的阻塞，交付一项最小修复建议及验收。** 这是任何阶段都可执行的有界调查，不要求先接通全部业务服务；实际任务需取得具体反馈，不能把示例当成已创建或完成的工作。

| 要素 | 本轮边界 |
| --- | --- |
| 交付目标 | 找到一个具体阅读/决策阻塞，交付证据支持的原因判断，以及一项能独立开工的修复任务说明。 |
| 学习问题 | 阻塞来自入口/表达、缺依据、未接通能力，还是目标尚未明确？哪一个观察能区分这些解释？ |
| 输入 | 固定文档/原型版本、使用者想完成的事、原始入口与操作路径、卡点和期望；涉及纠正时还需纠正原意与授权范围。当前任务承接这些输入；已接通的对象可在 evoLoop 登记，尚未接通的场景仍由任务/PR 保留证据。 |
| 动作 | 复核这一条路径；比较至多三个有依据的解释，标出支持与反对观察；选择一项最小可回退修复，说明暂不做什么。 |
| 交付与验收 | 给出失败位置、固定来源、判断及未知、被选修复的目标/责任范围/产物/实际使用判据。由未参与整理的消费者核对“证据是否支持该选择、输入是否足以开工”；缺必要事实时只交付受限判断和补证项，不虚构原因。 |
| 停止条件 | 到一个阻塞的判断和下一项工作说明为止；本任务不同时实施修复、接通全部系统或证明整个阶段效果。无值得推进的修复时，保留补证/暂停/停止理由。 |

后续若接受修复，另按其具体范围实施并让目标消费者重试原路径；再由[阶段回看](product/daily-loop.md#阶段交付后怎样选择下一步)决定认识和下一动作怎样改变。该调查验收、修复验收和阶段效果分别记录。已明确、在现有职责与授权内的纠正可由领域 session 并行修复，不必等待这个调查或中心逐项批准。人员实例、权限和预算来自实际工作，不在长期路线页预设。

## 如何更新本页

能力完成须附对应提交、运行结果和验证范围；不能只因文档写好或任务被标完成就改变状态。阶段失败可能产生新的判断或缩小范围，把原因与下一动作记录清楚即可。具体执行见[开发规范](development/standards.md)。
