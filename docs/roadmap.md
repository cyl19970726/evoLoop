## 完整目标与证明顺序

**最终要改变的是项目推进方式：**负责人给出目标、约束与关键取舍后，现有责任 session 能依据真实材料提出有边界的下一步，任务在开始时固定实际采用的主正文、需求和认识，由有权者承接并交付；目标消费者实际使用成果，反馈和反例再修订判断、受影响任务与下一动作，必要时补证、转向或停止。项目在换 session、丢回执和需求变化后仍能接续，负责人不必反复粘贴背景、传话和催促。两次相连的“行动→亲用→认识变化→下一动作”及第二次对前次证据的实际采用，是检验持续接续的目标；任务数、自动运行时长和 Wiki 页数不是替代指标。完整行为见[产品定义 J1—J6](product/definition.md#从一个目标走到第一次有效交付)与[P07](product/definition.md#p07--认识能够自主接续下一步)。

价值按三层核对：**基础可信**是身份、固定版本、权限、事务和恢复使一次选择可追；**首次有效交付**是领域工作经技术检查并被目标消费者沿原路径使用，结果可回到判断；**持续收益**是后续 session 正确采用纠正、减少重复提醒或遗漏，职责按真实负担试行且能退出，外置 Wiki 在可比任务中比直接读材料更有用或更省总成本。后一层必须有独立使用观察，不能由前一层的工程检查推定。少量材料直接可读时，不强制先建 Wiki 或新 Role。

最早的 S1a 切片（10 月下旬）只证明了第一层的一小段：已采纳需求改版能让两个尚未运行的任务保留旧依据并分别作新旧基线选择，失败后仍可查决定。它当时没有证明任务真正执行、交付被亲用、认知改变下一步、Wiki 有效、动态分工有收益或项目可持续运行；此后哪些在旧机上有限验证、哪些在新实例上还没有记录，见[当前基线](#当前基线)。每次扩片均应选择能连接上一层到下一层的真实使用场景，记录预期、观察和反证；未发生的效果保持未知。

**谁在做事。** 新实例上有两个试行 Role，都从 11-09 开始试行，11-23 回看去留：

**编制怎样变。** 按 [DEC-038](decisions.md)，同一 Role 加不加人由 Leader 根据每日评估决定，一次只增减一个 Session；上一次增加的实例有被接受的交付后，才加下一个；每次判断给出"补人""先拆开""必须等"之一，写明可并行项和当前上限，过度并行算作风险。新的长期 Role 仍由 Evocation 凭证据提出。

**11-09 的编制判断。** 11-09 与使用者讨论时判断，现阶段合适的上限是 Leader 1、Dev 不超过 3、QA 1：在 #229 前端工作进入派单前先加一个 QA，进入派单时再判断要不要第二个 Dev。这是当时的判断，不是规则，下次评估可以改。新实例上目前没有 QA Role，加 QA 有两种做法，还没有定：按 DEC-038 由 Evocation 凭证据提出并试行 QA Role，之后同 Role 加人才由 Leader 决定；或者由 Leader 指派一个不是作者的业务 Session 承担验收。截至本页更新，QA 还没有加。

**还没接上的部分。** 每日评估的 Schedule 尚未配置（新实例上 0 个 Schedule），评估目前由人发起；两个 Role 还没有试行回看记录，到期日是 11-23。

## 阶段及进入条件

| 阶段 | 要交付什么、依赖什么 | 退出证据与失败时的处理 |
| --- | --- | --- |
| M0 正式定义与仓库 | 产品目标、架构边界、规范、决定和可重建文档站；供后续切片共用同一判断依据 | 新 checkout 能重建，未参与编写者能按文档解释一个目标→任务→使用→下一步的场景并定位边界；误解进入修订，不用页数宣布完成 |
| M0.5 技术与包边界确认 | 为首片选定栈、共同 API、主数据/外部正文权威和进程依赖；OpenViking 0.5.1 的已测读写与未测语义索引、生产部署分开记录 | 选择、替代与代价可追，实际包依赖不越界；证据不足时缩小实现范围或保留候选，不为填架构图预造能力 |
| M1 任务与单次交接 | 在一个已有或新建项目中明确目标、阶段交付、学习问题、消费者和授权，接受有界任务；固定 Task/Document、Git 引用、真实运行时和恢复已在旧机上试用，飞书投影另行延后 | 一条 dogfood 修复/需求改版任务从接受基线走到真实交付与目标消费者使用；重复请求、结果未知和重启可查可恢复。若仅数据库或页面通过，保留为切片成果；若交接/亲用失败，记录责任、缺项与返工，不宣布 M1 完成。飞书实连不作为当前试用退出条件 |

| M3 分工管理试行 | 在已观察的遗漏、返工、切换或负担上比较改方法、续开会话、临时专项和新职责；同 Role 补实例由 Leader 按每日评估一次一人地决定（DEC-038），仅持续独立缺口才试行新 Role | 试行记录责任边界、首项工作、原基线、成本和退出条件；相近工作中核实际遗漏、等待、返工与维护成本。收益不成立就调整或撤回，并交接未完任务，不因创建角色判成功 |
| M4 持续使用与发布 | 将 S3 到期/重叠/暂停恢复与 S4 知识使用纳入受管项目试点；建立常在线运行、备份/回退、文档发布和可观察的日常入口 | 至少两次相连的行动、亲用、认识变化与下一动作能互相追证；日常讨论与定时检查不漏、不重、不造空任务，真实使用、成本和用户反馈经阶段回看后再扩大。若可靠性或净收益不足，缩小试点、补恢复或停止该路线；不以部署在线代替产品有效 |

M1 和知识候选补验可以做独立准备，不能因此把 M2 的业务收益视为已证实。M3 的职责定义可提前讨论，但实际收益必须经过试行。正式线上发布需有可用的运行与回退方案。

四部分不按四个互不相干的工程验收。M2 的最小闭环需让当前 session 形成并整合认识、经任务机制承接、实际使用并影响下一动作；已有职责可先承担工作，M3 再评价是否需要拆分新 Role。整体验收以产品 P07 的两次相连循环为目标，同时允许依据效果停止或转向。

| 首期工作台整体 | 从 M1→M2 接通基础与知识切片，再沿 M3 验证职责试行、M4 验证真实定时与持续接续，最终贯通[工作台六条路径](product/workbench.md#六条端到端使用路径)及各自验收 | 一个页面、原型按钮或其中一条路径通过，不代表整个工作台可用，也不证明在手机等其他设备上可用（常驻主机已有 HTTPS 入口，另一设备上的检查尚未完成）。 |

实施切片沿用[包架构 S1—S4](architecture/packages.md#切片与验证)：S1 的主数据、S2 的受控编辑/执行恢复、S3 的日程、S4 的外置知识是工程切片，不另立产品阶段。旧机上已接通 J1—J3 的目标、阶段、提议与接受，Git 固定来源、真实运行时、结果回查、日程和 Wiki 候选发布（新实例未部署 Wiki，见[当前基线](#当前基线)）；J4 的两轮相连交付、独立 Agent 消费与原生终态对账在旧机上已有受限实测；真人亲用、可比较成本和持续收益仍需证据。飞书出站/入站实连已延后，恢复验证留在其独立接入范围。**只有 M1 当前约定的交接与消费范围经过验证，才宣称 M1 完成。** M2 还须证明知识纠正实际影响后续行动，并与直接读材料比较；图谱等后置项沿用[工作台分期](product/workbench.md#分期与整体完成判据)。这里澄清完成单位，不把工程可用推定为产品效果。

## 当前阶段的一个小任务

**示例：定位一次“看完材料仍找不到下一步”的阻塞，交付一项最小修复建议及验收。** 这是任何阶段都可执行的有界调查，不要求先接通全部业务服务；实际任务需取得具体反馈，不能把示例当成已创建或完成的工作。

| 要素 | 本轮边界 |
| --- | --- |
| 交付目标 | 找到一个具体阅读/决策阻塞，交付证据支持的原因判断，以及一项能独立开工的修复任务说明。 |
| 学习问题 | 阻塞来自入口/表达、缺依据、未接通能力，还是目标尚未明确？哪一个观察能区分这些解释？ |
| 输入 | 固定文档/原型版本、使用者想完成的事、原始入口与操作路径、卡点和期望；涉及纠正时还需纠正原意与授权范围。当前任务承接这些输入；已接通的对象可在 evoLoop 登记，尚未接通的场景仍由任务/PR 保留证据。 |
| 动作 | 复核这一条路径；比较至多三个有依据的解释，标出支持与反对观察；选择一项最小可回退修复，说明暂不做什么。 |
| 交付与验收 | 给出失败位置、固定来源、判断及未知、被选修复的目标/责任范围/产物/实际使用判据。由未参与整理的消费者核对“证据是否支持该选择、输入是否足以开工”；缺必要事实时只交付受限判断和补证项，不虚构原因。 |
| 停止条件 | 到一个阻塞的判断和下一项工作说明为止；本任务不同时实施修复、接通全部系统或证明整个阶段效果。无值得推进的修复时，保留补证/暂停/停止理由。 |

后续若接受修复，另按其具体范围实施并让目标消费者重试原路径；再由[阶段回看](product/daily-loop.md#阶段交付后怎样选择下一步)决定认识和下一动作怎样改变。该调查验收、修复验收和阶段效果分别记录。已明确、在现有职责与授权内的纠正可由领域 session 并行修复，不必等待这个调查或中心逐项批准。人员实例、权限和预算来自实际工作；现在的编制见[当前组织](#当前组织)，本页不预设以后的编制。

## 如何更新本页

能力完成须附对应提交、运行结果和验证范围；不能只因文档写好或任务被标完成就改变状态。[当前基线](#当前基线)的三列分别更新：合入后填"已实现"，新实例上出现真实记录后填"用过"，约定的验收者签署后填"已验收"；发布新版本时同步改"运行在哪里、是哪个版本"。编制变化写进[当前组织](#当前组织)，并注明依据的评估。按日的实施与验收过程留在 Task 和过程 Document 中，需要长期保留的阶段性记录追加到[路线图历史](references/roadmap-history.md)，不再堆在本页。阶段失败可能产生新的判断或缩小范围，把原因与下一动作记录清楚即可。具体执行见[开发规范](development/standards.md)。
