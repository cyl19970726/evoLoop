# 阶段路线与当前状态

2026-10-20。阶段划分是当前实施建议；进入下一阶段取决于验收证据，尚无承诺日期。任务执行状态未来由 evoLoop 管理，飞书为协作入口，本页只汇总能力阶段和进入条件。

**先理解目标体验，再选择当下工作。** [产品旅程 J1—J6](product/definition.md#从一个目标走到第一次有效交付)描述未来使用者从目标到首次有效交付及下一步；本页 M0—M4 描述 evoLoop 自身的实施阶段，两者不是同一套编号。下面的文档调查示例可在当前仓库执行，但不代替目标产品的首次接入体验；它也不证明旅程已运行。

- 产品定义已按“认知演进／协作执行”两个维度与四部分补充；[Agent loop](product/agent-loop.md)和[Wiki 评价](product/wiki-evaluation.md)明确了下一步选择、分工流程、状态与验收设计，尚未运行整体闭环。
- OpenViking 与 nashsu/llm_wiki 的隔离小样本验证已完成，发现真实缺口；[摘要](references/validation-summary.md)记录版本与范围。
- 本轮建立正式产品、架构、开发规范及文档构建脚手架。具体仓库检查以提交对应的 CI 和本地检查结果为准。
- 尚无 evoLoop 业务 harness、正式飞书任务适配或生产认知库；未接入真实项目的持续协作。
- 已补 dogfood/需求判断、日常讨论和定时任务的产品约定，以及包架构与 Codex 接入设计；独立 [PR #2](https://github.com/cyl19970726/evoLoop/pull/2)进一步验证了自管线程的隔离夹具闭环和桌面宿主通知消费，尚未成为本分支已合并的生产适配器。
- [技术选型](architecture/technology-selection.md)已确定 PostgreSQL 项目主数据与运行存储方向，飞书改为 connector；任务/需求文档与 Wiki 的版本关系进入正式设计；TS/Node 核心、OpenViking 服务及具体部署仍待确认，v0.5.1 尚未实测。
- 已补[工作台产品](product/workbench.md)、[前端](architecture/frontend.md)、[存储](architecture/storage.md)和[知识关联](architecture/knowledge-flow.md)设计；可点击原型使用示例数据，尚无业务工作台。
- 已按固定 nashsu 源码形成[逐模块复用边界](research/nashsu-llm-wiki/frontend-reuse.md)和[Wiki 集成方案](architecture/wiki-integration.md)，并按完整产品路径[审阅原型](research/workbench-prototype-review.md)。纯函数、组件适配与桌面流程分别处理；当前未复制上游源码、接通服务或证明实际效果。

## 阶段及进入条件

| 阶段 | 要交付什么 | 要弄清什么 | 结束时怎样使用与判断 |
| --- | --- | --- | --- |
| M0 正式定义与仓库 | 产品、架构、规范、决定和可重建文档站 | 新读者能否理解目标与边界，Agent 能否找到当前合同 | 干净安装并重建；按文档定位一个场景及其实现边界；记录阅读反馈 |
| M0.5 技术与包边界确认 | 推荐栈、工作台页面与 API、存储约束/知识来源链、Wiki 固定候选/改造边界、包与进程依赖 | 维护哪些代码，复用哪些能力，证据和成本是否足以选择 | 记录选择与理由；核心包、外部权威、版本和许可范围可解释；未验证能力保留门槛 |
| M1 任务与单次交接 | 一个项目的 Task/Document 主数据、固定基线、工作台读取/提议/复核、Git 引用、飞书 connector、一个运行时 | 需求版本、任务基线与外部编辑能否一致地接续工作 | 完成一条 dogfood 修复与需求改版后的任务复核；核飞书投影/冲突；接到真实 Codex 并验收；模拟丢通知、重复请求和未知结果后恢复 |
| M2 认识改变后续行动 | 外置 Wiki 的贡献、维护、查询、修订与来源关系 | 用户纠正/反例是否真正影响新会话，代价是否值得 | 分批加入纠正，新的 session 完成任务；与直接材料读取比较；验证并发边界和恢复 |
| M3 分工管理试行 | 按证据提出并执行一次职责调整，或有理由维持现状 | 新分工是否改善持续责任，收益是否抵消交接成本 | 在相近任务中观察遗漏、返工、切换、提醒及维护成本，决定保留/修改/撤回 |
| M4 持续使用与发布 | 受管项目试点、文档子域名、运行与备份办法 | 长期材料增长和真实使用下是否可靠、可维护 | 真实阶段使用、日常两类讨论、定时检查的重叠/漏触发/暂停和恢复、成本与反馈复盘后再扩大范围 |

M1 和知识候选补验可以做独立准备，不能因此把 M2 的业务收益视为已证实。M3 的职责定义可提前讨论，但实际收益必须经过试行。正式线上发布需有可用的运行与回退方案。

四部分不按四个互不相干的工程验收。M2 的最小闭环需让当前 session 形成并整合认识、经任务机制承接、实际使用并影响下一动作；已有职责可先承担工作，M3 再评价是否需要拆分新 Role。整体验收以产品 P07 的两次相连循环为目标，同时允许依据效果停止或转向。

### 切片、阶段与整套工作台怎样区分

| 完成单位 | 可以据什么说完成 | 不能据此推定什么 |
| --- | --- | --- |
| 一项任务/一个切片 | 在固定范围内交付产物，并完成该任务约定的技术或消费验收 | 没有接入的运行时、飞书或 Wiki 不算通过；纯实现完成不代表阶段效果成立。 |
| 一个阶段 | 上表该阶段的交付与学习问题都有对应证据，未成立的效果保留失败/未知及下一决定 | M1 单次交接通过不代表 M2 认识使用有效；阶段范围可以按新证据修订，但须说明理由。 |
| 首期工作台整体 | 从 M1→M2 接通基础与知识切片，再沿 M3 验证职责试行、M4 验证真实定时与持续接续，最终贯通[工作台六条路径](product/workbench.md#六条端到端使用路径)及各自验收 | 一个页面、原型按钮或其中一条路径通过，不代表整个工作台可用，也不证明手机已有远程服务。 |

M1 可以分片准备和验收，建议先核 Task/Document 固定基线与旧版本拒绝，再接一个真实运行时的单次交接/未知结果核对，随后贯通飞书任务投影/回写冲突及对应工作台入口。各片需要的技术选择先按 M0.5 确认；可并行准备的部分不必等所有模块完成才开始。**只有 M1 上表范围都经过验证，才宣称 M1 完成。** Wiki 阅读、纠正和评价随 M2 接入，图谱等后置项沿用[工作台分期](product/workbench.md#桌面手机与阶段范围)。这里澄清完成单位，不把实施建议变成已运行能力或已批准的全部技术选型。

## 眼前的关键工作

1. 先完成技术选型和包职责的架构确认，解释推荐与替代方案，并选一个最小业务场景。
2. 确认其余技术后先建立 PostgreSQL Task/Document/Relation 合同及版本测试，再核飞书投影/回写权限和运行时接口；迁移协议夹具时补反例拒绝及丢回执对账。
3. 针对固定 OpenViking v0.5.1 的写入入口、来源撤回维护、原生恢复做有边界补验；用结果决定补丁范围，候选不满足时允许换后端。
4. 选择一段能持续积累反馈的真实小任务，建立提醒、返工与接续基线；不得用合成样例成绩替代。

这些是候选工作线，尚未建立真实飞书记录，也没有据此自动启动实施会话。后续任务按已有授权、可用资源和产品优先级推进。

## 工作台前端首片怎样落地

**当前只收敛方案，不继续完整实现静态原型，也暂不写真实前端代码。** 用户要求保留原型审查发现的问题，待主数据与共同 API 首片就绪后，直接在真实前端实现和验收。React/TypeScript/Vite 等仍是选型提议，本项计划不等于采纳或启动服务。

建议的首片是：**一个已有项目的需求改版后，使用者从总览找到受影响任务，阅读固定依据，逐项记录复核并回读结果。** 它覆盖页面主次、三项导航、Task/Document 阅读和一次真实命令往返；不是一次实现所有首次旅程、六条路径及外部集成。

| 要素 | 进入条件、交付与停止边界 |
| --- | --- |
| 输入与依赖 | M0.5 确认前端技术边界；S1 的真实 PostgreSQL Task/DocumentRevision/Relation 与授权 Query/Command API 可用。准备一份需求 r1/r2 和两个引用 r1 的未完任务，明确项目、责任、权限、各任务范围及消费者验收；没有真实对象就显示空态/缺项，测试夹具不成为默认工作数据。 |
| 页面交付 | 采用[三项导航建议](product/workbench.md#项目范围导航与事实状态)：总览呈现阶段/待处理/责任/使用缺项；工作区进入 Task 和过程 Document 全文/历史版，详情可追依据及影响；知识未接通时在独立入口明确说明。首片正文可限已获授权的内联 Markdown，HTML/资源包待阅读服务具备能力后接入，不声称全格式已验。 |
| 关键操作 | 从需求 r2 找到两个旧基线任务；一项以证据和有权责任者记录改用 r2、调整后续验收，另一项记录 r1 仍适用的理由。命令携带所见基线，经 core 验权与版本检查；结果由 API 回读，原接受依据和决定历史仍可查。 |
| 失败与恢复 | 旧版提交保留用户输入并显示当前版与差异；重复提交不产生两个决定；写成后丢响应先按原操作查询，不盲重发。待补证不显示绿色已处理；总览、列表和详情回读同一事实。缺权限/来源时显示责任和下一入口，不能靠前端按钮宣称获得授权。 |
| 自动检查 | 真实 PG/API 核旧基线拒绝、单次决定、丢响应回读和固定历史；前端核路由/修订深链、同源状态刷新、输入保留，以及权限/冲突/未接通状态。不用浏览器内状态替身证明后端保证。 |
| 用户验收与停止 | 未参与编写的使用者在本机桌面从普通入口找到一个待处理任务、读到完整固定依据、说明两个不同选择及责任，并回查记录结果；记录首轮误解和人工帮助。窄屏视口另核布局与阅读，不把它算作手机远程访问验收；真实手机接入待常在线主机、HTTPS 与登录条件就绪。完成这个阅读—复核切片即止，不因此宣布 M1、整套工作台或阶段产品效果已完成。 |

本轮发现的问题按能力依赖继续保留，不能为了缩小首片而删除：

| 后续能力切片 | 必须带入的约束 | 何时实现与验证 |
| --- | --- | --- |
| 首次目标与提议接受 | 首次空态不混入既有项目样本；目标/消费者/授权/责任、阶段交付与学习问题可回读。待补证、越权或待独立判断必须先有新依据及处理结果才能重判，同字段重提不能清掉待决；接受后不得被表单静默覆盖。 | Project/提议/接受命令就绪后沿 J1—J3 落地；不在前端另建持久任务状态机。 |
| 交付、消费者使用与下一步 | 技术、消费者观察、实际采用与阶段选择分别记录；返工或新交付使本轮检查/亲用/回看待核，旧记录仍可追。下一选择不自动变成已接受任务。 | 交付/消费证据与阶段回看 API 就绪后，按 J4—J6/P07 真实路径核对；静态“成功”按钮不能替代。 |
| 讨论、分工及恢复 | 确认交接包只说明准备/待承接；外部接收、决定登记、对象更新与亲用分别核。新职责先比较替代、试行/退出；日程暂停不抹掉在途未知。 | 按 M1 运行时接续、M3 分工、M4 定时的相应合同与实测能力接入。 |
| Wiki 与全格式阅读 | 过程 Document 与 Git 独立；Markdown/HTML 全文、资源/版本可核；知识正文、来源/反例、Review、发布/已读/采用分开。 | Blob/报告预览与 M2 外置知识服务分别可用后验证，未接通时显式缺项。 |

问题依据和原型覆盖界限见[原型审查补记](research/workbench-prototype-review.md#转入真实前端首片方案2026-10-20)，代码包与 API 责任仍由[包架构](architecture/packages.md)和[前端架构](architecture/frontend.md)维护。后续实施再按所选切片确认实际责任与验收，不把这张分期表当成已创建任务或已运行能力。

## 当前阶段的一个小任务

**示例：定位一次“看完材料仍找不到下一步”的阻塞，交付一项最小修复建议及验收。** 这是当前文档阶段即可执行的调查，不要求先实现业务服务；实际任务需取得具体反馈，不能把示例当成已创建或完成的工作。

| 要素 | 本轮边界 |
| --- | --- |
| 交付目标 | 找到一个具体阅读/决策阻塞，交付证据支持的原因判断，以及一项能独立开工的修复任务说明。 |
| 学习问题 | 阻塞来自入口/表达、缺依据、未接通能力，还是目标尚未明确？哪一个观察能区分这些解释？ |
| 输入 | 固定文档/原型版本、使用者想完成的事、原始入口与操作路径、卡点和期望；涉及纠正时还需纠正原意与授权范围。当前任务/PR 承接这些输入。 |
| 动作 | 复核这一条路径；比较至多三个有依据的解释，标出支持与反对观察；选择一项最小可回退修复，说明暂不做什么。 |
| 交付与验收 | 给出失败位置、固定来源、判断及未知、被选修复的目标/责任范围/产物/实际使用判据。由未参与整理的消费者核对“证据是否支持该选择、输入是否足以开工”；缺必要事实时只交付受限判断和补证项，不虚构原因。 |
| 停止条件 | 到一个阻塞的判断和下一项工作说明为止；本任务不同时实施修复、接通全部系统或证明整个阶段效果。无值得推进的修复时，保留补证/暂停/停止理由。 |

后续若接受修复，另按其具体范围实施并让目标消费者重试原路径；再由[阶段回看](product/daily-loop.md#阶段交付后怎样选择下一步)决定认识和下一动作怎样改变。该调查验收、修复验收和阶段效果分别记录。已明确、在现有职责与授权内的纠正可由领域 session 并行修复，不必等待这个调查或中心逐项批准。人员实例、权限和预算来自实际工作，不在长期路线页预设。

## 如何更新本页

能力完成须附对应提交、运行结果和验证范围；不能只因文档写好或任务被标完成就改变状态。阶段失败可能产生新的判断或缩小范围，把原因与下一动作记录清楚即可。具体执行见[开发规范](development/standards.md)。
