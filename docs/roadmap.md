# 阶段路线与当前状态

2026-10-21。阶段划分是当前实施建议；进入下一阶段取决于验收证据，尚无承诺日期。已实现切片的任务状态由本机 evoLoop/PostgreSQL 管理；飞书协作入口仍待接入。本页汇总能力阶段、已验证范围和进入条件。

**先理解目标体验，再选择当下工作。** [产品旅程 J1—J6](product/definition.md#从一个目标走到第一次有效交付)描述未来使用者从目标到首次有效交付及下一步；本页 M0—M4 描述 evoLoop 自身的实施阶段，两者不是同一套编号。下面的文档调查示例可在当前仓库执行，但不代替目标产品的首次接入体验；它也不证明旅程已运行。

## 完整目标与证明顺序

**最终要改变的是项目推进方式：**负责人给出目标、约束与关键取舍后，现有责任 session 能依据真实材料提出有边界的下一步，任务固定接受时的需求和认识，由有权者承接并交付；目标消费者实际使用成果，反馈和反例再修订判断、受影响任务与下一动作，必要时补证、转向或停止。项目在换 session、丢回执和需求变化后仍能接续，负责人不必反复粘贴背景、传话和催促。两次相连的“行动→亲用→认识变化→下一动作”及第二次对前次证据的实际采用，是检验持续接续的目标；任务数、自动运行时长和 Wiki 页数不是替代指标。完整行为见[产品定义 J1—J6](product/definition.md#从一个目标走到第一次有效交付)与[P07](product/definition.md#p07--认识能够自主接续下一步)。

价值按三层核对：**基础可信**是身份、固定版本、权限、事务和恢复使一次选择可追；**首次有效交付**是领域工作经技术检查并被目标消费者沿原路径使用，结果可回到判断；**持续收益**是后续 session 正确采用纠正、减少重复提醒或遗漏，职责按真实负担试行且能退出，外置 Wiki 在可比任务中比直接读材料更有用或更省总成本。后一层必须有独立使用观察，不能由前一层的工程检查推定。少量材料直接可读时，不强制先建 Wiki 或新 Role。

S1a 只证明第一层的一小段：已采纳需求改版能让两个尚未运行的任务保留旧依据并分别作新旧基线选择，失败后仍可查决定。它尚未证明任务真正执行、交付被亲用、认知改变下一步、Wiki 有效、动态分工有收益或项目可持续运行。每次扩片均应选择能连接上一层到下一层的真实使用场景，记录预期、观察和反证；未发生的效果保持未知。

## 当前基线

- 当前是本机试用切片：11 个 npm 工作区、PostgreSQL 迁移至 011；共同 API、CLI 与 React 工作台覆盖目标→阶段→Task 提议/判断/接受→交付→使用观察→关闭，并有 Role、Schedule、操作回执与恢复记录。构建通过；单元 130 项（129 通过、1 项外置服务 opt-in 跳过）、39 项文档测试和 17 个统一入口集成测试文件通过；测试是工程证据，不替代实际使用。
- 过程 Document 的 Markdown/HTML 与资源经受控 Blob 保存和完整回读；Git 正式文档按白名单路径、完整 commit 与 SHA256 固定，只在 PostgreSQL 记录引用和审核决定。真实浏览器已核静态 HTML/CSS/SVG 预览的背景、SVG 与空 sandbox；脚本内容不执行，也不能据此说交互页面已被完整理解。
- 外置 OpenViking **0.5.1** 已在仓库外真实写读、服务重启回读，并由普通工作台完成候选→审阅→发布。过程文档采纳新版后，旧知识的动态来源状态实际转为“需复核”；后续新知识已发布并由 Task 显式采用。语义索引、长期恢复、多写者与独立消费收益未验证，Wiki 正文和内部依赖不进入本仓库或 PostgreSQL。
- 自管 Codex App Server 曾以账号可用模型完成真实 Turn，重启后可读回全文。另一次后续运行在原生 completedAt 为空时过早记为 interrupted，约 89 秒后原生成为 completed；终态闸已修复，普通工作台显式复核把同一 Turn 的记录更正为 completed，保留旧事件并追加有署名的 `run.reconciled`，Task 与固定 Basis 未变。后续新运行报告已实际读到固定 Wiki，并核过所需源码；这仍不等于交付或消费完成。
- 两次相连真实 Task 已交付、由独立 Agent 使用并关闭，阶段已回看。后一次消费者实际下载新旧 HTML、CSS、SVG，字节哈希均与固定修订一致；首次因旧标签页界面缺入口而失败的观察保留，普通刷新重新登录后新增成功观察。日程经普通工作台提出过一项 Task，随后暂停并停止，历史和拟议 Task 保留、不再触发后续工作；职责提案比较了四种替代方案并延期，没有创建常设 Role。这些记录不证明长期收益。

### 独立负责人视角验收后的修复

独立 Agent 代行项目负责人从普通入口给出“部分通过”：任务延期理由不可见、已回看阶段无法纠正、负责人两类讨论入口缺失。最初“运行成果完全不可读”的判断已根据完整页面撤回；真实问题是专用原生答复与线程历史读取失败，保存的详细摘要仍可读。误判和纠正各自保留，不能继续按旧标题定为严重缺陷。

后续工程分为四项：**A1** 决定历史与追加纠正，**A2** 分工/方向的固定交接包与人工承接，**A3** 纯读原生历史、接受判断与交付导航，**A4** 整体检查、独立使用与合格 PR 合并。A1—A3 的源码和真实数据库回归已完成；本机迁移至 011，整合构建与上列检查通过。独立 Agent 已从普通页面回读任务延期理由和固定依据、追加阶段纠正并保留旧判断，原先失败的同一原生线程读回两次运行及最终答复；任务列表区分 proposed 与拒绝判断，交付链接可达，但新标签页须重新登录。

两类讨论包已由普通页面生成，分工包完成实际 native Agent 人工接续、决定、实际对象链接和有理由的决定纠正，旧事件与链接保留；方向包仍明确待人工承接，未登记决定。这不是 Desktop 自动接入或真人使用。首次跨阶段误配被正确拒绝，同时暴露“所有 409 均被当成版本过期”的恢复引导问题；修复后沿同一路径重试，完整草稿保留且可修改。窄屏还发现交付观察中的长链接与哈希造成横溢，按 DOM 证据修正断行后，同一页面 390px 复测中页面与滚动宽度均为 390；决定纠正后也明确显示本次后续行动与亲用待重新核对。工程交付见 [PR11](https://github.com/cyl19970726/evoLoop/pull/11)，合并状态以其固定提交检查为准。这四项是验收修复工作，不自动对应任何项目的 Goal/Stage，也不改变 M0—M4 的产品效果条件。

A4 的最终停写备份已校验 73 项文件，并恢复至独立空 PostgreSQL 18；迁移 011 后的 51 张表逐表行数与行内容摘要一致，Blob 和 Wiki 导出也已解包。Wiki 仍只验证导出解包，未自动导入新 OpenViking 服务；原服务重启后固定知识修订和新增讨论记录可读。该演练不证明跨存储原子快照或生产恢复。

| M4 持续使用与发布 | 将 S3 到期/重叠/暂停恢复与 S4 知识使用纳入受管项目试点；建立常在线运行、备份/回退、文档发布和可观察的日常入口 | 至少两次相连的行动、亲用、认识变化与下一动作能互相追证；日常讨论与定时检查不漏、不重、不造空任务，真实使用、成本和用户反馈经阶段回看后再扩大。若可靠性或净收益不足，缩小试点、补恢复或停止该路线；不以部署在线代替产品有效 |

M1 和知识候选补验可以做独立准备，不能因此把 M2 的业务收益视为已证实。M3 的职责定义可提前讨论，但实际收益必须经过试行。正式线上发布需有可用的运行与回退方案。

四部分不按四个互不相干的工程验收。M2 的最小闭环需让当前 session 形成并整合认识、经任务机制承接、实际使用并影响下一动作；已有职责可先承担工作，M3 再评价是否需要拆分新 Role。整体验收以产品 P07 的两次相连循环为目标，同时允许依据效果停止或转向。

## 工作台前端首片怎样落地

**本节保留 S1a 首片的历史边界：当时已有主数据 API、CLI 和初版真实工作台，本机 PostgreSQL 路径与有限浏览器走读已核，真人亲用待反馈。** 原型审查发现的问题继续作为真实工作台各片的验收约束。Git 固定引用、运行时和外置 Wiki 后来进入本机试用；飞书出站投影仍延后，M1 效果仍须核对。

S1a 的最小业务路径是：**一个已有项目的需求 r2 已采纳后，责任者找到两个引用 r1、处于“可做”且尚未运行的任务，阅读固定依据，逐项记录复核并回读结果。** 真实 PostgreSQL 与授权 Query/Command API 已通过这条路径的受限验证；初版页面已有总览/工作区和复核入口，已通过有限浏览器走读，尚待真人亲用反馈。完成 S1a 不代表首次旅程、完整 S1、M1 或六条路径已经贯通。

| 要素 | 进入条件、交付与停止边界 |
| --- | --- |
| 输入与依赖 | 真实 PostgreSQL Task/DocumentRevision/Relation、授权 Query/Command API；一份有明确采纳决定与现行指针的需求 r2，及两个引用 r1、处于“可做”且没有在途 Run/交付的任务。固定依据限当前有权读取的内联 Markdown 过程文档修订；明确项目、责任、各任务范围和验收。测试夹具不得成为默认工作数据。候选 r2 不能作为改用依据；已有在途运行的任务留待运行接续切片处理，不改写其历史依据。 |
| 页面交付 | S1a 已有可回读的 API/CLI 和初版页面，采用[三项导航建议](product/workbench.md#项目范围导航与事实状态)，从总览/工作区读 Task、过程 Document 原文与历史版，追依据及影响；有限浏览器走读已核、真人阅读与取舍待核。没有真实对象就显示空态/缺项。Wiki、Git 固定来源及 Blob/HTML 读取尚未接通时须明示不可用；不得以摘要或测试数据冒充完整依据。 |

| 失败与恢复 | 旧版提交保留变更意图并返回当前版与差异；重复提交不产生两个决定；写成后丢响应先按原操作查询，不盲重发。真实页面还须保留用户输入，待补证不显示绿色已处理，总览、列表和详情回读同一事实。缺权限/来源时显示责任和下一入口，不能靠前端按钮宣称获得授权。 |
| 自动检查 | 真实 PG/API 核候选 r2 拒绝、旧基线拒绝、单次决定、丢响应回读和固定历史；已有在途 Run 的任务不得通过 S1a 命令改写其执行依据。页面另核路由/修订深链、同源状态刷新、输入保留及权限/冲突/未接通状态；不用浏览器内状态替身证明后端保证。 |
| 用户验收与停止 | 未参与编写的使用者从本轮实际入口找到两项待复核任务，读完各任务**全部必需的**固定 Markdown 依据，说明不同选择与责任，并回查持久决定；记录首轮误解和人工帮助。任何必需的 Wiki、Git 或 Blob 原件未接通或不可达，都不能算作“完整依据已读”或让本片通过。在本机桌面核普通入口，窄屏另核布局；手机远程接入另验。完成 S1a 的阅读—复核才停止本片，不因此宣布完整 S1、M1 或阶段产品效果完成。 |

## 当前阶段的一个小任务

**示例：定位一次“看完材料仍找不到下一步”的阻塞，交付一项最小修复建议及验收。** 这是任何阶段都可执行的有界调查，不要求先接通全部业务服务；实际任务需取得具体反馈，不能把示例当成已创建或完成的工作。

| 要素 | 本轮边界 |
| --- | --- |
| 交付目标 | 找到一个具体阅读/决策阻塞，交付证据支持的原因判断，以及一项能独立开工的修复任务说明。 |
| 学习问题 | 阻塞来自入口/表达、缺依据、未接通能力，还是目标尚未明确？哪一个观察能区分这些解释？ |
| 输入 | 固定文档/原型版本、使用者想完成的事、原始入口与操作路径、卡点和期望；涉及纠正时还需纠正原意与授权范围。当前任务承接这些输入；已接通的对象可在 evoLoop 登记，尚未接通的场景仍由任务/PR 保留证据。 |
| 动作 | 复核这一条路径；比较至多三个有依据的解释，标出支持与反对观察；选择一项最小可回退修复，说明暂不做什么。 |
| 交付与验收 | 给出失败位置、固定来源、判断及未知、被选修复的目标/责任范围/产物/实际使用判据。由未参与整理的消费者核对“证据是否支持该选择、输入是否足以开工”；缺必要事实时只交付受限判断和补证项，不虚构原因。 |
| 停止条件 | 到一个阻塞的判断和下一项工作说明为止；本任务不同时实施修复、接通全部系统或证明整个阶段效果。无值得推进的修复时，保留补证/暂停/停止理由。 |

后续若接受修复，另按其具体范围实施并让目标消费者重试原路径；再由[阶段回看](product/daily-loop.md#阶段交付后怎样选择下一步)决定认识和下一动作怎样改变。该调查验收、修复验收和阶段效果分别记录。已明确、在现有职责与授权内的纠正可由领域 session 并行修复，不必等待这个调查或中心逐项批准。人员实例、权限和预算来自实际工作，不在长期路线页预设。

## 如何更新本页

能力完成须附对应提交、运行结果和验证范围；不能只因文档写好或任务被标完成就改变状态。阶段失败可能产生新的判断或缩小范围，把原因与下一动作记录清楚即可。具体执行见[开发规范](development/standards.md)。
