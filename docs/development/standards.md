# 开发规范：从已观察问题形成可验证约束

状态：2026-10-19 初版。当前只有 `docs/` 与隔离 Wiki 实验；以下规范约束后续实现与接入，**不表示 harness、飞书适配器或正式 Wiki 已经部署**。技术栈、部署形态与具体接口要由正式架构和后续试点确定。产品目标见[产品定义](../product/definition.md)，职责与数据边界见[架构总览](../architecture/overview.md)及[接口约定](../architecture/contracts.md)。

规范按“观察到的问题 → 约束 → 验证 → 何时重看”保留理由。实验结论只在其固定版本和合成样本范围内有效；设计、源码推断、实际运行和用户亲用分别标注。可发布的实验事实以[验证摘要](../references/validation-summary.md)为入口，决策依据及源材料迁移见[决定登记](../decisions.md)和[来源沿革](../references/lineage.md)；不从公开正文链接未发布的本地实验文件。

## 数据与执行边界

- **任务状态只有一个权威。** 用户选定飞书多维表格作为任务权威；仓库与 Wiki 只保存任务 ID/链接、所用修订和必要摘要，不各自维护一份可写任务状态。飞书适配器尚未实施，不能把提议字段或手工清单写成已生效行为。
- **认知在开发仓库外。** Wiki 可以是服务存储或独立 Markdown vault；其正文、来源、索引、修订和原始 session 归档不能自动同步回此公开 repo。仓库只维护正式产品、架构、规范与接入配置。发布知识时引用稳定知识 ID 和修订，公开导出是只读视图，不成为第二份可编辑正文。
- **会话不是权威数据库。** 每个业务 session 可以提出认识、处理自身领域问题并验证结果；Wiki 维护 session 负责跨来源整合、冲突和过时修订；分工管理 session 评估职责变化。逻辑职责从实际问题和效果演进，不预置一套固定岗位，也不因换聊天窗口增加角色。任何新常设职责须写清现有职责为何接不住、替代做法、试行与退出条件。
- **外部副作用有可核对结果。** 写入任务、知识或通知时使用稳定操作 ID、目标 ID 与基线修订；超时或丢失回包后先读回确认，再决定是否重试。提交成功只代表存储接受，不代表下游读取、语义正确、用户满意或已部署。

## 变更和验证

行为改变时选择能检验失败模式的最小检查，保留首次失败与修复后证据；不写只复述实现的测试。对冲突、撤回、重试和恢复，要检查持久状态与下一次读取，不只看 HTTP 状态码。当前 Wiki 实验用的是合成材料，不能外推到真实历史规模、多租户权限或生产可靠性。

常规变更形成聚焦 PR，描述触发、前后行为、影响、实际检查与尚未验证处。小修可直接准备清楚的可审阅差异；公开仓库首次自举提交是建仓例外。GitHub Actions 文档检查工作流已存在，远程结果只按对应提交的运行记录报告；本文不声称分支保护或公网部署已配置。当前 Node 22.19.0 只为文档构建所用，不代表未来 harness 技术栈已定。本地可运行 `npm ci`、`npm test`、`npm run docs:check`、`npm run docs:build`；在 Git checkout 中再运行 `git diff --check`。项目技能若需新增，默认放 `.agents/skills/<name>/SKILL.md`，不因任务推进而全局安装。

## Dogfood、调度与运行时接入的验证约定

应用代码开始前先记录[技术选型](../architecture/technology-selection.md)的确认结果、固定版本和包职责；当前推荐方案尚未转为已采纳基线。首片应锁依赖、验证 Node/原生 SQLite/协议类型，并复用 Python 研究的判据重新检验拟议 TS 客户端。新上游版本须保留旧实测结论、单独核变化和迁移，不能直接把发布说明填入“已通过”。

一次真实工作暴露的产品能力缺口应保留使用步骤、预期/实际、来源、影响范围和消费者判据，进入统一任务提议；新需求的接受决定与实现检查分开。领域责任者可在授权范围内修复，独立判断按事项需要路由。规则和工具的小改也应写明预期作用，但不能把每次调整自动当成已验证产品需求。产品过程见[日常工作闭环](../product/daily-loop.md)。

Codex 适配器固定 CLI 版本与生成 schema，协议类型只留在适配包。测试覆盖请求/响应关联、服务器请求路由、Turn 终态和中断、断线对账、派发结果未知；普通 RPC ID 不作跨重试幂等凭据。先用替身验证策略，再用隔离真实任务验证宿主能力，分别报告结果。生成类型和初始化成功不能证明模型执行或桌面会话互通；现有研究边界见[App Server 调查](../research/codex-app-server-20261019.md)。

调度测试用可控时钟覆盖时区、同一触发重复到达、定义修订、重叠、漏触发和暂停；至少一次真实平台恢复测试验证“写入已发生但响应丢失”不导致重复派发。停用日程与停止在途运行分别核对，未完成操作持续对账。构建和源码依赖按[包架构](../architecture/packages.md)保持单向，核心规则不引用平台 SDK 或本机聊天数据库。
