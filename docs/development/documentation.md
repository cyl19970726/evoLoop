# 文档维护与公开阅读

状态：2026-10-19 修订。仓库保存可公开的正式产品、架构、开发规范、接入配置和[研究报告](../research/README.md)。用户已将原 `docs/validation/` 统一归入 `docs/research/`，后续选型、调查、实验和探索也放在这里，并纳入 HTML 文档导航。研究记录保留过程与失败，**不自动代替当前正式文档**。早期 `docs/design/` 及原始实验材料仍保留在本地；公开整理不抹掉原始版本。

## 每类事实的权威位置

| 要回答的问题 | 权威正文 | 其他位置如何引用 |
| --- | --- | --- |
| 用户目标、阶段边界、体验与实际使用验收 | [产品定义](../product/definition.md) | 架构和规范引用该目标的稳定 ID；不复制一份独立目标状态。 |
| 系统层级、组成、数据权威和运行边界 | [架构总览](../architecture/overview.md) | 产品文档解释用途；具体接口在 contracts。 |
| 项目间、会话间、飞书与 Wiki 的接口和状态语义 | [接口约定](../architecture/contracts.md) | 实现和测试引用接口 ID/版本，不另写一个相矛盾的字段表。 |
| 怎样开发、验证和处理已观察失效模式 | [开发规范](standards.md) | 贡献入口只列最短流程，指回具体规范。 |
| 工作项状态与日程定义 | evoLoop PostgreSQL 主数据 | 飞书是 connector 投影及受控编辑入口；仓库/Wiki 引任务 ID/修订，同步状态单独记录。 |
| 原生需求、方案及其采纳修订 | evoLoop DocumentStore | 原生正文在外置 PostgreSQL；Git 正式文档用引用模式，按 repo/path/commit 登记，不另建可编辑正文。 |
| 来源、跨 session 认识、争议和修订 | 开发仓库外的独立 Wiki/vault | 正式文档可引用知识 ID 和固定修订的可发布摘要；不复制可编辑 Wiki 正文。 |
| 探索了什么、如何验证、观察到什么、为什么提出某个建议 | [研究与探索](../research/README.md)及各专题报告 | 固定问题、版本、方法、结果与限制；采纳后链接正式决定，不把建议标成已采用。 |

原生需求文档与现有正式 Git 文档按 [项目数据](../architecture/project-data.md)区分维护模式。原生需求若发布为 Git 正式规范，明确切换当前正文维护者并保留旧修订引用，不能两边分别维护现行版本。

同一事实只选一个可改写权威。跨文档用 ID、相对链接和修订连接事实；若一个设计变化同时改变目标、接口和执行办法，则**在同一次可审阅变更中**分别更新产品、架构与规范，并检查引用。不是每次小型文字修正都要触发全套角色审批；受影响的领域 session 可直接修复并说明依据。

## 一次正式修订怎样完成

1. 写明触发：用户纠正、实际产物、实验失败、运行事件或外部变化。区分“观察到”与“推断/建议”，保留来源 ID、日期、适用范围和原状态；不能把有限样本升级成通用结论。
2. 找到权威正文与引用它的文档。修订当前说法时标出被取代的旧决定和生效条件；未决冲突写出各方依据、缺的证据和下一次回看条件，不按最后编辑时间判真。
3. 对应调整验收：产品目标如何由普通读者/用户亲用证明，接口如何在真实读写路径核对，规范的检查能否抓到既有失效。自动检查与人类使用结果分开记录。
4. 检查公开边界、站内链接、图和生成结果。文档可放完整的可公开研究报告和审阅后的资产；`sessions/` 原始归档、外部 Wiki 正文、密钥、本地日志/截图与私有材料留在仓库外。公开资料默认可发布，不等于所有原始证据可公开。
5. 交付时列出变动的权威页、关键依据、已运行检查、未验证项和需要重看的条件。对历史设计/研究/验证文档仅添加明确状态或新引用，不无声改写当时实验事实。

## 站点源与生成物

当前站点工具以 `docs/` 和清单列出的根入口为源，`docs/site.json` 是**页面严格白名单**，只发布其中列出的页面，构建 HTML 到 **gitignored `site/`**。正式正文指向未列页面的链接会使 `docs:check` 失败；图片、图表和下载文件须由已发布页面引用且位于 `docs/assets/`，资源本身不必在 manifest 逐项列出。不使用作者本机绝对路径、开发 repo 外的私有文件或依赖登录的图片 URL 当公开证据。知识导出若要展示在站点，应带知识 ID、修订、生成时间及可公开依据，作为只读构建产物，不同步回开发仓库成为另一份权威正文。

本地工具已提供 `npm ci`、`npm test`、`npm run docs:check`、`npm run docs:build`，在 Git checkout 中还应运行 `git diff --check`。GitHub Actions 工作流也已提供；远程 CI 的结果以具体提交的运行记录为准，不据此声称公网站点已发布。生成 HTML 不手工修补，也不提交到公开 Git 历史；构建应能从仓库源文件与明确依赖复现。若以后决定版本化生成物，先记录与源文件的一致性机制及审阅代价，再修订本约定。

## Mermaid 流程图

正文使用 `mermaid` 代码围栏。构建工具仅在有图的页面加载本地打包的渲染脚本；离线可读，无需 CDN。图按原始字号显示，可横向滚动、放大并展开源码。使用一致的颜色图例，并把输入、模型判断、持久数据、条件和异常分开；源码检查通过后，还需实际打开生成页面检查图是否渲染、文字与箭头是否可读。图较大时按机制拆图，不用缩小字号掩盖拥挤。
