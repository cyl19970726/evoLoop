# 文档维护与公开阅读

状态：2026-10-20 统一。本文是文档归属、修订与站点检查的唯一流程正文；一次变更的入口见[贡献指南](../../CONTRIBUTING.md)，证据分级与交付口径见[开发规范](standards.md#证据与交付)。

## 每类事实的权威位置

| 要回答的问题 | 权威正文 | 其他位置如何引用 |
| --- | --- | --- |
| 用户目标、阶段边界、体验与使用验收 | [产品定义](../product/definition.md)及所属产品页 | 架构引用目标和判据，不独立维护一份目标状态。 |
| 层级、组成、数据权威、接口与状态语义 | [架构总览](../architecture/overview.md)及所属架构/合同页 | 实现引用对应合同/版本；执行规范只写如何验证，不复制字段表。 |
| 哪些已确认、哪些待采纳，阶段到了哪里 | [决定记录](../decisions.md)、[阶段路线](../roadmap.md) | 其他页引用决定及阶段，不把研究建议改写成已实施能力。 |
| 一次变更怎样开始、怎样验证 | [贡献指南](../../CONTRIBUTING.md)、[开发规范](standards.md) | 入口列最短流程；具体规则只在所属章节维护。 |
| Task/Schedule 与过程文档的运行数据 | evoLoop/PostgreSQL；DocumentStore 仅含任务关联的需求、详述、讨论等过程文档 | 飞书是 connector；过程文档直接关联 Task，保留不可变修订，可保存 Markdown/HTML 与资源包。此为已选归属，尚未实现生产服务。 |
| 正式产品、架构、规范与配置正文 | 各 repository 的 `docs/` | 不登记为 Document Table 的另一类行；用独立 Git 来源的 repo/path/commit 连接任务或知识。 |
| 来源、跨 session 认识、争议与知识修订 | 开发仓库外的独立 Wiki/vault | 固定知识 ID/修订及可发布摘要，不复制第二份可编辑 Wiki 正文。 |
| 调查、实验方法、观察、限制与建议 | [研究与探索](../research/README.md) | 新报告登记研究入口与站点清单；正式采纳后链接决定和目标正文，保留原结果。 |

Document Table 与 Git 正式文档的连接按[项目数据](../architecture/project-data.md#6-工作文档怎样沉淀为仓库正式文档)执行：从一份或多份过程文档中择要整理采纳结论，形成仓库变更，保留来源修订与原件历史。纳入候选写清目标路径/章节、目标基线、成立/未决结论和差异；完成审阅、合入后登记实际 commit。**预览构建在交付审阅前运行**，合入后发布则核对实际合入源；不把“合入后才能预览”变成阻塞。

同一事实只维护一个可改写正文，其余用相对链接与固定修订引用。目标、接口和执行方法都受影响时，在同一次可审阅变更中同步，或明确关联未完成的跨域工作；小型文字修正不触发全部角色审批。原型可随设计发布，但须标示例/未接服务，不能作为真实运行证明。早期 `docs/design/` 和原始实验保留本地历史，不代替当前正式正文。

## 后续维护责任与触发

本次集中补齐不建立新的常驻职责。后续沿项目已有的产品文档、架构与开发规范责任承接；实际 Role、Session 与权限须在分派时核对，职责名称和旧聊天都不自动授权。Lead 负责发现待办、确定优先次序和独立验收；所属领域负责人负责把已采纳变化改进其权威正文。跨域变化由各正文的维护者约定文件所有权和回收者，在同一 PR 同步或留下明确关联的后续 Task。

| 持续责任 | 何时触发 | 应修改并由谁复核 |
| --- | --- | --- |
| 产品文档 | 用户目标、使用路径、验收合同、真实消费者反馈或阶段结论变化；新能力已合入但产品页仍称待实现。 | 产品维护者核[产品定义](../product/definition.md)、所属产品页及[阶段路线](../roadmap.md)，以实际使用者能否按新说明完成路径复核；Lead 对本次交付与目标消费者的观察分别验收。 |
| 架构 | 核心对象权威、状态/接口、运行与恢复机制、外部系统边界或已采纳技术决定变化。 | 架构维护者核[架构总览](../architecture/overview.md)、所属合同/专题及[决定记录](../decisions.md)，用实现、schema 和适用的真实运行证据复核；跨端合同由受影响实现者共同检查。 |
| 开发规范 | CLI/Skill 命令或权限合同、Git/CI/发布流程、工程交接与恢复做法变化，或真实执行反复出现遗漏与无效负担。 | 规范维护者核[贡献指南](../../CONTRIBUTING.md)、[开发规范](standards.md)、[Agent CLI](agent-cli.md)与项目 skill；让下一位无本轮历史的执行者按候选说明实际工作，Lead 按其结果和项目检查复核。 |

触发后先核当前实现、固定来源和实际验收，再决定改正文、保留原文还是标为未验；关闭一次修订不等于已取得真人体验或持续收益。Schedule 可以支持明确授权的周期工作，但目前没有为这三类文档维护配置并验收一个运行中的周期任务；例行回看仍由现有负责人和 Lead 按实际变化安排，不写成自动提醒。

## 从任务结论到所属正文

确认一项过程结论值得长期使用后，先看它回答读者哪一个问题，再改该页的唯一正文：目标和判据归产品定义，完整跨 Session 接力归功能场景，Role/Task/Run 与数据权威归项目数据和合同，实际命令归 Agent CLI，工程检查归开发规范，当前做到哪里归阶段路线。原过程 Document、Task、PR 与使用观察保留固定修订和失败历史；在正文只写已成立的规则、适用版本和未验边界，不复制逐次 Run 流水账。领域责任者维护自己的页，Lead 对跨域顺序和实际验收负责；小修无需让所有领域重复审批。

**图随所属事实改。** 两张[产品卫星图](../product/definition.md#两张产品卫星图经营交付与组织改进)的可维护源分别是[经营图源](../assets/company-delivery-loop.workflow.json)与[改进图源](../assets/company-evocation-loop.workflow.json)；同名 HTML 是确认过的完整交互图，PNG 是其静态预览。2026-10-29 首次纳入时保留原版 HTML 字节，仅将图源 `meta.output` 改为仓库内相对路径；经营预览从同一原版 HTML 的 Archify visual-check 生成，改进预览沿用同 hash 的原预览。后续改图先核[产品定义](../product/definition.md)和[完整场景](../product/functional-scenarios.md)的演员与交接，再修改图源、重生成 HTML 和预览，检查内容与图源一致，浏览器核宽窄屏可读；不要只手改 PNG 或 HTML。细字以完整交互图放大阅读。产品局部时序图仍以 `product/functional-scenarios.md` 的 Mermaid 为权威，日常和工作台图只画各自局部问题；架构结构图以 `assets/evoloop-system-structure.architecture.json` 为权威，四张机制预览以 `assets/evoloop-system.model.json` 与 `scripts/architecture-map/reading.js` 为权威，由 `architecture:build` 生成 SVG/HTML。合同、数据和运行专题的 Mermaid 在相应 Markdown 原位维护。改图时同改图前的问题、图后的证据边界和跨页下钻链接；架构生成物不得独立手改。原结构与生成步骤见[架构图与正文的位置](#架构图与正文的位置)。

## 一次正式修订怎样完成

1. **保留触发与依据。** 用户纠正、实际产物、实验失败或外部变化发生时，记录来源修订/日期、适用范围及旧状态。区分观察与建议，不能把有限样本升级为普遍结论。
2. **改所属正文并追引用。** 找到当前权威页与旧关键词，更新受影响正文/摘要及后续任务依据；被取代决定保留替代关系，不按最后编辑时间判真。未决冲突保留各方依据、缺口与回看条件。依据是[纠正传播实验](../references/validation-summary.md)及[Document Table 归属纠正](../decisions.md)；再次出现旧说法或入口变化时复查。
3. **按语义调验收。** 文字修正检查准确性与链接；目标/接口变化同步相关判据。不同文件由不同会话负责时按[协作规则](standards.md#多-session-协作)交接具体路径，不以“已通知”替代实际整合。
4. **审公开边界并构建。** 仓库可发布正式文档、脱敏研究与必要资产；原始 session、外置 Wiki、凭据、身份材料、模型原件及私有日志/截图不进入公开 Git。检查实际差异与资源，不只依赖忽略规则；然后运行下节检查并核生成页。
5. **交付实际状态。** 按[交付口径](standards.md#证据与交付)列变动正文、依据、检查及未验证项。历史实验仅补状态/新引用，不无声改写当时事实；研究建议只有明确采纳后才进入正式合同。

## 站点源与生成物

`docs/` 和清单列出的根入口是源，`docs/site.json` 是**页面严格白名单**；新增可发布页面需登记，研究页还需加入[研究索引](../research/README.md)。Markdown 链接目标必须已发布，资源须在 `docs/assets/` 并由发布页引用，无须逐项列 manifest。公开正文不用本机绝对路径、私有文件或依赖登录的图片 URL。

HTML 构建到 gitignored `site/`，不手改生成页或提交巨大构建产物；修改源再重建。此规则来自[既有报告实践](../references/lineage.md)。若更换发布平台或要版本化产物，先说明源/产物一致性与审阅代价再修订。知识导出若供公开阅读，须有知识 ID、修订、生成时间和可公开依据，保持只读，不成为第二权威。

## 文档检查与构建

文档或构建工具变更在交付前运行以下现有检查。使用 `package.json` 要求的 Node 环境；当前应用与文档 CI 统一使用 Node 24。首次安装或锁文件变化时先 `npm ci`；依赖已齐且未变时无需每次重装。

```sh
npm run test:docs
npm run docs:check
npm run docs:build
git diff --check
```

- `npm run test:docs` 检验文档构建器的回归用例；`docs:check` 核白名单、站内链接/锚点、资源路径，并在清单内 Markdown 正文中拦截 Users 用户目录路径、file 协议与 codex 协议这几种已知私有地址模式。它不扫描发布资源的正文，也不能穷尽其他本机路径或敏感信息，不核正文语义或外站可达性；正文与资源内容仍须按本节人工审阅。
- `docs:build` 生成阅读页。核改动页面的标题、正文层级和关键链接；新图、布局或交互变化还须在浏览器实际打开，检查渲染、文字/箭头和受影响操作。纯文字修正可检查生成 HTML，无需重做所有历史页面/原型的视觉验收。
- `git diff --check` 核差异格式；另外审阅文件清单、内容和发布资源，确认无无关变更、私有材料或生成 `site/` 入库。

多人核验时可复制本次源文件、清单、资产、脚本和锁文件到忽略目录的独立快照，在快照运行同一组 npm 检查并记录对应源版本；它只能证明该快照。共享树后来变化时重新检查受影响部分，合并最终检查由整合者回收。无需为了快照修改构建器或覆盖共享 `site/`。

仓库已提供 GitHub Actions 文档工作流。CI、审阅、合入和公网部署的报告统一按[开发规范](standards.md#证据与交付)执行；构建工具不自动读取全部过程文档或自动发布，当前没有由本地构建推导出的公网部署。

## Mermaid 流程图

触发：新增或修改图。使用 `mermaid` 代码围栏；构建工具在含图页加载本地脚本。动作：统一图例，区分输入、模型判断、持久状态、条件与异常；复杂图按机制拆分。验证：源码检查后在生成页实际查看文字、箭头、横向滚动与放大，不能靠缩字号掩盖拥挤。依据是既有报告的生成阅读实践；图组件、布局或渲染依赖改变时复查。本文纯文字维护不要求重验全站旧图。

## 架构图与正文的位置

触发：架构机制、包职责、端口、跨模块关系或阅读交互变化。先明确读者在该段遇到什么困难、图要呈现什么关系、看完应能解释或判断什么；先核现有图是否已经回答，再决定复用、合并或补图。图紧接提出问题的正文，直接提供简约预览，需要下钻时再打开交互。不能以节点齐全、工具检查通过代替读者理解。

总览第 2 节的结构图解释责任、进程内装配与外部权威；第 3 节的工作回路解释连续行动；第 4 节辨认正文权威；第 5 节分别解释 unknown 恢复与依据改版。完整模块索引放在包架构，供实现定位。专题中的来源链、ER、事务、源码依赖与接口时序保留各自的细化问题，不再重复一张概念回路。图用白底、细线和少量强调色，详细说明和来源按需展开。

[结构规范](../assets/evoloop-system-structure.architecture.json)由 Archify 3.2.0 authoring/finalize 验证拓扑、边界与固定来源，原生 HTML 和回执仅在本地忽略目录保留。`scripts/architecture-map/structure.js` 基于同一规范生成简约结构预览和节点下钻；这是项目阅读层，独立检查其布局、标签与交互，不以原生回执代替。旧的四部分、模块树、回路原生 HTML 入口合并到同一阅读页，兼容文件仅转向对应视图。

[模块模型](../assets/evoloop-system.model.json)保存 12 个拟议包、子模块与有固定来源的关系。`reading.js` 维护四个机制的说明与来源；`mechanism-svg.js` 为对应正文生成简约预览规格；`plain-svg.js` 输出无需脚本的静态 SVG；`app.js` 默认展示系统结构，并连接正文深链与索引，`viewer.js` 处理完整索引的折叠投影。修改所属事实和相关模型后，运行 `npm run architecture:build` 同时生成主阅读页与五张 SVG，再执行本页检查。发布副本不手改；整站 `site/` 仍不入库。

测试检查预览与源一致、结构拓扑/端点、模块覆盖、折叠不丢关系和深链兼容。引用行范围按固定 Git 提交验证；单条 `sources.revision` 可覆盖模型的默认版本，增量更新入口时保留其他节点的历史依据。文档移位不改变旧来源含义；CI 因此读取完整提交历史。浏览器检查正文内联显示、上下文链接、结构节点展开/收起和内部层级、返回正文、模块搜索/关系与深浅主题。信息组织较大变化时，请未参与作者工作的读者从正文开始解释系统并自选问题下钻，保留首答及反馈修正；代理试读不作为真人理解增益的量化证据。阅读层不访问业务 API，也不代表生产前端。
