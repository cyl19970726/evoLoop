# 体验与信息架构：让人看清依据、责任与后果

2026-10-30 · 前端目标与阅读合同。页面能力是否已实现、部署或通过消费者使用，以[阶段路线](../roadmap.md)和对应版本的验证为准；下列界面要求不把目标能力写成当前服务事实。

读前先看[产品工作台的职责与六条路径](../product/workbench.md)。这里把这些目标落实为信息主次、导航与跨页面交互；具体像素、组件和实现留给[设计系统](design-system.md)及[前端架构](architecture.md)。

## 首次进入与已有项目的首页

**首次进入**时，首页先呈现项目目标、目标消费者、现有约束/授权和已有材料，让人看清已登记事实与缺口，再与既有 Agent 沟通首项工作或补证责任；必要时可从页面直接登记。材料可以是当前对话、仓库文件、用户描述或已有任务；零材料也能如实开始。选择来源或连接方式属于实现设计，不要求强制网页向导，也不把接通飞书、Wiki、Codex 自动控制作为创建项目的前置条件。尚无阶段或服务时显示“待判断／未接通”及下一步，不能填入原型数据。

**已有项目**首页先显示当前阶段交付与学习问题、进展与最近变化、最需判断或核对的事项、责任者、依据和消费者使用结果。人能从这里进入对象详情，带着相反依据和备选与既有 Agent 沟通；权限内常规修复由 Agent 执行后，首页与详情应可读回决定落到哪个需求修订、Task、知识 Review 或职责试行，以及后续是否实际被采用。阻塞、异常和无新证据都如实显示；补证、接受或取舍的直接页面操作按需可达。

## 同一项工作，信息主次怎样随结果改变

以[首次旅程](../product/definition.md#从一个目标走到第一次有效交付)的月报工作为例，下面是用于设计推导的情境，不是当前界面已实现的截图或新增运行记录。负责人打开项目时，先要回答“目标还有什么差距、谁接着做、我是否需要取舍”。全部对象可追溯，不意味着首次就把它们全部铺开。

- **尚未形成工作时**，先呈现希望运营完成的月报、已有反馈及缺项，主要下一步是与现有责任 Agent 明确一个有界动作。没有任务时不以空任务表代替目标入口。
- **已在执行时**，先呈现当前任务、承接者、采用依据和真实阻塞；运行细节按需展开。若没有待取舍事项，人应能确认工作有人承接，无需再次催促。
- **Run 已结束而运营仍卡住时**，先呈现“仍不能完成月报”、具体失败步骤、所用交付与接续责任；同时保留技术检查通过这一事实。主要入口是查看失败与跟进修复，不能用运行完成的成功摘要覆盖未满足的验收，也不能只展示“报告已提交”。
- **使用达到标准后**，先呈现谁用哪版完成了什么、仍有什么限制，以及下一步为何保留、改变或停止；历史报告、旧失败和运行明细仍可下钻。一次通过不需要把阶段或所有职责都关闭。

详情可采用单列叙事或分栏，但应连起**原要求 → 当前交付 → 实际观察 → 下一责任与动作**。例如运营反馈“日期仍要手改”时，负责人从任务详情进入固定交付和失败观察，带着链接与领域 Agent 沟通；Agent 按当前授权读取原件、定位并修复，回读新交付；消费者再沿原步骤使用并记录结果，人从同一任务看见旧失败与新观察。无需由人到多个聊天逐次复制过程；若承接入口尚未接通，明确显示待承接与跟进责任。

同一任务续跑或返工后，运行页应先回答“当前在看哪一轮、它与本任务哪次运行有关”。默认依据实际运行与正式派发关系定位；只有最近派发可核时明确标为最近记录，不能从旧循环已停止推断当前任务已停止。循环选项用可区分的短标识、状态、实际时间与关联说明，完整目标及阶段正文可展开阅读。用户主动查看历史后，回读不替其改选；切换任务或身份则重新核定。缺失或有歧义的关系保持未核定，不能把旧预算和下一责任套到当前运行。

这条交互也可能因前提失败而停止：无权读取交付时先显示权限缺项与可联系的责任者，原件缺失时显示不可验证，采用的版本过期时要求核对差异。它们不自动证明内容错误，更不能把一次失败操作记成“已用”。若新反馈改变验收，先核在途执行，再按[任务改版规则](../product/tasks-and-documents.md#链接和改版)处理；页面不通过悄悄换新版来消除旧失败。消费与结束的责任判据见[交付之后的接续](../product/functional-scenarios.md#交付之后谁接住未完成的工作)。

以上规定信息与动作的优先关系，不确定总览的最终布局。总览 F4 的整体产品验收仍按阶段路线核对；本轮可按真实能力优化各页面，但不能用布局、工作区或详情的局部通过宣称完整首页和产品闭环已交付。

## 项目范围、导航与事实状态

全局先选**项目**，跨项目内容只有明确授权时出现。任务、文档、关联、分工、日程和异常是能力及对象分类，不要求各占一个常驻左侧入口。**主入口收拢为“总览、工作、知识”**，另让讨论、协作、日程、运行和异常在清楚的上下文入口可达；在真实前端验证其可发现性，不再为完善目录扩写静态原型。这里改变的是入口组织，完整功能与验收仍保留。

| 常驻入口 | 首先回答什么 | 上下文中的功能入口 |
| --- | --- | --- |
| **总览** | 当前目标与阶段、最需要判断什么、谁接着做、最近使用与决定后果 | 待判断摘要直达工作区；方向讨论、分工与试行从相应卡片进入。没有新取舍就如实显示。 |
| **工作** | 工作进到哪、改了什么、依什么、谁负责、决定和结果如何？ | 待判断、任务、过程文档作为区内页签；过程文档可先于 Task 创建，不要求先开任务。日程从任务区或总览到期项进入；关联从 Task、Document 或知识详情的“依据与影响”进入，可沿稳定链接往返。 |
| **知识** | 当前认识是什么，来源/反例在哪，是否需要纠正？ | 专题、全文、来源、版本、Review；效果评价从知识区或阶段回看进入。知识空间仍允许独立浏览，不以已有任务为前提。 |

**目标是为待处理/异常保留固定的全局入口**，让阻塞、未知结果、外部编辑冲突及处理责任可发现，并从相关对象回链；不因收拢侧栏而藏进多层“更多”。当前内置“待核对操作”主要核对该身份和项目保存的共同命令回执；知识发布/撤回等专用对账仍在知识页，待办与依据影响复核仍在工作页。缺少项目级聚合时显示范围和原页入口，不把本地回执数量当作全部异常。仓库 `docs/` 继续通过项目菜单中的独立仓库入口与上下文出处链接访问，不作为 Document Table 行。搜索与固定对象链接补充直达，不代替上述正常入口。

共用外壳、色彩、阅读密度和响应方式由[设计系统](design-system.md#共同视觉语言)维护；本页只说明信息与入口之间的关系。

这些入口的日常可发现性仍待验证。真实使用若表明某项高频工作反复难找，再按证据提升入口，而不是把全部路由和技术对象提前平铺。首片范围与可观察验收见[工作台前端首片](../roadmap.md#工作台前端首片怎样落地)。

搜索结果按对象类型、项目、修订和权限分组。所看历史版与当前版的差别持续可见；详情先回答“现在是什么、为什么、谁接下一步”，再展示关系、历史及来源。列表、卡片与详情按对象区分业务、运行、同步、知识和效果五种事实，不合成一个“全部完成”。“待复核”“结果未知”“所见版本过期”和权限缺口须有可追的责任与下一入口；空态说清缺任务、证据、权限还是服务尚未接通。

## 首页与核心详情的布局约束

| 页面 | 产品层必须让用户同时看见或到达 | 可由设计选择的表达 |
| --- | --- | --- |
| 首页 | 首次进入的目标/消费者/约束与首项动作；已有项目的阶段问题、当前责任、真实使用结果、两类讨论和异常入口；决定之后能返回受影响对象。 | 卡片或列表、单栏或多栏、讨论材料折叠方式；首屏可按首次/已有状态调整。 |
| Task | 完整主正文、轻量类型、四态进度、固定需求/知识修订、责任者、验收、交付、技术检查、约定的亲用结果与等待/下一动作；上游修订差异可追。 | 列表筛选、侧栏、时间线或分栏详情；不能把同步或运行状态覆盖业务状态。 |
| Document | 表格逐行查阅与完整正文阅读可达，关联 Task 链接独立；所看版本、原文/预览、资源缺项和返回列表条件可见。 | 元数据侧栏、分页、手机收起次要列；不能用卡片摘要替代全文。 |
| Knowledge | 专题主动浏览到完整正文；所看/当前修订、来源及反例、相关认识、纠正 Review 与原件可核。 | 三栏或渐进展开、可选图谱、卡片密度；图谱不代替文字关系和正文。 |

这些约束描述用户必须完成的阅读与按需动作，不规定唯一像素布局或页面组件；颜色沿用[设计系统](design-system.md#共同视觉语言)的浅色、无绿色约定。F1 的重点验收是人能沿工作区与详情解释进展、变化、依据、责任、决定和结果，与既有 Agent 沟通后读回经 CLI 提交的修订及有权读取的执行记录；仅把新建、编辑、审阅表单全部摆上页面不算成功。桌面与手机的使用边界见[响应与范围](design-system.md#桌面手机与阶段范围)，具体前端读取、权限和修订映射见[前端边界](architecture.md)及[Wiki 工作区](../architecture/wiki-workspace.md)。

## 关键交互怎样闭合

下表沿两类入口说明输入、执行者和人可见的后果；默认由 Agent 经业务 skill＋CLI 提交业务变更，人保留按需直接操作。具体控件、来源连接方式与自动化程度可在设计时选择。常规授权内工作不增加中心审批，页面上的“已发起”也不能冒充外部会话已接收。

| 路径 | 输入与前置 | 动作与选择 | 可见状态、下一入口与失败恢复 |
| --- | --- | --- | --- |
| **首次从目标形成可做任务（J1—J3）** | 负责人提供目标、消费者、约束/授权，以及已有材料或明确的未知；项目可以尚无 Task、Document 或 Wiki。 | 人从首页/既有会话沟通目标，责任 session 经业务入口登记阶段交付和学习问题；未定问题保留为 issue/spec 或讨论；首项工作限定到一项可核的修复或调查。依据足够且在授权内就创建待处理 Task；缺关键事实先指定有限补证；目标或资源超界才提交具体取舍。Task 主正文由创建时的 Document 承载；其他过程文档可先建立再关联 Task。 | 首页出现阶段判断与首项工作的范围、验收、责任和停止条件；开始后的 Task 可看到固定依据。无承接者时显示待承接和补位责任；平台未接通时提供人工接续入口，不能把任务标为已派发。 |
| **已有需求纠正到实际采用（J4—J6）** | 新版需求或消费者失败有原文、来源、旧基线和受影响对象；未完任务仍引用旧版。 | 人从 Document 修订追到影响并沟通纠正；Agent 读取固定新旧版，按任务及 Run 状态分流，再逐项记录改用新版、旧版仍适用或待补证；知识 Review 保留相反证据。已运行任务的接续边界见[需求纠正](../product/daily-loop.md#需求纠正怎样处理)。责任者修复或补证，目标消费者沿原路径重试。 | Task、Document 和知识各显示所见修订与处理理由；首页能看到亲用结果与下一动作。飞书旧编辑冲突保留双方意图并转异常页；发布知识或合并代码后仍未亲用时，效果保持未知。 |
| **讨论跨 Codex 往返** | 首页已有分工或方向问题、备选、固定依据、授权边界和目标责任 session。 | 用户确认交接包后打开或人工转给既有 Codex 会话；讨论产生决定、未决项或补证要求，由有权 Agent 经业务入口记录到相应过程文档、Task、知识或职责说明，并登记所用来源；人工直接记录按需保留。 | 工作台展示“待承接／已登记决定／执行与亲用待核”等真实状态，提供返回对象的链接。若无法证实 Desktop 跳转或自动回写，就用可核对的人工记录和后续回读；不能将打开聊天或通知成功写成决定已执行。 |

讨论入口准备的是**受控工作交接包**：项目、目标、所读基线、证据链接、要回答的问题和权限边界，由人确认后交给合适的现有 session；已登记且获授权的自管任务可经协调服务发起。能否从页面直达 Desktop 聊天由宿主能力实测决定。Codex 仍是真实会话工具；工作台只显示可验证的会话概要、任务关联和经验证的跳转/发起入口，不嵌入或接管现有 Desktop 聊天，也不把自管 App Server Thread 伪装成同一窗口。若自动承接能力不可用，页面写“待承接”并给出人工接续入口。

本机实现提供“讨论当前分工”和“讨论下一阶段”两个入口，共用上述交接过程。交接包可完整阅读和复制，固定依据、问题、备选和授权边界随过程文档保存；人工承接观察、决定及其纠正各有署名和时间。可以登记“暂无新取舍”，也可以链接已经存在的 Task、Stage、Role 或 Document；这不会自动接受任务、建立常设职责或宣称对象已执行。Desktop 自动接入尚未验证，当前使用人工接续。总览的产品进度依据实际 Goal→Stage→Task 关系；工程里程碑见[路线图](../roadmap.md)，两者不按序号自动对应。

## 上下文页面与返回

| 入口 | 首先回答的问题 | 保留的下一步与边界 |
| --- | --- | --- |
| 讨论与依据复核 | 哪版来源改变了什么，谁有权判断？ | 打开固定原件、相反依据和处理理由，返回原文档/Task；不从保存或通知推断已执行 |
| 异常与操作恢复 | 哪个原操作结果未知，最后可核事实是什么？ | 按原 operationId 查询；保留输入和草稿，明确对账责任，不鼓励换ID重试 |
| 效果评价 | 每个 case 的材料、产物、采用、亲用与成本是什么？ | 分条件看证据和未知，回到知识或阶段；没有依据不生成综合胜率 |
| 仓库与配置 | 正式规则在哪里，哪些能力已配置且可用？ | Git 正式正文与过程文档分开；配置写入、原生生效和实际使用分别核对 |

跨页面返回保留项目、身份、对象、筛选、所选修订和阅读位置。页面缓存只保存阅读状态，当前事实仍须回读；切项目/身份/对象不能先显示旧对象正文配上新对象链接。固定历史深链保持原修订，另给当前版入口。

## 从理解到验证

读者先从熟悉的项目问题找到相关页面，再区分 Task/Session/Run、交付与使用，沿固定证据作判断，最后回看行动是否改变。熟悉者可直接从对象或异常进入，但始终能回到原因与范围。

验证从[六条产品路径](../product/workbench.md#六条端到端使用路径)选择受影响的一条，记录普通入口、实际步骤、所用版本、失败和返回。新增组件、一次技术检查或一份报告不等于整段闭环已通过。
