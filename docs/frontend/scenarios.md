# 场景与交互：人在工作台怎样完成一件事

本页从产品场景出发，说明人在工作台从哪里进入、依次经过哪些页面、在页面上做什么、交给 Agent 做什么；再由这些场景推出布局和跳转规则。场景的业务定义见[功能场景](../product/functional-scenarios.md)、[六条端到端使用路径](../product/workbench.md#六条端到端使用路径)和[日常工作闭环](../product/daily-loop.md)；本页只写界面上的交互。

## 必须先保证的核心路径

用户确认，现有工作台虽然不合理，但以下能力是日常离不开的，新版首先保证它们，并且比现在更直接：

1. **任务列表与任务详情**：按状态筛选，并能排序（优先级、截止时间、最近进展、创建时间、对账阶段）。
2. **从任务直接看到关联文档**：主正文、关联的过程文档（如需求总图、Leader 编排总览）、固定依据、交付物，都在任务右栏列出，点开即读。
3. **任务绑定 Session**：在任务右栏看到并设置承接的 Session（受管或外部登记的会话）；“已分派 / 已接受 / 正在运行”分开显示。任务的四态与对账阶段一眼可辨。
4. **看清 Leader 怎样安排 Session**：Leader 会持续维护一份编排总览文档，写目标、下一步怎样排这些任务、任务之间有没有资源冲突；再配合结构化安排，也就是每个 Session 的当前任务与队列，以及任务的优先级、截止时间和依赖。详见[场景 11](#场景-11看清-leader-怎样安排-session)。

## 谁在用

- **项目负责人**：最主要的使用者。观察进展、读证据和成果、作取舍，大多数修改通过与现有 Agent 对话完成。
- **领域责任者与 Leader 的人类协作者**：核对任务组合、承接和验收安排。
- **消费者**：按任务要求实际使用交付，并记录结果。

Agent 通过业务 skill 和 CLI 工作，不需要点页面（[DEC-030](../decisions.md#用户已确定的方向)）。所以每个场景里，人的动作以“读、判断、沟通、回看”为主，页面上的写操作是按需的补充。

| 7 | 定时检查与未知结果 | 日程 | 所选日程的最近运行 → 产生的任务 → 结果未知的操作 | 看触发与产生的工作；结果未知时按原操作查回 |

### 场景 1：一批需求怎样变成可执行的工作

这是最常见的起点，也是最容易“提了需求却看不到落在哪”的地方：

1. 人在 Sessions 里与需求 Session 对话，一次说明多条需求、目标和约束。
2. 需求 Session 经 CLI 为每项明确的工作创建 Task 和主 Document（正文与验收）；跨多个任务时，再写一份**总图 Document**，说明用户、对象、步骤、本轮切片和建议顺序（见 `evoloop-requirements` skill）。
3. 新建任务不会直接启动 Leader：Leader 由任务关注和结果通知两个后台泵触达，或由人发消息唤醒。Leader 读取这些任务后，经 CLI 记录计划、依赖、承接者和验收责任，再派发执行。界面显示“已通知 Leader”和“Leader 是否已处理”两项，并且已发送不等于已读。
4. 人回到工作台读回：任务列表里出现了哪些任务，各自写清了什么；总图文档列出了哪些任务、顺序和依赖；Leader 的安排落到了哪些任务上。

界面要支持：

- 任务列表可按“来源对话或总图”和“最近创建”筛选，一眼看到这一批需求产生了哪些任务。
- 总图文档的右栏列出它关联的任务及其当前状态；任务的右栏列出它所属的总图。
- 对话中提到的任务和文档显示为可点击的对象链接，点开即在工作模块中打开。

现状：任务和总图之间只能通过文档引用反查；“目标 → 阶段 → 任务”的旅程页只能从深处链接进入。

### 场景 11：看清 Leader 怎样安排 Session

Leader 负责组织任务组合、顺序、承接和验收。它的思考写在一份**编排总览文档**里，并且每轮更新：本阶段目标、下一步怎样排这些任务、哪些任务会争用同一个 Session 或同一份资源、为什么这样排。具体安排则落在结构化数据上：任务的优先级、计划开始与截止时间、前置依赖（`work.plan.set`、`work.dependencies.set`），任务绑定的 Session（`task.assignment.set`），以及各 Session 的驻留队列。

界面这样呈现：

- Sessions 空间的内层栏顶部固定一项“Leader 安排”，下面才是各个 Session。
- 中间上半部分是**当前的编排总览文档**（最新修订，可展开全文和历史修订）；下半部分是**安排看板**：每个 Session 一行，写它的职责、当前任务、排队任务和状态；没有承接者的任务单独一组。
- 右栏列出可以从数据直接看出的冲突与风险：同一个 Session 被安排了多项进行中的任务、依赖还没完成的任务已经开始、截止时间已过或临近、待验收却没有可用的验收者。总览文档里写的冲突以文档为准，界面只补充数据能证明的部分。
- 从看板点任务进入工作 › 任务，点 Session 进入它的对话；返回时回到“Leader 安排”。

现状与缺口：编排总览现在只是一份普通的过程文档，系统里没有标识“哪份是当前的编排总览”，界面无法固定展示它，需要在合同里加一个明确标记，见 [#229](https://github.com/cyl19970726/evoLoop/issues/229) 的依赖。任务列表的接口只支持分页，不支持排序；在服务端支持之前，排序作用于已载入的全部页，并在列表上注明。

## 从场景看布局

把十个场景放在一起看，有四个规律：

1. **最频繁的往返是“任务 ↔ 承接 Session ↔ 固定成果”。** 工作和 Sessions 两个空间各有长列表、筛选和阅读位置，来回切换时都要原样保留。
2. **有几样东西在任何地方都要看得见**：待我处理的事、结果未知的操作、账号与当前项目。
3. **每个空间都有自己的对象列表**：任务、文档、知识专题、日程、职责、Session。列表需要一整列的高度来扫读和筛选。
4. **中间读正文和对话，右边核事实。** 对话、任务正文和文档全文需要最宽的连续阅读区；状态、责任、版本和来源放在旁边随时可查即可。

由此得出布局（细节见[布局](layout.md)）：

- **保留双左栏，重新分工。** 外层模块栏负责“在哪个空间”和全局信号：工作、Sessions，底部是待我处理（带计数）和账号；内层上下文栏负责“这个空间里看哪个对象”：顶部是项目切换，下面是本空间的分区导航和对象列表。
- **中间是主体内容流，右侧是可收起的信息栏。**
- 和单条左栏相比，双左栏多占约 72px，换来两件更重要的事：一键在工作与 Sessions 之间切换且各自状态不丢；全局信号有固定位置。宽度不够时先收起右栏，再收起内层栏。

## 对象之间怎样互相查看

在一个对象里看另一个对象，是最常见的动作：在任务里看文档、在文档里看任务、在 Session 里看任务和文档。统一规则是：**看一眼在右栏，深读或要操作再去它自己的页面**。这样正在读的正文、正在进行的对话都不会被打断。

| 层 | 怎样触发 | 行为 |
| --- | --- | --- |
| 悬停预览 | 鼠标停在对象链接上 | 小卡片：名称、类型、状态、版本、责任；不跳转。仅桌面 |
| 在右栏查看（默认） | 单击对象链接 | 右栏新开一个页签显示该对象的“速览”，中间不动；地址栏用 `panel=` 记下当前速览，替换而不新增后退记录 |
| 在中间打开 | 速览顶部的“在中间打开”，或在速览里按 Enter | 去对象自己的页面（它所属的空间与分区），新增一条后退记录，页头出现“返回 <来源名称>”；这个速览页签关闭，右栏回到“信息”，显示该对象的版本、来源和关联 |

| 在…里 | 看… | 右栏速览显示什么 | 在中间打开后去哪 |
| --- | --- | --- | --- |
| 任务 | 文档 | 文档阅读器，打开任务固定的那一版；顶部写“任务固定 v3 · 当前 v4”，并给“查看当前版”。Markdown 可以在右栏读完；HTML 报告给“宽屏阅读”，直接在中间打开 | 工作 › 文档与知识，选中该文档；页头“返回任务：<名称>” |
| 任务 | 承接的 Session | 实体卡、实时状态行、待办清单、最近几条对话；底部“进入对话” | Sessions 空间的该 Session；页头“返回任务” |
| 任务 | 交付物 | 交付物文档的固定修订，加技术检查与使用观察 | 文档页 |
| 文档 | 任务 | 任务速览：名称、状态与对账阶段、承接 Session、完成条件、最新交付与使用，以及它和本文档的关系（固定依据 / 关联 / 交付物） | 工作 › 任务，选中该任务 |
| Session | 任务 | 任务速览，同上；对话与输入框不受影响 | 工作 › 任务；页头“返回 Session” |
| Session | 文档或交付物 | 文档阅读器，打开消息里引用的那一版 | 文档页 |
| Leader 安排 | 任务或 Session | 对应的速览 | 对应的页面 |

- 速览里的链接继续在右栏新开页签，不弹窗套弹窗；页签最多 5 个，超出时关闭最早的未固定页签。
- 速览只放“看”和最常用的一两个操作（如任务的“绑定 Session”、文档的“查看当前版”），完整操作在对象自己的页面。
- 速览和对象页面用同一套组件（同一个文档阅读器、同一份任务摘要），两处内容一致。
- Esc 关闭当前右栏页签；按住 Cmd/Ctrl 点击在新标签页打开。
- 窄屏：速览从底部升起，占屏约九成，上滑变全屏；“在中间打开”就是进入该页面，返回回到原页面原位置。

## 跳转规则

| 情况 | 行为 |
| --- | --- |
| 在正文或对话里点到文档、任务、交付物、Session | 按上一节在右栏打开速览，中间保持不动 |
| 打开同一空间的对象 | 在中间打开，内层栏同步选中，地址栏更新 |
| 打开另一空间的对象（如任务 → Session） | 切到对应空间，内层栏选中目标；页头给“返回 <来源名称>” |
| 返回 | 页头返回和浏览器后退一致：回到原空间、原筛选、原选中和原阅读位置 |
| 固定修订链接 | 打开那一版，另给“查看当前版” |
| 外部原件或下载 | 新标签页打开 |
| 按住 Cmd/Ctrl 点击 | 在新标签页打开（路径 URL 落地后） |
| 切换项目或身份 | 清掉旧项目的内容；有未保存的草稿先提示 |

地址栏记录项目、对象、修订、筛选、页签和当前右栏速览，刷新或分享后回到同一位置。

## 列表的选取与筛选

- 范围（全部 / 我的承接 / 某个总图）、状态、类型和搜索都写进地址栏，可分享、可返回。
- 选中项不在当前筛选结果里时，保留选中并注明原因。
- 计数注明是“已载入范围”还是“全部”；没读完时不说“没有”。
- 上下方向键移动选中，Enter 打开；表格视图用于批量对账，列可配置。

## 写操作放在哪里

- 页头最多一个主操作，例如任务页的“开始”或 Session 页的发送。
- 其余操作放在右栏的“操作”区或更多菜单里；危险或不可逆的操作用确认弹窗，写清影响对象和结果。
- 每个写操作都可以改由 Agent 经 CLI 完成，页面上写明这一点，不强迫人填大表单。

## 已发现的交互缺口

这些问题在现有代码中可复现，改版时一并处理。前半部分来自读代码，后半部分来自在独立测试实例上用合成数据实际走一遍（合成数据由 `scripts/seed-frontend-scenarios.mjs` 写入）。

**读代码发现**

- 多处 Session 链接带 `tab=overview`，它不是合法页签，会退回默认页签。改版后的任务列表和验收视图已不再带这个参数。
- 从任务进入 Session 时带了返回信息，Session 页没有读取，因此没有“返回任务”。（#229 F1a 已补：任务、任务表格、统筹安排、文档进入智能体或任务都带返回，见 `shared/returnLink.ts`。）
- 文档的返回白名单不含总览、设置和连接器，从这几页打开的文档只能回到文档列表（`shared/ui/returnRoute.ts`）。（#229 F1a 已加入。总览进入任务仍没有返回：总览页拿不到当前身份。）
- 评价、协作、收件、旅程、知识只能从深处进入，导航里找不到。
- `roles` 与“团队 › 职责档案”是两个地址、同一个组件。
- 导航名“文档与知识”与页面标题“过程文档”不一致。
- 旧任务索引的文档视图和旧的“当前工作”组件已无引用；改版时都已删除。

**实际走查确认**

- 原始标识随处可见：任务表“当前进展”格、总览“下一责任”、文档侧栏“引用此文档的任务”都显示完整 Role UUID；收件页依据变化显示修订短 ID。新版由对象链接与名称解析统一处理。
- 关系藏在第二层以下：从任务找所属总图要在“当前工作”页签往下滚近两屏；从总图找这批任务要展开默认收起的文档侧栏；任务列表不能按总图筛选。
- 声明的消费者没有入口：以消费者登录，“待我验收”仍是 0 项，它只列具名的验收接力安排。新版“待我处理”已加“等我使用的交付”，按工作索引里当前交付的声明使用者判断（#229 阶段 5 修复）。
- “任务操作”页签把七八个操作做成折叠块堆在一起，没有权限的几项各写一遍“当前身份没有审阅权限”；记录使用观察要手动填自己的身份 ID。
- “依据复核”有待处理项时，入口在任务页最底部的页签里，首屏没有提示。
- 深链页签参数不一致：任务操作是 `tab=actions`，按名称猜的 `tab=operations` 不生效。
- 页面切换时先闪现上一页，再显示新页；首屏有“读取项目…”“正在读取任务…”两段等待。
