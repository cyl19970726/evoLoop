# 设计原则：简约、阅读优先、事实分明

工作台帮人看清项目里发生了什么，并在需要时与 Agent 沟通。大多数修改由 Agent 经业务 skill 和 CLI 完成（[DEC-030](../decisions.md#用户已确定的方向)），界面因此以阅读为主，操作为辅。本页是改任何界面前都要读的共同原则；颜色、字号等数值见[设计基础](foundations.md)，组件见[组件清单](components.md)，页面骨架见[布局](layout.md)。

## 从业务到界面

人来到工作台，通常要回答下面几个问题。页面、字段和组件都从这些问题推导，而不是从数据表推导。

| 人要回答的问题 | 需要看到的事实 | 在界面上的位置 |
| --- | --- | --- |
| 现在该关注哪件事？ | 工作目标、进展、最近变化、下一责任 | 左栏的对象列表，选中后中间读正文 |
| 谁在接手，是否真的在做？ | 职责、具体 Session、接受记录、当前 Run | 右栏的承接与运行信息，可直达 Session |
| 该等还是介入？ | Agent 回复、工具进展、待答问题、失败 | Session 中间的对话与活动流 |
| 交出来的东西能用吗？ | 固定成果、完成条件、实际使用 | 任务和文档的中间正文，右栏放版本与来源 |
| 为什么总要返工？ | 多轮失败、采用的规则、使用反馈 | 从任务和团队进入复盘，形成下一项改进 |

Task 承载工作承诺，Session 承载持续协作，Document 承载可核的正文。三者分别需要“比较、观察、完整阅读”，在三栏布局里对应左栏列表、中间主体流和右栏信息。对象关系的完整定义见[产品定义](../product/definition.md#核心对象怎样连接)和[任务与文档](../product/tasks-and-documents.md)。

## 十条原则

1. **简约克制。** 一屏最多一个主操作，其余用次要或幽灵样式。颜色只用来表达状态和主操作，不做装饰；不加装饰性阴影、渐变和动画。默认选更安静的写法。
2. **阅读优先。** 正文、对话和全文占中间最大的空间；元数据、来源和诊断放右栏或按需展开。长内容在自己的区域滚动，整页不横向滚动。
3. **先答“现在怎样”。** 详情先回答“现在是什么、为什么、谁接下一步”，再给关系、历史和来源。
4. **每类事实分开说。** 业务状态、运行、同步、知识和使用效果各自显示，不合成一个“全部完成”。常见的区分见下表。
5. **不虚构。** 没有数据就明说没有。不用示意人数、统计或原型数据填充页面。
6. **空、加载、失败、无权限、未知分开显示。** 重新读取时保留上次内容并标“正在核对”；读取失败时说明旧内容仍在，不变成普通空状态。每种情况都写原因和可行的下一步，技术细节放在可展开的诊断里。
7. **原始标识放在来源层。** ID、hash、UUID 不出现在列表单元格、标题和正文里；需要时点开来源或悬停查看。
8. **界面用产品语言。** 不显示内部实现词，例如“PG记录：无在途占用”“原生状态待核”。改写成用户能理解的说法，原词放进诊断。
9. **写入走共同 API。** 页面上的写操作只调用已有且有权限的 API，与 CLI 同一套授权、固定修订和操作回执。保存草稿和操作 ID；结果未知时按原操作查回，不换新 ID 重试。危险或低频操作放进明确的操作层。
10. **返回不丢位置。** 跨页返回保留项目、筛选、所选对象和阅读位置。切换项目、身份或对象时，页面不混入上一个对象的正文、链接或错误。

| 要分清的事实 | 界面表达 |
| --- | --- |
| Task 业务状态与工作进度 | todo / in_progress / done / cancelled 是业务状态；待承接、受阻、待验收说明当前事实，并附原因和下一责任 |
| Role、分派与实际承接 | Role 是持续职责；分派的目标和接受回执才说明谁具体承接，同 Role 不等于已接手 |
| Session 与 Run | Session 就绪不等于 Run 在运行；队列占用另列 |
| 当前与历史 | 已完成或已取消的 Task 保留的分派、Run 和 Session 标为历史 |
| 技术检查与使用 | 交付的技术检查、实际使用观察和有权者关闭分别显示 |
| 消息与同步 | 已保存、已发送、已读、已采用分别显示，不从通知推定已读或已用 |

业务字段和状态转换以[接口合同](../architecture/contracts.md)为准；本表只约定怎样让人分辨，浏览器里不另做一套状态机。

## 信息主次随结果变化

同一项工作在不同阶段，首先要让人看到的东西不同：

- **还没形成工作时**，先看目标、已有反馈和缺项；主要下一步是与现有 Agent 明确一个有界动作。
- **正在执行时**，先看当前任务、承接者、采用的依据和真实阻塞；运行细节按需展开。没有待取舍时，让人确认有人承接和下次回看的条件即可，不需要再催促。
- **运行结束但使用仍失败时**，先看“仍不能完成”、失败步骤、所用交付和接续责任，同时保留技术检查已通过这一事实。
- **使用达标后**，先看谁用哪一版完成了什么、还有什么限制，以及下一步为何继续、调整或停止。

同一任务续跑或返工后，运行与 Session 页先说明“当前在看哪一轮、它与本任务哪次运行有关”：按真实 Run、正式派发和循环归属确定，分开“当前在途”和“最近派发”；关系有歧义时显示未核定；用户主动选了历史一轮后，自动刷新不把它切回。

例子与完整场景见[首次旅程](../product/definition.md#从一个目标走到第一次有效交付)和[交付之后的接续](../product/functional-scenarios.md#交付之后谁接住未完成的工作)。

## 界面用语

界面文字只用中文（[DEC-037](../decisions.md#用户已确定的方向)）。保留原文的只有产品名 evoLoop、模型名、代码、命令、技能名和文件路径；中文与数字、英文之间留一个空格。文档和代码里继续用下表右列的英文名，界面上只出现左列。

| 界面用语 | 文档与代码 | 说明 |
| --- | --- | --- |
| 智能体 | Session | 一个持续工作的执行者，有头像和名字 |
| 统筹 | Leader | 安排智能体、排期，处理资源冲突 |
| 统筹总览 | Leader 编排总览文档 | 统筹写的本轮安排 |
| 复盘 | Evocation | 周期性回看整套工作方式 |
| 职责 | Role | 智能体承担的分工 |
| 成员 | Member（#219 的人类账户） | 只指人，不指智能体 |
| 任务 / 总图 / 依据 | Task / 需求总图 / Basis | 依据是任务固定引用的文档版本 |
| 交付 / 使用记录 | Delivery / Observation | 使用记录是用过之后的反馈 |
| 投递 | Connector delivery | 微信等外部平台网关送来的一批消息；不是任务的“交付” |
| 日程 | Schedule | 定时触发的工作 |
| 合并请求 | Pull request | 代码仓库里的合并请求 |
| 一轮 / 排队消息 / 插话 | Turn / Queued message / Steer | 插话只在支持的运行时出现 |
| 对话线程 | Thread（运行时原生线程） | 智能体在运行时里的一条对话，只在填写或核对路由时出现 |

状态用两到四个字（进行中、待验收、受阻、待返工、等你回答），不用“PG 记录”“原生状态”这类实现词。旧页面在各自迁移的 PR 里改成这套用语。

## 交互怎样闭合

- **默认路径**：人在工作台读到问题，与现有 Agent 沟通；Agent 经业务 skill 和 CLI 提交修改；人回到工作台读回结果。页面上的“已发起”不等于外部会话已接收。
- **从目标形成任务**：首页或现有会话里明确目标、消费者和约束，责任 Session 登记阶段和首项工作。无人承接时显示“待承接”和补位责任。
- **需求纠正**：从文档修订追到受影响的任务，按任务和 Run 的状态逐项记录改用新版、旧版仍适用或待补证。已运行的任务怎样接续见[需求纠正](../product/daily-loop.md#需求纠正怎样处理)。
- **讨论交接**：交接包写明项目、目标、所读依据、要回答的问题和权限边界，由人确认后交给合适的 Session。打开聊天或通知成功不等于决定已执行。

## 动效

动效只用来说明状态变化：展开、收起、面板进出、新条目出现、正在进行。时长 150–250ms，减速收尾；用户开启“减少动态效果”时关闭。不做装饰性或循环动画，进行中的状态用一个小图标表示即可。实现方式见[前端架构](architecture.md#5-推荐前端技术与取舍)。

## 可访问性

- 所有操作都能用键盘完成，焦点清楚可见；仅有图标的按钮要有可读名称。
- 文字与背景的对比度符合 WCAG AA；颜色之外总有文字或图标说明含义。
- 弹窗和抽屉打开时锁定焦点，按 Escape 关闭并回到触发位置。
