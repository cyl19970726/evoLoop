# 来源与演进

这份说明解释 evoLoop 从哪些工作中产生，以及怎样使用已有资产。原始会话和详细审计保留在项目的本地历史资料区，不随公开仓库发布；本文是可共享的抽象说明，不声称公开仓库包含完整审计证据。

## 觉察 Kernel 的贡献

觉察从实际开发会话中观察到：负责人反复补充产品、架构和规范工作，结论需要人工传话，任务缺少连续身份，交付与下一步之间容易断开。它提出通过不同观察视角、共享过程资产和可靠交接来降低这些负担。

我们参考其产品报告的组织方式：先说明问题和用户，再给核心概念、具体场景、范围与验收；参考其架构报告的层次：目标约束、组件与数据流、存储归属、接口、失败恢复、决定和风险。历史报告中的具体数字、技术选型、角色数量和上线状态不直接成为 evoLoop 的当前事实。

觉察仓库仍是独立工程资产。evoLoop 延续问题和方法，不在本轮将旧工程改名、整体搬入或宣称已经兼容。需要复用某段代码时，应先检查其假设、许可证与当前边界，再单独验证。

## 工作台与认知协作带来的要求

后续“认知会话／执行会话”的实践，使关注点进一步落到认识如何产生并改变行动：用户持续纠正目标理解，提出分阶段交付与学习，要求完成后实际使用产品，再决定下一阶段。

因此 evoLoop 把材料、判断、行动和反馈之间的关系作为产品主线。所有 session 形成认识，Wiki 维护者整合和追溯，分工管理者评估协作结构；产品是否变好需要使用证据，不能通过角色齐全、报告完备或任务数量来推断。

## 外教平台的文档实践

外教平台展示了让正式文档源文件进入仓库、用脚本生成 HTML、校验引用与产物一致性的维护方式。它的业务报告生成器依赖自己的结构化数据与架构扫描，不是可以直接搬到任意项目的通用文档站。

evoLoop 采用这套源文件与可重建阅读视图的原则，使用适合当前文档规模的轻量脚手架。我们也吸收巨大内嵌 HTML 容易产生重复变更和冲突的经验：生成目录不进入 Git，公开资源通过明确入口管理。

## 继承与调整

| 继承的意图 | evoLoop 当前选择 |
| --- | --- |
| 任务有身份、交接可追溯 | 第一期使用飞书任务权威，通过适配器补运行合同；不照搬旧自建任务数据库 |
| 从历史识别遗漏的观察视角 | 设分工管理责任，结合历史以外的成果、用户使用、负荷和未来需求 |
| 共享项目认识 | Wiki 独立于开发 repo，Markdown 可以接受；知识系统仍待选定 |
| 产品与架构报告可持续维护 | 正式 Markdown 在仓库，同源构建 HTML；认知正文与原始材料不随仓库发布 |
| 减少用户充当传话和节奏支撑 | 明确交付、接收、验证与结果未知的恢复路径，并在真实工作中测量效果 |

当前方向的权威登记在[决定记录](../decisions.md)。旧设计只提供其当时的经验，不覆盖用户后来的明确纠正。

## 公开资料与本地证据的关系

公开文档应能独立解释目标、方案、已知结果及限制。对不发布的历史材料，使用抽象观察和范围说明；不留下假装可用的本机路径，不把助手回忆当逐字原始记录。

知识底座的实验已有独立[验证摘要](validation-summary.md)。公开摘要提供版本、案例和结论边界；完整日志、模型配置、消费产物与本机证据仍由实验资料区保管。新贡献者可以据公开案例设计新的验证，但仅克隆仓库并不会获得原实验数据。
