# evoLoop 产品定义

2026-10-20 · 产品基线 v0.7，目标体验设计。先从问题、使用者和一段完整经历理解产品，再看支撑机制和验收索引。本文描述期望产品；当前实现程度只由[阶段路线](../roadmap.md#当前基线)说明，设计不等于已经运行。首次旅程及界面映射是本次补全的待验证设计，既有方向见[决定记录](../decisions.md)。

## 一句话定义

**evoLoop 帮助一个人与多个 Agent 持续推进项目：把目标变成有依据的工作，让交付经过实际使用，再用结果修正理解、下一步和协作分工。**

希望减少的是人反复补背景、传话、催促和补救遗漏的负担。人仍负责目标、价值取舍与关键体验反馈；Agent 会话在授权内负责判断、执行、验证和接续。第一阶段聚焦软件产品开发，其他探索型项目是后续适用方向。

## 为什么要做

觉察项目与后续工作台讨论暴露了几类持续问题。以下是需求来源和观察方向，不是本轮重新进行的完整历史审计；来源范围见[来源与演进](../references/lineage.md)。

| 工作中出现的现象 | 我们需要的变化 |
| --- | --- |
| 人类反复说明目标、提醒继续、在会话间转告完成 | 任务有持续身份、责任和可恢复交接，人可以看到接续结果 |
| Agent 写出了报告，却没有使用产品或吸收用户评价 | 阶段目标包含学习问题，完成后沿真实路径使用产物并修订判断 |
| 多轮纠正散落在历史里，新会话仍按旧理解行动 | 当前认识能追到依据和修订，后续任务能发现相关纠正与反例 |
| 一个 session 包含越来越多职责，频繁切换上下文 | 根据观察面、持续责任和协作成本试行新的分工 |
| 产品、架构、规范越写越多，实际工作仍重复出错 | 文档和方法依据使用效果维护，规则可以修订或撤回 |

目标是形成可持续的工作能力。减少人类重复提醒、返工和交接遗漏，是判断这种能力是否发生的主要信号；具体数值基线仍需在真实试点中建立。

## 用户与实际入口

**主要使用者是项目负责人及与其共同工作的领域责任者。** 负责人想知道项目现在为何做这一步、需要自己取舍什么、已交付的东西是否真正有效；领域责任者想准确理解依据、完成本领域工作并让结果接得下去。实际使用成果的消费者可以是负责人、业务用户或另一个 Agent，须按任务明确，不能以作者自己满意代替。

Agent 的一次持续会话称为 **session**；它承载某项职责或临时工作，而不是产品预置的岗位。这里先理解人和 Agent 怎样共同完成工作，具体认知、分工职责在后文解释。

目标产品以项目工作台帮助人阅读依据、作判断和追结果；现有 Codex 聊天继续承载讨论，飞书是可选用的受控协作入口。正式规范从各项目仓库阅读，知识从独立知识空间阅读。这些入口连接同一项目，保留各自的正文和状态权威，不要求人每天在窗口间转述。当前只有文档、隔离实验与合成原型，见[当前基线](../roadmap.md#当前基线)。

## 从一个目标走到第一次有效交付

下面是一段**假设的目标产品经历**，用于说明完整闭环，不是本轮已运行的试点。一个已有导出工具的软件项目收到运营反馈：“拿到 CSV 后仍不能独立完成月报。”负责人想达成的结果是“让运营独立完成一次可核对的月报”，尚不知道问题来自导出内容、使用说明还是交接方式。

| 步骤 | 人和 Agent 经历什么 | 应留下什么，才能继续 |
| --- | --- | --- |
| **J1 — 带着目标进入** | 负责人说明预期结果、不能改变的约束和可投入范围，关联现有项目、可用仓库/反馈；指明谁会实际使用成果。材料不足就保留未知，责任者先确认能否访问必要材料；尚无承接者时，由负责人指定当前会话承担首项工作或明确待承接与补位责任。 | 一个可回读的目标、已知/未知、消费者、权限与资源边界，以及接住这次工作的责任者。已有项目可复用现有依据；新项目可先形成阶段候选，不强制先导入全部历史、连接飞书或建立 Wiki，也不为开始工作先增设长期角色。 |
| **J2 — 形成首阶段和首项工作** | 责任 session 对照反馈与目标，提出阶段交付“让一份真实导出支撑一次月报”和学习问题“当前阻塞由什么引起”。若证据不足，首项工作只复核一条路径；若已有明确且授权内的缺陷，可直接提出修复。负责人仅在目标、权限或资源需要取舍时介入。 | 有理由的阶段候选和一项有范围、输入、责任、交付/消费者验收、停止条件的任务提议；或具体补证/暂缓理由。不是把整个阶段一次性塞入一项任务。 |
| **J3 — 接受并推进工作** | 有权责任者核对接受条件，固定采用的需求与知识依据。执行者复核、修复或委派，保留进度、交付和交接；已有成果或操作结果未知时先核对，避免重复做。 | 接受时的基线、当前责任、可查的产物及接续条件。需求或讨论可先成过程文档再 link 任务；任务执行固定实际依据，不能随上游改版静默换成新版。 |
| **J4 — 交付成为实际使用** | 技术检查后，运营沿原工作路径完成月报并核对结果。若仍卡住，记录失败点并判断返工、改需求还是补证；如果首次工作仅是调查，就先验收调查，再接受后续修复与使用验证。 | 具体产物修订、技术检查、谁实际用了什么及结果。任务自己的验收要求亲用时，缺使用证据不能关闭；纯实现子任务可完成，阶段效果继续未知。 |
| **J5 — 从结果修订认识** | 领域 session 记录哪个解释成立、哪个被推翻；认知责任者综合需求、使用与反例，修订有长期价值的认识。需求改变时逐项复核引用旧基线的未完任务；短小且直接材料已足够的工作可以先直接读材料。 | 带依据的认识变化或“暂不改变”的理由；必要的需求/知识修订与任务影响判断。通知送达、正文发布与后续实际采用分别核对。 |
| **J6 — 回到下一步或结束** | 首页让负责人看见目标差距、决定及后果。授权内的下一动作由可用 session 承接；若目标已达成或继续无价值，就结束并保留理由。之后若持续负担或责任缺口显现，再比较改方法、补容量、临时专项和职责试行。 | 下一动作能指向本轮实际证据，或有理由地停止。形成第二次相连循环后才能评价持续接续；不能用任务、会话或 Wiki 页数增加代表成长。 |

**首次价值发生在 J4 的目标工作变得可完成，并由 J5/J6 改善下一步判断；登记项目、创建文档和启动会话只是支持动作。** 一次调查也可以产生有价值的阶段结论，但不能冒充用户已经完成月报。首次工作从哪里进入（已有聊天、导入项目或工作台入口）属于入口实现选择；上表输入、责任、接受条件与结果不能缺。界面如何承载这段经历见[工作台的旅程映射](workbench.md)，具体操作与缺项处理见[日常工作](daily-loop.md)。

## 核心对象怎样连接

理解旅程只需先分清下列概念；这是使用层的关系，不是要求读者先掌握数据库模型。

| 概念 | 用户为什么需要它 | 与其他对象的关系 |
| --- | --- | --- |
| 项目与阶段 | 知道希望发生什么变化、现在验证哪一段 | 阶段同时有交付和学习问题，决定任务的价值及验收范围。 |
| 过程文档 | 保存需求、任务详述、讨论与决定的完整历史 | Document Table 只含这些过程文档，可先创建后与 Task 多对多 link；任务采用具体修订。 |
| 任务 | 知道谁在什么依据下做什么、到哪一步、如何验收 | 指向采用的需求/知识修订、责任者、交付与实际使用，状态不能代替效果。 |
| 交付与使用证据 | 区分“做出来”和“真正帮助完成工作” | 关联产物修订、技术检查、消费者行为/反馈，进入阶段回看。 |
| 认识与外置 Wiki | 说明为什么这样判断，何时该改变 | 保存来源、解释、反例、适用条件与修订；供后续任务按需读取，不持有另一份任务状态。 |
| 仓库正式文档 | 表达项目当前采用的产品、架构和规范 | 各 repo 的 `docs/` 独立维护，不是 Document Table 行；采纳的过程结论可经审阅纳入，原件保留，引用固定 commit。 |
| 职责与 session | 区分持续负责什么和现在由哪个会话承载 | 同职责续开会话不等于新增岗位；委派仍须有最终责任和结果回收。 |
| 日程 | 按约定时机检查是否需要工作 | 触发按普通任务接受条件判断，日程暂停与在途任务停止分别核对。 |

因此，一条可追溯工作关系是：**目标/阶段 → 采用需求及认识的任务 → 交付与亲用 → 新证据和认识变化 → 需求修订或下一任务**。evoLoop/PostgreSQL 持 Task、过程 Document、日程与跨对象关系；飞书作为 connector 提供投影与受控编辑；Git 正式正文及外置 Wiki 正文各有独立权威。字段和版本细节见[项目数据](../architecture/project-data.md)。

## 核心闭环

**目标与约束 → 有依据的判断 → 任务与实验 → 实际交付和使用 → 反馈与认识修订 → 下一阶段选择。**

每个阶段同时约定交付目标与学习目标。例如，阶段目标可以是“让一个领域 session 发现文档问题、完成修复，并由另一会话使用修复后的文档接续工作”；学习问题则是“现有任务、文档和交接机制是否足以让用户不再传话”。

阶段结束要留下使用记录、目标差距、认识变化和下一动作。一个局部阶段可以以“假设被推翻、应改变方向”结束，只要证据和后续决定明确。不能用所有子任务标为完成来自动判定整体目标达成。

**自动推进的产品目标**是：在已有目标、权限与资源范围内，系统能发现该回看什么、生成或修订有理由的任务、接续执行、使用成果，并把结果带回下一轮；减少用户反复补上这些连接。观察不足时安排有价值的调查，超出目标或授权时请求具体取舍，阶段目标达成或继续投入无价值时允许结束。循环次数、任务数量和持续运行时间不作为成长指标。

## 这里怎样定义认知

在本产品中，**认知工作是围绕目标持续建立和修正对当前处境的理解，使行动有理由、可检验，并能随新证据改变。** 这是服务产品设计的工作定义，不宣称提供完整的认知科学理论。

一份可供下一步使用的认识应能回答：

1. 我们想达成什么，哪些条件决定成败？
2. 目前实际发生了什么，依据来自哪里，什么尚未确认？
3. 哪些解释或方案可能成立，各自的适用条件、代价与反例是什么？
4. 下一步为什么选择这个动作，预期观察到什么？
5. 什么结果会使我们保留、修订或撤回判断？

认识通过阅读材料、操作真实产品、观察结果、比较解释和接受反馈形成。材料包括会话过程，也包括代码、产物、任务、运行状态和用户使用评价。记录时应保留“目标 → 行动 → 产物 → 使用与评价 → 下一步变化”的连续关系。

一项认识的关键价值，是改变行动的选择或成立条件。例如，观察到“新会话没有采用用户纠正”后，要比较究竟是未收到交接、没有读到当前修订，还是读到了却理解错误；不同解释对应不同修复和检验。只有“沟通需要加强”的总结不足以指导下一步，需说明可区分解释的观察及其结果会怎样改变方案。

## 两个维度，四个组成部分

用户确认以两个维度思考产品：**认知演进**回答“我们如何理解目标与现实，下一步为什么值得做”；**协作执行**回答“由谁承担，怎样接续与验证，失败后如何恢复”。两者共同形成有效的 Agent loop：既改善项目的下一步选择，也改善完成工作的方法和分工。

| 产品组成 | 要持续回答的问题 | 必须产生的变化 |
| --- | --- | --- |
| **① 认知循环** | 根据实际工作与用户评价，目标取决于什么？判断怎样变化？现在最值得推进或弄清什么？ | 有依据的阶段选择、学习问题、任务或停止/转向决定，并在授权内推动下一步 |
| **② 动态多 session** | 现有职责为何接不住目标？需要改善方法、补容量，还是拆出持续独立责任？ | 有说明、有工作流程和回看条件的 session/职责安排；效果不好可调整、合并或撤回 |
| **③ Task 与状态机** | 工作由谁负责，走到哪，缺什么，谁接续，何时算完成？ | evoLoop 中的任务状态与真实成果一致；飞书协作视图可对账，执行、交接和未知结果能被核对与恢复 |
| **④ LLM Wiki 与 evaluator** | 认识如何形成可追溯的当前版本？后续 session 用它是否真的改善行动？ | 外置知识持续修订，独立消费和实际效果有证据，评价能反过来改变知识与工作方法 |

认知循环主要体现第一个维度；多 session 与任务机制主要体现第二个维度；Wiki 与评价连接两者。四部分是能力边界，不要求建立四个独立进程或四个固定会话。分层关系见[四部分架构图](../architecture/overview.md#2-分层与依赖)，具体工作过程见[Agent loop](agent-loop.md)，日常入口见[日常工作闭环](daily-loop.md)，人机界面见[项目工作台](workbench.md)，Wiki 的构建与评价见[Wiki 有效性约定](wiki-evaluation.md)。

## 谁负责把循环接起来

领域 session 在本领域形成认识、提出任务、执行或委派修复并验证结果。产品、架构、开发、体验和运维是可能出现的观察面，不是第一天必须建立的岗位清单。

专门认知 session 把领域观察、真实使用和项目目标联系起来，比较解释、识别未知、在授权内推动下一步；初期同时承担外置 Wiki 综合维护。它不是所有局部工作的审批中心，也不代替领域责任者使用产品和修复问题。

分工管理 session 根据积压、返工、切换、交接、产物与用户反馈，判断现有责任能否接住目标；先比较方法/工具、容量和临时专项，再决定是否试行新的持续职责。新职责有工作说明、首项任务、回看与退出条件。四部分是能力边界，可以由现有 session 承担，不要求四个固定窗口或四个进程。

负责人日常可与认知职责讨论下一步，与分工职责讨论责任安排；已接受、授权内工作不依赖每日人工出席。各职责的输入、判断与交接见[Agent loop](agent-loop.md)，具体日常动作见[日常闭环](daily-loop.md)。

## 第一期范围

| 能力 | 第一期边界 |
| --- | --- |
| 项目主数据与协作入口 | evoLoop 在 PostgreSQL 保存任务、日程和原生需求文档及其修订；飞书多维表格提供任务投影与受控编辑入口，外部写入经权限和基线校验 |
| 项目工作台 | 先让人看见待判断、任务和需求版本、依据与异常并完成关键取舍；Codex 聊天、Git 正文与 Wiki 仍由各自权威承载，按[工作台设计](workbench.md)分期验证 |
| 会话协作 | 先适配一个实际可用运行时；明确能读取、派发、唤醒、确认的能力范围 |
| 认知与知识维护 | 专门认知 session 整合并推动下一步，全员贡献；Wiki 外置，允许 Markdown，先验证贡献、修订、消费与评价闭环 |
| 动态分工 | 建立分工管理责任，按证据试行；不为所有项目一次创建全部角色 |
| 正式文档 | 产品、架构、规范和决定记录存仓库，可重建 HTML；可发布内容默认公开 |
| 运行可靠性 | 先限制并发与运行范围，验证重复、未知结果和重启恢复，再扩大能力 |

自动购买资源、无边界扩张 Agent 数量、复制一套独立 Wiki 正文、自研通用知识数据库以及未经验证的多机高可用，不进入首个闭环。后续范围依真实瓶颈决定。

evoLoop 仓库拥有协作支撑代码与自己的正式文档。受管项目的业务代码和正式产品文档仍在各自仓库；项目之间共享方法和接口，不混合任务身份、知识空间或权限。

## 如何判断产品有效

先记录一组可比较工作的基线，再观察引入机制后的变化。下表是评估设计，尚无达标统计。

| 观察对象 | 记录什么 | 防止误判 |
| --- | --- | --- |
| 人类介入 | 重复解释、传话、提醒继续、补救遗漏的次数与原因 | 保留必要的目标决定和体验反馈，不以“人越少越好”评价 |
| 交接 | 交付到接续的等待、遗漏、重复执行、未知结果恢复 | 工具返回成功不能单独证明对方已处理 |
| 认识使用 | 新会话的约束遗漏、错误引用、纠正采用、实际动作变化 | 页数和检索命中不等于有效使用 |
| 产品效果 | 阶段真实操作的完成情况、用户反馈与返工 | 工程自检与用户体验分开验收 |
| 分工收益 | 持续责任是否补齐，切换、协作、维护和模型成本怎样变化 | 角色增加本身不计成功，收益不成立可以撤回 |
| 自动推进质量 | 下一动作的证据、价值与授权是否明确；减少了哪些重复提醒；是否在应停时停止 | 自动创建任务、持续调用模型或扩大分工不等于项目成长 |

知识底座的首轮小样本验证已暴露维护和并发缺口，且未证明优于直接阅读少量材料。见[验证摘要](../references/validation-summary.md)。因此本产品仍需验证长期材料增长、跨阶段修订与实际协作带来的收益。

## 场景索引怎样使用

前面的旅程帮助理解产品；下面 P01—P12 保留需求身份、详细结果和验收，便于设计与实现追溯。**编号不是页面顺序、独立模块或相同优先级。** 按要理解的层次选择：

| 层次 | 对应场景 | 阅读目的 |
| --- | --- | --- |
| 项目推进主线 | P01、P02、P07、P09 | 从目标到领域工作、实际使用与下一动作，对应 J1—J6。 |
| 认识和分工怎样改变 | P04、P05、P08 | 纠正是否影响行动，评价是否可靠，职责调整是否值得。 |
| 体验与支持能力 | P10、P11、P12 | 日程、过程文档和工作台如何支撑主线，而非各自构成项目成功。 |
| 横贯各步骤的质量约束 | P03、P06 | 中断恢复、正式方案一致和可读可用，适用于整段旅程。 |

## 必须支持的场景

### P01 — 从目标形成可推进的阶段

负责人提出目标，责任 session 将目标拆成有交付、有学习问题的阶段，登记依据、限制和验收方式。未知条件进入调查或实验；允许在证据变化后重新选择阶段。

**验收**：新加入的 session 能解释当前阶段为何值得做、完成后怎样使用，以及什么结果会改变下一步；无需靠负责人重新讲完整背景。

### P02 — 领域发现问题并负责解决

架构、产品、体验或开发 session 在实际工作中发现缺陷、新需求或方法问题，进入 evoLoop 同一任务集合，并可在飞书任务表协作。负责人可以自己修复或委派有明确边界的工作，最后回收交付并验证效果。

**验收**：从发现依据能追到任务、责任者、交付和验证；委派后责任不消失，合并代码与产品效果分别可查。

### P03 — 交接可以恢复

执行者提交成果后，接续方能发现并确认所需动作。通知丢失、会话中断、请求超时或运行时暂不支持自动唤醒时，系统保留实际状态和恢复路径。

**验收**：模拟一次中断或丢通知后，重新检查能恢复待处理交付；既不静默遗漏，也不因盲重发造成重复执行。尚无法确定结果时明确显示“未知”。

### P04 — 纠正能改变之后的工作

用户纠正、实际反例或环境变化进入知识维护过程。维护者定位依赖旧认识的页面和未完成任务，修订当前判断、保留来源和适用范围；存在分歧时记录各方依据。

**验收**：一个未参与整理的新 session 能采用纠正后的约束完成具体任务，并能追溯其依据；旧内容不再无说明地成为当前结论。

### P05 — 工作证据推动职责演进

任何 session 都可以提出职责调整。分工管理者结合历史、负荷、返工、用户体验、运行结果和下一阶段需求，区分知识或工具问题、容量不足和独立职责缺口。

**验收**：每项角色试行有问题依据、替代办法、职责边界、交接、观察指标及退出条件。它可以产生新角色，也可以选择改工具、增加同职责实例、临时专项、合并或撤回。

### P06 — 人和 Agent 读到一致的正式方案

产品、架构和规范各有明确正文归属；Git 中的源文件生成 HTML。人能看清目标、状态和关键取舍，Agent 能按当前任务定位相关章节、接口及判据。

**验收**：正式文档可在新 checkout 重建；阅读入口没有依赖本机目录的断链；变化与所描述行为一致。阶段结束实际让使用者或新 session 按文档操作，记录误解和阻塞。

### P07 — 认识能够自主接续下一步

一个阶段交付或出现用户反馈后，专门认知 session 将效果与原需求文档基线、预期和知识修订比较，形成继续、修订、补证、停止或请求取舍的决定。在已有授权内，新任务进入 evoLoop 并被可用 session 承接；需求或认知发生变化时，引用旧基线的未完任务也得到复核。

**验收**：至少观察到两次相连的“行动 → 实际使用 → 认识变化 → 下一动作”，第二次动作能指向前一次的具体证据；不依赖人类再次粘贴背景、提醒完成后通知或替 Agent 决定每个常规步骤。若触发停止条件，系统能够给出依据并结束，而非为保持循环继续造任务。这是待运行的验收场景。

### P08 — Wiki 的贡献可被检验

独立 session 在相同任务与约束下使用 Wiki，评价其能否采用当前认识、追溯来源并完成有用成果；与直接阅读材料等可比入口比较效果及总成本。失效案例进入知识修订或方法改进任务。

**验收**：能够区分来源是否可靠、认识是否正确、消费者是否采用、实际产品是否改善；不把检索命中或模型自评分当作全部收益。实验约定与案例见[Wiki 构建与有效性评价](wiki-evaluation.md)。

### P09 — 真实使用驱动产品成长

各领域 session 在完成真实任务或使用 evoLoop 时，能把遇到的产品或协作机制缺陷、以及新需求提交到 evoLoop 同一任务集合；飞书任务表是可用的协作入口。记录区分来源是否为 dogfood、任务属于缺陷还是需求、提议是否已被接受；dogfood 指真实工作或使用暴露能力差距，并不等同于每次提示词调整。常规且在现有职责授权内的修复可由责任者接受；新方向、争议或跨领域影响交给合适的独立判断者，不让所有事项排队等待同一中心批准。

**验收**：至少一项真实使用暴露的问题保留复现步骤或标明不确定的观察、期望效果、受影响系统/项目、报告者与判断责任者；重复提议归并而新证据仍可追溯。它经判断、执行和目标消费者实际使用后，能解释产品判断或下一动作怎样变化；缺少判断者时仍有明确的补位责任与回看条件。见[日常工作闭环](daily-loop.md)。

### P10 — 约定时间的工作可接续且可停止

负责人或已获授权的 session 可为一次性或周期性工作约定触发时间；触发只检查是否需要按普通任务接受条件推进，不自动认定任务值得做。计划需要时区、错过时机、重叠运行、暂停、停止及责任者的可见语义。

**验收**：一次错过触发与一次重叠触发都能恢复或按约定跳过，并保留理由；暂停只禁止后续触发，停止在途工作需另有请求和核对结果。没有新证据或有效待办时，周期检查不制造空任务；执行结果仍经过原任务的消费者验收。此为待实现的产品场景，不表示已有自动化服务。

### P11 — 工作文档驱动任务，并把成立结论沉淀为正式文档

**场景**：需求、任务详述或技术讨论形成有身份和修订的过程文档，Document 与 Task 可直接多对多关联，任务采用固定需求基线；新需求被采纳后，责任者逐项复核旧基线任务及支持或挑战它的 Wiki 认识。长期成立的结论可经仓库审阅纳入正式文档，原讨论及未采纳意见可回查。

**用户结果**：过程文档在 Document Table 中打开全文；repo `docs/` 从独立入口读取，Wiki 保存在仓库外。修订和整理不会把三者变成同一份正文。任务或知识引用正式文档时使用仓库路径和固定 commit。

**验收**：用一次真实需求改版核对两个引用旧基线的任务：一项保留原基线记录并按新版调整验收，另一项记录旧版仍适用的理由；相关 Wiki 认识进入回看。新消费者按选定基线完成工作，交付、亲用、认识变化及下一动作可追溯。飞书旧版编辑与新基线冲突时，保留原提议，标为待处理且不静默覆盖；最终采纳决定及接受者可追溯。一次多来源到多目标的正式文档整理，能从固定过程来源追到采纳范围、目标段落和合入 commit，并从正式文档回查依据；原件、未采纳意见和旧任务基线仍在。任务完成、PR 合入、报告构建与使用效果分别核对。此场景尚未运行。

**详见**：[工作台的全文阅读](workbench.md#从表格打开完整过程文档)保留 Markdown/HTML 原件、资源、版本与返回列表的产品判据；[过程文档和仓库正式文档](workbench.md#过程文档和仓库正式文档的关系)说明用户如何选择性沉淀；[项目数据](../architecture/project-data.md#3a-工作文档怎样沉淀为仓库正式文档)与[接口合同](../architecture/contracts.md)维护关系、旧版编辑冲突和整理流程。

### P12 — 工作台让人看见依据、取舍和后果

负责人从项目首页准备分工与下一阶段两类讨论；领域责任者从待判断事项、任务和证据继续工作。知识空间是独立入口，可按专题浏览知识点卡片、阅读外置 Wiki 完整修订、追溯来源与相关认识并提交纠正。需求文档、Git 正式规范引用、Session 职责、交付与亲用结果也有可追溯入口；任务、运行、同步、知识和实际效果各自显示状态。现有 Codex 聊天仍由 Codex 承载，工作台提供概要、跳转和受控工作入口。

**验收**：一名不掌握历史聊天的新使用者能从首页找到当前目标、一个待取舍问题的相反依据及责任者，完成取舍后追到需求/任务/知识修订和消费者使用结果；另一个使用者能从任务反查固定基线并识别飞书同步冲突。第三名使用者不经讨论也能从专题进入完整知识页，核对来源、反例和版本，提交纠正并看到正文是否实际更新。桌面和手机都能读到关键状态与反例，不靠用户在会话间转告。页面、动作和分期见[项目工作台](workbench.md)；待判断、日程/异常与知识效果评价也须有明确入口。参考 nashsu 的代码复用不改变这些产品判据，具体实现见[Wiki 集成方案](../architecture/wiki-integration.md)。此场景尚未运行。

## 产品文档如何继续演进

需求或体验变化先更新本文相应场景与验收，涉及边界或交接时联动[架构](../architecture/overview.md)，涉及执行方法时联动[开发规范](../development/standards.md)。关键方向记录在决定登记中；认识形成的过程与原始材料继续留在独立知识空间。

正式产品文档表达当前采用的目标和方案。产品维护者需要用实际阅读、执行和使用反馈验证表达效果，并把重复出现的理解问题转成改进任务。
