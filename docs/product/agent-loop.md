# Agent loop：从认识到下一步

2026-10-20 · 产品行为设计，尚未部署。先读[产品定义中的首次旅程](definition.md#从一个目标走到第一次有效交付)，了解一个目标怎样走到首次交付及真实使用；本页接着解释**为什么下一步能被判断、承接和复核**。它回答四部分在 J1—J6 各做什么，不是另一条入门故事。两个贯穿维度是**认知演进**与**协作执行**；整体关系见[架构图](../architecture/overview.md#2-分层与依赖)，主数据边界见[项目数据](../architecture/project-data.md)。

## 一轮循环应留下什么

一次有效循环要能连接“当时希望什么 → 观察到什么 → 判断怎样变化 → 为什么选择下一动作 → 谁承接并做出了什么 → 实际使用后怎样”。认识可以支持继续，也可以要求补证、改方向或停止。下表把首次旅程的交接点映射到机制；J1—J6 是阅读顺序，不代表必须依次创建六个任务或六个 session。

| 旅程交接 | 主要机制与责任 | 输入 → 可观察输出 | 人与 Agent 的取舍 |
| --- | --- | --- | --- |
| J1 → J2：目标到首步 | ① 认知循环；现有责任 session 综合目标、材料与未知 | 目标、约束、消费者 → 阶段交付、学习问题、首个有界动作 | 授权内可提出并推进；目标与授权缺口交人作具体取舍 |
| J2 → J3：选择到执行 | ③ Task 与状态机、② session 分工；领域责任者承接 | 选择依据、接受条件 → 固定需求基线的任务、责任与接续条件 | 证据足够就做，缺证先有限补证；新职责先诊断和试行 |
| J3 → J4：交付到使用 | ③ 区分任务、运行和效果状态；领域责任者交付，目标消费者亲用 | 成果与技术检查 → 使用过程、未达成处与反馈 | 技术通过由执行者核，使用效果由真实消费者核 |
| J4 → J6：反馈到下一轮 | ④ 有必要时持久认识并评价，① 复核下一动作 | 使用差异、来源及反例 → 受影响认识/任务的复核，继续、补证或结束 | 认知责任者综合；改变目标或越权时请有权者决定 |

首次引入时先由现有 session 承担必要职责，按证据决定是否拆分。运行机制负责发现触发、派发与回收，认知判断由有任务上下文的 session 完成；定时运行本身不会产生有价值的认识。输入可以是已有项目材料，也可以暂时只有人的目标；未知应保留为未知，不以接入全平台或建立 Wiki 作为首步条件。

## ① 认知循环：持续决定下一步为何值得做

在 J1—J2，现有责任 session 从目标、约束、已有材料和目标消费者提出阶段交付、学习问题与首个有界动作；已有证据足以判断时直接做，缺关键证据时先安排能改变选择的补证。J4—J6 再用真实使用反馈复核原判断。领域 session 在工作中形成局部认识，专门认知 session 汇集跨领域判断并推动经授权的下一动作；业务 session 继续保有自己的判断、修复和验证责任。

**触发条件：** 阶段交付或实际使用结束、用户纠正、来源/环境变化、执行前提被推翻、交接反复失败，以及约定的阶段回看。可配置周期检查用来发现遗漏；没有新证据时允许保留原判断，不要求每次检查制造新任务。

**下一步选择的说明：** 关联目标、来源与知识修订；写明观察和解释、备选方案、选中理由、预期效果、反证/停止条件、责任者、验收及资源范围。调查任务还需说明“查明不同结果后会怎样选择”，避免调研无限扩张。

**自动推进边界：** 既有授权内的常规工作可以登记、承接和执行，无需用户逐步传话。改变目标、超出权限或资源约定时，呈现具体取舍；阻塞时记录缺项和恢复条件。总体目标不因任务全部完成而自动达成，也不因出现新想法就无限扩大。

## ② 动态多 session：先诊断，再改变分工

J2—J3 默认由现有责任 session 承接；J5—J6 若反复出现独立责任缺口，再检查是否需要改变分工。分工管理 session 综合完整工作过程、任务积压、上下文切换、返工、交接等待、代码/运行结果、用户体验和下一阶段需求。任何 session 都可以提交分工建议，专门认知 session 也能提供跨领域依据。管理者负责比较替代方案与回看效果，不替各领域审批全部工作。

**每个新增 session 都要有工作说明。** 它至少绑定一个职责或临时任务，说明为什么现在需要、承担的目标、输入及当前修订、可操作范围、首项任务、输出与验收、触发/工作/交接流程、完成或停止条件。沿用既有 Role 时引用其当前说明并补实例差异；新增 Role 时还必须提供以下依据：

| 提案要素 | 必须说明 |
| --- | --- |
| 具体缺口 | 哪些工作/反馈显示责任没有被持续承担，为什么不是知识、工具或容量问题 |
| 替代办法 | 改现有方法、续开会话、补实例、临时专项能否解决，各自成本如何 |
| 职责边界 | 独立目标、观察范围、输入输出、可写资产、与现有责任重叠时怎样处理 |
| 工作流程 | 何时检查或接任务、读取哪些材料、怎样判断与修复、向谁交付、怎样确认被使用 |
| 试行与退出 | 首批任务、原有基线、回看时点/触发、收益判据、成本限制及撤回后的交接 |

例如，开发 session 偶尔遇到一次部署失败，可以先修复并补运行说明。若版本发布、告警响应、恢复演练持续挤占产品开发，且有独立目标和观察面，再提出运维职责试行。依据是实际工作负担、失效模式与未来需求，不能只因为项目“变大”就自动增岗。

## ③ Task 与状态机：让选择可靠地变成工作

J2 的阶段候选不等于一项执行任务；从中提出的具体工作进入统一任务集合的“待判断”，满足接受条件、确定责任和授权范围后才转为“可做”并在 J3 执行。需要补证时可先接受一项有限调查，不能把“已有任务记录”误作“已接受或已派发”。evoLoop 是任务与日程的事实源，以 PostgreSQL 保存身份、状态和修订；飞书多维表格是任务投影与受控协作入口。统一任务机制承接需求、缺陷、调查、实现、知识维护和职责试行；认知 session 与领域 session 都可提出任务。原生需求文档独立保存目标、范围与验收的版本，任务引用接受时的需求基线。重复提议归并时保留各自依据与验收。

**三类状态分别记录，互相核对：**

| 状态 | 回答什么 | 示例 |
| --- | --- | --- |
| 业务任务 | 接受做什么，谁负责，交付是否符合该任务判据 | 文档修复已交付完成 |
| 运行操作 | 派发/停止/写入是否真实发生，是否需要对账 | 派发超时，是否创建 session 暂未知；不能盲目重发 |
| 效果验证 | 在目标使用场景是否达到预期 | 文档已修复，但新用户接入体验仍未验证 |

任务的验收包含实际使用时，没有使用证据就不能关闭该任务；纯实现子任务可以完成，关联的阶段效果仍保持待验证。这样既允许细分工作，又不把“实现任务完成”升级为“产品目标已达成”。

**外部协作与接续结果：** evoLoop 保存任务和日程主记录，飞书提供投影及受控编辑。旧版编辑冲突保留原提议和处理责任，不静默覆盖；飞书断线不抹掉核心任务。交付后要能查到接续责任者是否处理、目标消费者是否采用，即使通知丢失也能从持久记录发现待办。阻塞、暂缓、取消及结果未知保留理由、责任和在途结果；恢复先核实际状态，不能盲重发。身份映射、版本校验、同步、派发、停机恢复和停止回执的具体语义只在[项目数据](../architecture/project-data.md)、[接口合同](../architecture/contracts.md)与[Codex 接入](../architecture/codex-integration.md)维护。

真实使用中提出 dogfood issue、新需求判断、负责人日常两类讨论与定时工作的具体行为见[日常工作闭环](daily-loop.md)。它们进入同一任务和认知循环；调度与运行时接入见[Codex 接入架构](../architecture/codex-integration.md)。

## ④ LLM Wiki 与 evaluator：让认识可积累、可质疑、可检验

J4 的真实使用若改变跨 session、跨任务仍需使用的判断，J5 才有必要把来源、反例和适用条件持久成认识；一次性材料足以支持眼前任务时，可直接引用材料。Wiki 供各 session 按任务读取，专门认知 session 负责综合判断和初期维护。正文权威在开发仓库外，evoLoop 保存任务及必要引用，边界见[项目数据](../architecture/project-data.md)。

evaluator 是一组评价工作和可复核方法，可由独立 session、确定性检查与人类实际使用共同完成，初期无需再设一个常设角色。它要分别回答来源是否忠实、认识是否正确、纠正是否传到旧页与依赖任务、消费者是否采用、真实成果是否改善，以及收益是否抵消总成本。

第四部分的完整建设流程图、对照设计和案例见[Wiki 构建与有效性评价](wiki-evaluation.md)。评价发现的问题回到对应维护/修复任务，并影响下一轮认知选择；通过检索测试并不等于阶段产品效果通过。

## 用一个连续场景验收四部分

以下是 P07 的拟议**跨两次行动**验收，尚未运行；它接在[首次旅程](definition.md#从一个目标走到第一次有效交付)之后，检验机制能否让第二次行动采用第一次使用所得认识，而非重复一遍入门故事：

1. **看到差距。** 第一次交付经目标消费者实际使用后暴露未达成处，领域 session 保留步骤、产物与评价。
2. **形成选择。** 认知 session 比较改需求文档、补工具或试行新职责，选择能检验关键解释的最小行动，关联需求基线、知识修订与 evoLoop 任务。
3. **可靠执行。** 演练派发回包丢失，先确认已有实例，避免重复执行；执行中续开同职责 session，Role 数不增加。
4. **检查实际效果。** 新消费者按修订后的依据完成第二次真实任务。Wiki evaluator 核对认识和来源是否被采用，阶段评价检查任务结果与人类反馈。
5. **调整分工与认识。** 若多次出现持续独立责任缺口，试行新职责并交付说明/流程；收益不成立就撤回，交接未完任务和知识。
6. **接续或结束。** 根据实际效果安排下一动作、补证或停止，并让下一 session 采用最新判断，形成第二次可追溯循环。

记录约束遗漏、返工、重复提醒、交接等待、未知结果恢复、知识修订采用、实际使用效果与总成本。是否有效由这些变化决定，具体基线和判断标准在试点前约定；当前没有达标统计。
